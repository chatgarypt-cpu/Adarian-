> 四层工作流：Owner Brief → Iteration Contract → Runtime Dispatch → Evidence / Closeout

## 第 1 层：Owner Brief（人话摘要）

**1. 这轮干嘛？**

把当前 stdlib http.server + 静态 HTML 的前端，重构为 Flask REST API + Vue 3 SPA。按产品同学出的 8 步工作台原型（事件录入 → 报告生成）分 Sprint 垂直切片交付。

**2. 为什么现在做？**

产品同学已经用手写 Prototype 定义了完整的 8 步工作流（seed → config → models → run → review → report → history → settings）。当前 `serve` 子命令基于 stdlib http.server，只有简单的模型选择和启动按钮，接不住这个产品愿景。同时，产品需求明确了"附录 A 固定输出"等能力，需要一个可迭代的前端底座。

**3. 谁调度？谁执行？**

- 调度：Hermes（本次 dispatch）
- 执行：Codex CLI（每节点独立 dispatch）
- 审查：Hermes（每节点 dogfood 验证后汇报 Owner）

**4. 单节点还是多节点？**

workflow_dag — 6 个节点，串行执行。节点间有数据依赖（N+1 依赖 N 的产出）。

**5. 会碰哪些文件？**

```
src/adarian/serve/          ← 新增 Flask API 包
frontend/                   ← 新增 Vue 工程（项目根）
pyproject.toml              ← +flask, flask-cors 依赖
adarian.sh / start.command  ← Goal 6 改 serve 入口
```

**6. 做完我看什么？**

浏览器打开 `http://localhost:9788`，完整走一遍 8 步工作流：
1. 贴 seed 文本
2. 配推演参数
3. 选模型
4. 启动推演 → 看到实时进度
5. 查看结果对比
6. 生成报告
7. 看历史任务
8. 改设置

每步界面数据来自真实后端 API。

**7. 什么情况必须停？**

- Codex 修改 `src/adarian/phase*/`、`src/adarian/analysis/`、`src/adarian/parser.py`
- Codex 修改 `simulation_dataset.json` schema
- Codex 删除或重写 `batch.py` / `run.py` 等 CLI 入口

### 12. 运行管理与幂等设计

#### 12.1 Problem

用户可能多次点击"开始推演"按钮，或在网络闪断后重试。同一份 seed + 配置不应重复运行。

#### 12.2 方案

三层防御：

**第一层 — 前端按钮状态**
`POST /api/run` 点击后按钮立刻 disable + spinner，防止重复提交。请求完成后（成功或失败）恢复按钮状态。

**第二层 — API 幂等性（idempotency key）**
每个 `POST /api/run` 请求携带一个从 `seed_text + 配置参数` 计算的 SHA256 签名作为 `idempotency_key`：

```
POST /api/run
{
  "seed_text": "...",
  "config": { ... },
  "idempotency_key": "sha256(seed_text + json(config))"
}
```

后端维护一个 LRU 内存缓存（最近 100 条映射），收到请求时：
1. 查询 `idempotency_key` 是否已有对应 `batch_id`
2. 有 → 返回已有 batch_id + 状态（不重复创建）
3. 无 → 启动新推演，记录映射

**第三层 — 并发上限**
在同一时间只允许最大 `max_concurrent` 个 batch 运行（默认 3）。超过上限返回 429 + 当前活跃 batch 列表，前端提示用户等待或取消其他任务。

#### 12.3 World 级重试与错误恢复

**核心原则：batch 是容器，world 是执行单元。一个 world 失败不影响其他 world。**

```
batch_20260624_183101/
├── world_0 (model A) → ✅ 完成
├── world_1 (model B) → ❌ 失败（连接超时）
└── world_2 (model C) → ✅ 完成
```

**重试机制：**

用户可以在运行监控页或结果审查页看到每个 world 的状态标记，对失败的 world：

1. **一键重试** — 点击失败 world 的"重试"按钮
2. **重新选模型** — 在弹出菜单中更换模型（比如 model B 挂了，换成 model D）
3. **复用已产出数据** — 重试只跑该 world 的管线，不碰其他 world 已有结果

API：

```
POST /api/run/<batch_id>/worlds/<world_id>/retry
{
  "model": "qwen3-30b-tke",
  "description": "替换挂了模型B"
}
```

执行逻辑：
1. 杀该 world 的旧进程（如果还在跑）
2. 清空该 world 的输出目录
3. 用新模型重新跑完完整管线
4. 更新 batch 状态

**取消机制：**

| 操作 | API | 行为 |
|------|-----|------|
| 取消单个 world | `POST /api/cancel/<batch_id>/<world_id>` | SIGTERM → 3s → SIGKILL，不删已产出 |
| 取消整个 batch | `POST /api/cancel/<batch_id>` | 遍历所有活跃 world 子进程，逐个清理 |

取消的 world 标记为 cancelled，不影响其他 world。

**Token 效率保障：**
- 只重试失败的 world，不重跑成功的
- world 间无数据依赖（Phase 1-3 管线独立）
- 取消即止损，不等超时自动失败
- 结果审查页展示各 world 状态，failed 的数据不参与聚合

#### 12.4 历史任务数据来源

`GET /api/history` 扫描 `outputs/runs/` 目录，不写额外中间文件。

数据来源：

| 字段 | 来源 |
|------|------|
| batch 元信息 | `batch_config.yaml` 或目录名解析 |
| event_name / event_scale | `world_0/simulation_dataset.json` → `run_info` |
| risk_verdict | 逐个 world 读 `simulation_dataset.json` → `risk_verdict.level` |
| risk_type_classification | `simulation_result.risk_type_classification.primary_types` |
| 状态判定 | `run.log` 末尾是否有完成标记，或目录 mtime |

**不需要额外数据库。** `outputs/runs/` 本身就是历史存储，扫描 + 解析够用。
