# 迭代计划：v1.3.2 — 风险类型分类体系扩展 (✅ 已完成)

## 背景

当前系统仅支持 13 个风险类型（RISK_TYPE_LABELS），且 `classify_risk_types()` 主要基于关键词匹配 + audience mode + 极化阈值，产品侧判定其为"过于泛化，主要风险类型容易变为负向叙事风险"。

产品侧已交付 v0.2 规格文档（`docs/archive/audit/productside_review/政府治理视角舆情风险分层与等级映射清单_v0.2.md`），定义了 20 个二级风险类型、5 个一级风险域。经混合检索补充缺口后，本次迭代扩展为 **6 个一级域、26 个二级类型**，统一维护在 `spec/risk_mapping.yaml` 中。

## 架构设计

```
Agent（压缩的上下文 + 26 个类型的精简规范）
  ├── 规范：v0.2 §3 总表中的类型名 + 典型场景 + 触发方向
  ├── 不注入：每类全量的触发线索/四档表现/正反例（prompt 会炸）
  └── 输出：primary_types（top-3，从 26 个中选）
        ↓
code（TYPE_TO_DOMAIN_MAP，静态 dict）
  ├── primary_types[0] → primary_domain
  └── TYPE_TO_DOMAIN_MAP[type] = domain（26 个类型固定映射）
        ↓
dataset.risk_type_classification
  ├── primary_types         ← Agent 输出 top-3
  ├── type_labels           ← 对应中文标签
  ├── primary_domain        ← code 映射（#1 类型所属一级域）
  └── primary_domain_label  ← 对应中文标签
        ↓
Phase 4（纯消费，.get() 读）
```

**Prompt 组成：** 每个二级类型只保留 1 行精简描述（key + label + domain_label + 典型场景）。26 行合计约 600 token。全量注入 Qwen 32K 上下文窗口，不到 5%。不触发线索/正反例/四档表现。Agent 基于类型名称 + 典型场景的语义判断做选择。

**分级索引机制：** `primary_domain` 是 code 从 `primary_types` 的 #1 类型推断的，属于 code-owned 静态映射。未来新增二级类型只需追加到 `TYPE_TO_DOMAIN_MAP`，不动 Agent prompt，不动一级域枚举。

## 红线

1. **不改 `simulation_dataset.json` 的顶层 schema 结构** — 只能在现有 `risk_type_classification` 字段内扩展，不新增顶层 key、不改 _schema_version
2. **Agent 选二级类型（top-3），不做一级域输出** — 一级域由 code 映射，不在 Agent 输出 schema 中
3. **prompt 是压缩的** — 只注入 v0.2 §3 总表的精简信息（类型名 + 典型场景 + 触发方向），不注入 §4 的全量触发线索/四档表现/正反例
4. **TYPE_TO_DOMAIN_MAP 是 code-owned 静态 dict** — 不是 Agent 输出，也不是 if/else 规则链。新增二级类型只改这个 dict
5. **Phase 4 不做任何分类逻辑** — Pure consumer 原则已落地，Phase 4 只能从 dataset 消费 `risk_type_classification`
6. **不改变 `risk_level` 判定逻辑** — LOW/MEDIUM/HIGH/CRITICAL 的 `assess_risk()` 逻辑不动
7. **一次迭代只建骨架** — 不设计"自动化 vs 配置"的开关/插拔，不做 Agent 多级兜底

## Goal 2 — RiskClassifier Agent（全量 26 类型 + 单次 LLM 分拣）

**变更原因**：现有的关键词匹配规则覆盖不了语义判断。改为 LLM Agent，读取压缩的结构化上下文 + 26 个二级类型的精简描述，一次性输出 top-3 风险类型。

```
Phase 3（仿真引擎）→ tick_logs + x_t_sequence
  ↓
src/analysis/（分析层）
  ├── risk_analyzer.py
  ├── inflection_detector.py
  ├── stance_analyzer.py
  └── classifier.py（新建）
        └── RiskClassifier.classify()
              ├── 构造 query_text（压缩结构化上下文）
              ├── 读取 26 类型的精简映射表
              └── 1 次 LLM 调用 → ClassificationOutput
  ↓
src/parser.py（编排聚合层）
  ├── 调 RiskClassifier.classify() → primary_types
  └── TYPE_TO_DOMAIN_MAP[primary_types[0]] → primary_domain
  ↓
simulation_dataset.json
  ↓
Phase 4（纯消费）
```

**为什么不开销与效率担忧**：
- 26 个类型的精简描述（每类 1 行：key + label + 典型场景）合计约 600 token。加上 system prompt（~200）+ query_text（~400）+ schema（~100），总 prompt 约 1,300 token。Qwen 上下文窗口 32K，占用不到 5%
- 单次 LLM 调用约 15-30s，占总 pipeline 耗时（~414s）的 5-7%
- embedding recall + 相似度检索虽然快，但引入新依赖（embedding model）+ 多一步调用 + query 压缩调优成本。当前 26 类规模的收益不足以覆盖这套基础设施

**Scope**：
- 新增 `src/analysis/classifier.py` — `RiskClassifier` 类
  - `_build_query_text()`: 从 `simulation_result` + `source_context` 压缩为稳定 query，包含：event_name / event_type / risk_level / key_entities + roles / key_groups + final attitude / representative_comments（3-5 条摘要）
  - `_classify()`: 1 次 LLM 调用。输入：压缩后的 query_text + 26 个二级类型的精简映射表（来自 `spec/risk_mapping.yaml`，每类 ID + label + domain_label + 典型场景 1 行）。输出：Pydantic schema 约束的 `ClassificationOutput`
  - `classify()`: 编排 _build_query_text → _classify → 返回 ClassificationOutput
- Agent 输出 schema：`ClassificationOutput`（`primary_types: List[str]` 3 个，从 26 个类型名中选择）
- 26 个类型的完整描述（触发线索/正反例/四档表现）不注入 prompt，只保留在 `spec/risk_mapping.yaml` 中供查阅
- 现有 `classify_risk_types()` 保留原样，作为 Agent 失败时的兜底
- `primary_domain` 在 parser.py 中 code 映射：`TYPE_TO_DOMAIN_MAP[primary_types[0]]`

**失败路径**：
1. Agent 返回非法类型（不在 26 个列表中）→ 丢弃该项，不足 3 个时用 `classify_risk_types()` 补齐
2. Agent LLM 调用失败 → fallback 到 `classify_risk_types()` 的输出
3. `TYPE_TO_DOMAIN_MAP` 缺失 → hard fail，不写入 dataset

**文件变更**：

| 文件 | 改动 |
|------|------|
| `src/analysis/classifier.py` | **新建** — RiskClassifier（_build_query_text + _classify + classify） |
| `src/schemas/phase3.py` 或新建 | **新建** Pydantic schema `ClassificationOutput` |
| `src/parser.py` | `parse()` 中新增 `RiskClassifier.classify()` 调用 + TYPE_TO_DOMAIN_MAP 映射 `primary_domain` |
| `src/whitebox/token_tracker.py` | `_PHASE_MAP` 注册新的 caller 函数名 |

**验收**：
- 对 test8 seed 文本，Agent 输出 top-3 至少 2 个符合预期（如"平台治理与消费争议外溢风险"、"负向叙事聚合风险"）
- `primary_domain` 通过 TYPE_TO_DOMAIN_MAP 正确映射
- Agent prompt 总 token ≤ 1,500
- 整条 pipeline 耗时增加 ≤ 30s

**红线**：
- Agent 不做一级域输出——域由 code 映射
- Agent 不做自由文本联想——推理基于 query_text + 类型映射表
- prompt 中每个类型只保留 1 行精简描述，不注入触发线索/正反例/四档表现
- 不改变 `assess_risk()` / `risk_level` / `audience_mode` 等现有逻辑

## 观测层设计决策

### 分析子模块的 phase 标记

当前分析层（`RiskAnalyzer` / `InflectionDetector` / `StanceAnalyzer`）为纯代码计算（毫秒级，无 LLM 调用），运行时观测上不需要独立的 phase 标记。在 `parser.py` 中将其全部归入 `phase3_parser` 一个条目即可。

**何时需要加 phase 标记**：当分析层引入 LLM 调用时（如本迭代 Goal 2 的 `RiskClassifier`），必须在 `parser.py` 的调用点周围加 `logger.log_phase_start/end`，否则该 LLM 调用不会被 `TokenTracker` 的 per_phase 摘要捕获，run.log 的 PHASE SUMMARY 中也看不到耗时。

### TokenTracker 的自动捕获

`RiskClassifier` 的 LLM 调用通过 `LLMClient.register_observer()` 被 `TokenTracker` 自动捕获，不需要额外 wiring。但 per_phase 归类依赖 `TokenTracker` 内部的 `_PHASE_MAP`（caller 函数名 → phase 映射），`RiskClassifier` 的 caller 函数名需要在 `TokenTracker._PHASE_MAP` 中注册，否则被归入"其他"。
