# 🧠 架构变更说明（新增关键模块）

### 当前结构问题
- 当前 chain 执行与 profiling 主控处于同一进程控制面
- runner-level timeout 只能结束“等待”，不能可靠结束底层同步调用
- 线程级 timeout 对同步 SDK / HTTP 调用缺乏真正 kill 能力
- 该问题在单轮小规模运行下尚可接受，但在后续并发场景中会迅速放大

---

### 目标结构（本次之后）
列出模块划分：

- Module A：`Parent Orchestrator`
  - profiling 主控，负责 spawn / monitor / kill 子进程
- Module B：`Chain Worker Subprocess`
  - 子进程内执行单个 chain request 或单个 case-model 执行单元
- Module C：`Termination Recorder`
  - 将 timeout 与 kill 结果写入 raw log

# 🔧 详细修改指令（给 Codex）

## 任务 1：将 chain 执行抽离为 subprocess worker
**目标**：
把当前 chain 单元执行从主进程 / 线程内调用改为独立子进程执行。

**输入**：
- `profiling/chain_runner.py`
- 当前 chain 单元执行逻辑

**输出**：
- 一个可被主进程调用的子进程入口，例如：
  - `profiling/chain_worker.py`

**实现要求**：
- 每次只处理一个最小 chain 执行单元
- 输入输出必须结构化
- 子进程退出码与结果 payload 必须可被父进程判定
- 不允许在第一版就引入复杂 IPC 框架

---

## 任务 2：实现 subprocess 级 spawn / timeout / kill
**目标**：
让 profiling 主控能够对单个 chain 子进程执行可控管理。

**输入**：
- chain 执行单元参数
- timeout 配置

**输出**：
- 一个统一调用层，例如：
  - `run_chain_in_subprocess(...) -> ExecutionOutcome`

**实现要求**：
- 至少支持：
  - spawn 成功
  - 正常完成
  - timeout 后 kill
  - 子进程异常退出
- timeout 后必须执行 kill，而不是只结束等待
- 若 kill 失败，必须显式记录，不允许伪装成功

---

## 任务 3：raw log 增加 execution/termination 字段
**目标**：
让日志能反映 timeout 后是否真实终止。

**输入**：
- chain raw log 现有字段

**输出**：
- 新增最小字段：

```json
{
  "execution_mode": "subprocess",
  "timeout_triggered": true,
  "termination_method": "kill",
  "timeout_final_state": "killed"
}
```

**实现要求**：
- 不改变已有 `request_id / attempt_id` 语义
- 字段缺失时必须有明确默认值
- 不允许 aggregate 层自行猜测 termination 结果

---

## 任务 4：aggregate 兼容 execution hygiene 字段
**目标**：
在不改变 v1.1.19 主状态判定逻辑的前提下，补充 execution hygiene 观测。

**输入**：
- chain raw logs
- 新增 execution / termination 字段

**输出**：
- 可选摘要指标：
  - `subprocess_execution_count`
  - `timeout_count`
  - `killed_count`
  - `kill_failed_count`
  - `worker_exit_abnormal_count`

**实现要求**：
- 不要因本轮新增字段而重写 aggregate
- `overall_status` 逻辑保持 v1.1.19 收口结果

---

## 任务 5：做一次小规模受控验证
**目标**：
验证 subprocess isolation 是否让 timeout 后的运行面更干净。

**输入**：
- 当前小规模 full profiling 配置
- 低并发（2~4）试探配置

**输出**：
- 一次验证记录，至少回答：
  - timeout 后子进程是否被真正 kill
  - 是否仍存在持续后台诊断日志
  - kill 结果分布如何
  - 是否具备下一轮更高一级并发试探条件

**实现要求**：
- 本轮只允许小规模受控测试
- 不允许上正式高并发压测

---

# 🔒 实现约束（非常重要）

- 不允许继续在线程 timeout 封装层做复杂补丁
