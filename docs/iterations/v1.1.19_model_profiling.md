# 📦 Profiling 核心原则

任务书的核心原则是：

```text
Measure first, then schedule
```

即：先测真实性能，再做调度决策。
评估维度应覆盖 latency、throughput、concurrency，而不是仅凭经验判断。

结合当前项目的真实执行方式，本次 profiling 进一步落到两个层面：

1. **基础性能**：模型本身的响应速度与并发能力
2. **真实链路性能**：模型在 Generator → Validator → Retry 业务链路中的可用性与稳定性

# 🧪 测试分层设计

## Layer A：基础性能层（Simple Prompt）

目标：测基础延迟、基础并发能力、API 稳定性。

### Simple Prompt

```text
请输出 JSON：
{
  "summary": "50字以内",
  "risk_level": "low/medium/high"
}

事件：
某品牌因客服回应不当引发争议，网友出现批评与辩护两种声音。
```

### 记录指标

* simple_latency
* simple_timeout_rate
* simple_error_rate
* simple_concurrency_performance

---

## Layer B：真实生成层（Generator）

目标：测真实业务复杂任务承载能力。

本层直接使用当前项目已有的原装 prompt：

* `GENERATOR_SYSTEM_PROMPT`
* `GENERATOR_USER_PROMPT`

其任务特征包括：

* 长 system prompt
* 强 JSON schema 约束
* event_entities + opinion_spreaders 双列结构
* I / P / C 约束
* estimated_percentage 约束
* persona 字段差异化约束
* related_event_entity 约束
* can_speak / original_statement 业务约束

这类 prompt 已明显超出普通复杂问答范畴，更接近真实业务链路，因此应作为 complex profiling 主样本。

### 记录指标

* generator_latency
* generator_timeout_rate
* generator_json_parse_rate
* generator_schema_fail_rate
* entity_count_stability
* opinion_spreader_count_stability
* estimated_percentage_sum_validity

---

## Layer C：链路通过层（Validator + Retry）

目标：测模型在真实链路下的通过率与收敛能力。

本层直接使用：

* `VALIDATOR_SYSTEM_PROMPT`
* `VALIDATOR_USER_PROMPT`

执行逻辑：

```text
Generator 生成
→ MiniMax Validator 审查
→ 若 fail，则将 errors 作为 error_feedback 回注给 Generator
→ 最多重试 2 次
→ 统计 first_pass_rate / final_pass_rate / avg_retry_count
```

### 记录指标

* review_latency
* first_pass_rate
* final_pass_rate
* avg_retry_count
* end_to_end_latency

## 首轮测试案例

为保证横向可比性，首轮 profiling 固定 2-3 条 `seed_text`，不允许随机换料。

建议按三档设计：

### Case 1：中规模 / 中争议

* event_scale = 0.5
* event_controversy = 0.5

### Case 2：中高规模 / 高争议

* event_scale = 0.7
* event_controversy = 0.8

### Case 3：高规模 / 高争议

* event_scale = 0.9
* event_controversy = 0.9

目的：

* 观察 event_scale 对人数与 I 分布的影响是否稳定
* 观察 event_controversy 对 P 分布约束是否稳定
* 观察高负载 schema 下 persona 字段是否更容易崩坏

# 🧮 首轮判定规则

## 1. 并发上限判定

稳定并发上限定义沿用任务书：

满足以下条件的最大并发值：

1. timeout_rate < 5%
2. latency 没有明显指数级上升
3. 输出质量稳定

在本项目中，“输出质量稳定”具体落到：

* JSON 可解析
* Validator pass 稳定
* final_pass_rate 不显著崩塌

---

## 2. Stability 分级

### high

* timeout_rate < 5%
* final_pass_rate 高
* avg_retry_count 低
* schema 崩坏少

### medium

* timeout_rate 在 5%~15%
* 存在一定 Validator fail
* 通过重试后可恢复

### low

* timeout_rate > 15%
* first_pass_rate / final_pass_rate 明显偏低
* schema 错误频繁
* 重试仍不稳定

---

## 3. Pool 分类

### fast

* simple_latency 低
* end_to_end_latency 可控
* concurrency_limit ≥ 3
* stability = high

适用：

* 高频任务
* 非重型 schema 任务
* 并行执行

### heavy

* generator_latency 或 end_to_end_latency 偏高
* 但 final_pass_rate 高
* 复杂任务承载能力强
* 稳定性中等以上

适用：

* 复杂结构化任务
* 关键路径任务
* fallback 主承接模型

### fragile

* 裸速度不一定慢
* 但 timeout / schema fail / retry_count 明显偏高
* 并发下链路容易崩

适用：

* 仅限轻任务
* 不进入关键路径

# 🔧 角色分工

## Codex：执行层

**目标**：执行 profiling 全链路并输出统计结果。

**输入**：

* 模型列表
* simple prompt
* generator prompt
* validator prompt
* 固定 seed cases

**输出**：

* raw logs
* model_profiles.json
* profile_summary.md

**职责**：

1. 发起 simple prompt 测试
2. 发起 generator 测试
3. 调用 MiniMax 执行 validator 审查
4. 若 validator fail，则将 errors 拼回 error_feedback 并重试
5. 最多重试 2 次
6. 记录 generator / validator / end-to-end latency
7. 汇总 profile

**约束**：

* 不主观判断模型好坏
* 不重写 prompt 逻辑
* 不扩展测试范围
* 只做执行与统计

---

## MiniMax：审查层

**目标**：负责 Validator 审查与结构化反馈。

**输入**：

* seed_text
* generator 输出 JSON

**输出**：

* pass / fail
* errors[]
* 可选审查备注

**职责**：

1. 使用 validator prompt 审查 generator 输出
2. 输出结构化 pass / fail
3. 若 fail，返回 errors
4. 可选进行抽样质量审查，重点检查：

   * persona 差异是否明显
   * occupation / personality / phrases 是否真实区分
   * P / I 分布是否基本合理

**约束**：

* 不替 generator 重写内容
* 不参与调度决策
* 以格式与结构校验为主

# 🔒 实现约束

* 不允许跳过 raw logs
* 不允许只给主观结论不给数据
* 不允许把 profiling 和 scheduler 开发混在同一轮
* 不允许第一轮就追求精确建模，优先拿到趋势
* profiling 的判断口径必须尽量统一
* 原则仍为：

```text
趋势 > 精度
可决策 > 漂亮报表
先测量，再调度
```

这与任务书中“不追求精确值、趋势大于精确、不要过度测试”的原则一致。
