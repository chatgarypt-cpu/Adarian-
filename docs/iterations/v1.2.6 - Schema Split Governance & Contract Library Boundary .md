## 4. Design Intent

### 4.1 为什么要做 Schema Split

当前系统已经不再只是“跑通一个多智能体流程”，而是在进入 Generation Governance 阶段。

后续链路会逐步形成：

```text
LLM raw output
  ↓
Parser
  ↓
Compiler / Canonicalizer
  ↓
Validator
  ↓
ValidationReport
  ↓
Targeted Repair Loop
  ↓
Diff Guard
  ↓
Accepted EntityExtractionOutput
```

这条链路必须依赖稳定的 contract library。

因此 v1.2.6 的设计意图是：

```text
先治理契约资产，再治理生成过程。
```

schema 在本系统中的角色不是普通类型定义，而是：

```text
1. 智能体输出契约
2. Phase 间接口契约
3. Validator 判断依据
4. Repair Loop 边界
5. Diff Guard 风控基线
6. 未来产品侧报告标准的承载层
```

---

### 4.2 为什么不等待产品侧

产品侧当前仍在讨论：

```text
1. 拐点标准
2. 代表性发言标准
3. 报告骨架
4. 指标科学性
```

这些属于 Phase 4 / product report governance 的 future track。

v1.2.6 处理的是底层契约资产：

```text
1. schema 边界
2. type ownership
3. import compatibility
4. common type placement
5. contract library structure
```

二者不存在强依赖。

结论：

```text
产品侧没定标准，工程侧不硬编码标准；
但工程侧可以先把 contract library 货架搭好。
```

### 5.5 Legacy Compatibility Boundary

新增原则：

```text
兼容是迁移工具，不是永久架构资产。
```

本版本允许短期保留 legacy shim，但必须满足：

```text
1. shim 不得包含业务逻辑。
2. shim 只允许 re-export / compatibility import。
3. shim 文件头必须写明 deprecated note。
4. shim 必须标明 replacement path。
5. shim 必须标明 retirement condition。
6. shim 必须集中登记，便于后续删除。
```

建议 deprecated note 模板：

```python
"""
Deprecated compatibility shim.

Do not add new business logic here.
Replacement path: src.schemas.phase1 / src.schemas.phase2 / ...
Target removal: after v1.2.7 P/C/V skeleton passes smoke and contract tests.
"""
```
