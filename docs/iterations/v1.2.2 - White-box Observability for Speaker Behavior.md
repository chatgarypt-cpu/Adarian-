## 🎯 本次迭代目标

### 问题描述

- 当前存在的问题：
  - v1.2.1 已经初步建立 `run_dir / run.log / timing_summary.json / run_meta.json`，一次 E2E 运行已经可以归档与复盘。
  - 但当前 `tick_logs.json` 仍然只能说明“谁发言 / 谁未发言 / 谁不可发言”，无法解释：
    - 为什么某个 agent 发言；
    - 为什么某个 agent 沉默；
    - 为什么某个 event entity 被阻断；
    - 为什么某个可发言群体没有进入发言队列；
    - speaker selector 的候选数、选中数、预算、分数、排名是什么。
  - 当前 `comment = （未发言）` 与 `reasoning = 本轮未进入发言队列` 只能描述结果，不能解释决策过程。
  - Tick 0 中 `劝阻吸烟女子 / 吸烟男子 / 涉事民警` 等实体被标记为不可发言，但缺少结构化解释：
    - 是否因为 `can_speak=false`；
    - 是否因为无直接原话；
    - 是否只有转述材料；
    - 是否因为隐私 / 身份 / 政策风险；
    - 该判断来自 Phase 1 LLM 输出、后处理规则，还是默认 fallback。
  - 当前系统无法支持后续白盒测试中对 speaker behavior 的解释型审计。
  - 当前 Phase 4 即使返回成功，也可能出现 `final_report.md` 局部截断；典型表现是生成到“综合建议 / 应对建议”等末尾章节标题后正文为空或明显不足。

- 影响范围：
  - 影响 Tick 级白盒解释能力。
  - 影响 speaker selector 行为审计。
  - 影响 silent / blocked agent 的原因追踪。
  - 影响后续 influence trace / stance_delta explainability 的基础字段建设。
  - 影响 Phase 4 报告是否可作为政府决策部门交付件。
  - 不影响当前 Phase 1-4 主链是否能跑通。

  - 但这是**观测结构缺口**，不是模拟策略错误。
  - 本轮只增强观测，不改变模拟行为。

目标：


```text

```

2. `report_completeness.py` 至少提供一个函数：

```python
check_report_completeness(markdown_text: str) -> dict
```

返回字段至少包含：

```text
report_truncated
truncation_reason
report_completeness_score
missing_required_sections
report_char_count
report_ends_cleanly
```

3. 最小检测规则：

必需章节检查：

```text
事件概述 / 事件概要
舆情态势
风险评估
关键风险点
应对建议 / 综合建议
```

尾部完整性检查：

如果最后一个非空标题是：

```text
## 综合建议
## 应对建议
### 综合建议
### 应对建议
```

且标题后正文少于 80 个中文字符，则：

```text
report_truncated = true
truncation_reason = "final section has heading but insufficient body"
```

结尾清洁检查：

如果 `final_report.md` 以以下模式结束，判定疑似截断：

```text
未闭合代码块
Markdown 表格半行
列表符号结尾：- / 1. / •
冒号结尾：建议：
最后一行是标题
```

字数下限检查：

```text
report_char_count < 800
```

则判定疑似截断。

完整性评分：

```text
初始 report_completeness_score = 1.0
每缺一个必需章节：-0.15
report_truncated = true：-0.35
report_ends_cleanly = false：-0.20
最低为 0.0
```

4. `main.py` 在 Phase 4 生成 `final_report.md` 后调用该检查。

5. 检查结果必须写入 run_dir：

```text
outputs/runs/<run_id>/whitebox_summary.json
```

最小结构：

```json
{
  "report_completeness": {
    "report_char_count": 0,
    "report_truncated": false,
    "truncation_reason": "",
    "report_ends_cleanly": true,
    "missing_required_sections": [],
    "report_completeness_score": 1.0
  }
}
```

6. 如有必要，也可以在 `run.log` 中记录一行 summary：

```text
REPORT COMPLETENESS report_truncated=false score=1.0 char_count=...
```

## 新增白盒观测指标：Phase 4 报告截断检测

### 问题背景

- 当前 Phase 4 即使返回成功，也可能出现 `final_report.md` 局部截断。
- 典型表现：报告生成到“综合建议 / 应对建议”等末尾章节标题后，正文为空或明显不足。
- 对政府决策部门场景而言，报告截断等同于不可交付，因此必须纳入白盒验收。

### 新增指标字段

- `report_truncated`: true / false
- `truncation_reason`: string
- `report_completeness_score`: 0.0 - 1.0
- `missing_required_sections`: list[str]
- `report_char_count`: int
- `report_ends_cleanly`: true / false

### 最小检测规则

1. 必需章节检查：

   `final_report.md` 至少应包含：
   - 事件概述
   - 舆情态势
   - 风险评估
   - 关键风险点
   - 应对建议 或 综合建议

2. 尾部完整性检查：

   如果报告最后一个非空标题是：
   - `## 综合建议`
   - `## 应对建议`
   - `### 综合建议`
   - `### 应对建议`

   且标题后正文少于 80 个中文字符，则判定：
   - `report_truncated = true`
   - `truncation_reason = "final section has heading but insufficient body"`

3. 结尾清洁检查：

   如果 `final_report.md` 以以下不完整模式结束，判定为疑似截断：
   - 未闭合代码块
   - Markdown 表格半行
   - 列表符号结尾，如 `-`、`1.`、`•`
   - 冒号结尾，如 `建议：`
   - 最后一行是标题

4. 字数下限检查：

   如果 `report_char_count < 800`，判定疑似截断：
   - `truncation_reason = "report too short"`

5. 完整性评分：

   初始 `report_completeness_score = 1.0`
   - 每缺一个必需章节：-0.15
   - `report_truncated = true`：-0.35
   - `report_ends_cleanly = false`：-0.20
   - 最低为 0.0

### 白盒报告新增输出段落

请在白盒测试报告模板中新增：
