## 第一章：背景材料

### 1.1 历史回顾：我们是怎么走到这里的

**v1.3.0（Phase3 Parser Aggregation Layer）：**
一次性将原本散落在 Phase4 报告层的确定性分析能力（风险判定、拐点检测、立场分析）抽离为 Phase3 独立模块：
- `src/phase3/risk_analyzer.py` — RiskAnalyzer（受众模式、风险判定、信号、风险类型）
- `src/phase3/inflection_detector.py` — InflectionDetector（拐点检测）
- `src/phase3/stance_analyzer.py` — StanceAnalyzer（立场矩阵）
- `src/phase3/parser.py` — SimulationDatasetParser（聚合消费三个模块输出）

同时创建 `main_new.py` 作为新路径入口，通过 bypass 对比（新旧 Phase4 输出逐维度对比）验证抽离成功。

**v1.3.0.1（Phase4 New Consumer Wiring Repair）：**
修复了新路径 Phase4 的三个 wiring blocker（B1: LLM markdown 被丢弃、B2: parse 重算 dataset 字段、B3: contract block 注入旧信号），使新路径 Phase4 真正消费 simulation_dataset 而非在内部重算。

**现状：两个入口、一个混合体。** 新旧两条路径共享同一个 `report_agent.py` 文件，该文件既有旧的计算函数又有新的消费函数。

### 1.2 当前架构问题

#### 问题一：双入口并存，无默认路径

| 入口 | 流程 | 状态 |
|------|------|------|
| `main.py` | Phase1→2→3→old Phase4（内联计算） | 旧路径 |
| `main_new.py` | Phase1→2→3→Phase3 Parser→new Phase4（纯消费） | 新路径（已验证通过） |

两个文件 85%+ 代码相同（run_phase1/2/3、build_run_paths、write_run_meta、write_whitebox_artifacts 等）。维护两份就是双倍的摩擦。

### 1.3 目标架构：Phase4 作为纯消费端

```
┌──────────────────────────────────────────────────────────────┐
│  Phase1 (实体提取)                                           │
│  Phase2 (社交拓扑)                                           │
│  Phase3 (tick simulation)                                    │
│  Phase3 Parser (RiskAnalyzer + InflectionDetector            │
│                  + StanceAnalyzer → simulation_dataset)      │
│                             │                                │
│                             ▼                                │
│  Phase4 (纯消费端)           ← simulation_dataset 作为唯一输入 │
│  ┌─────────────────────┐                                     │
│  │ • 接收上游结构化数据   │  ← 不做任何分析计算                 │
│  │ • 加载 prompt 模板    │  ← report_prompts.py              │
│  │ • 调用 LLM 生成报告   │  ← 所有字段校验、分析判定已在上游完成 │
│  │ • 保存产物            │  ← save_report + save_markdown    │
│  └─────────────────────┘                                     │
└──────────────────────────────────────────────────────────────┘
```

**Phase4 的职责被严格限定为：**
1. **接收**上游的 `simulation_dataset`（包含 run_info、risk_verdict、risk_type_classification、inflection_points、agent_stance_matrix、emotion_trajectory 等全部已经计算好的结构化数据）
2. **加载**自身的 prompt 模板（`report_prompts.py` 中的 `REPORT_SYSTEM_PROMPT` 和 `REPORT_USER_PROMPT_SUFFIX`）
3. **调用** LLM，将上游数据注入到 prompt 中，让 LLM 生成报告叙事
4. **保存**产物（final_report.json + final_report.md）

**Phase4 不做的：**
- 不调用 `assess_risk()` — 这是 Phase3 RiskAnalyzer 的事
- 不调用 `identify_inflection_points()` — 这是 Phase3 InflectionDetector 的事
- 不调用 `_build_code_owned_agent_stance_matrix()` — 这是 Phase3 StanceAnalyzer 的事
- 不调用任何信号计算函数
- 不执行任何"如果...那么..."的风险研判逻辑
- 不调用旧 `generate_report_with_llm()` 全路径

**注意：** Phase4 可以（且需要）将 `simulation_dataset` 字段映射为 `Phase4Output` Pydantic model（通过 `_build_phase4_output_from_simulation_dataset()`），这种映射不是"生成新字段"——它只是将上游结构化的数据转换为下游消费端需要的 schema 格式。真正的判定值（risk_level、inflection_points 等）在 dataset 中已经确定。

### 1.4 遗留代码的处理哲学

旧计算函数不应被删除——它们仍有历史价值（bypass 对比需要引用、作为 Phase3 模块实现的参考实现、回归测试）。

### 1.5 Bypass 对比的退出：从产品流程到 dev 诊断工具

bypass 对比是 v1.3.0 迁移期的验证工具，回答的问题是："Phase3 模块抽离后，计算结果和旧内联函数是否一致。"

**作为产品，bypass 没有意义。** 产品运行时只有一条流程：

```
Phase1 → Phase2 → Phase3 → Phase3 Parser → Phase4（消费 dataset → 生成报告）
```

在 `main.py` 运行时插入 bypass 对比等于：
- 每次运行都调一遍已被替代的旧计算函数（浪费 CPU + LLM tokens）
- 产出一个用户不需要的 `bypass_comparison.json`
- 增加运行时出错的可能性（旧 import 链挂在已归档的代码上）

**新架构下 bypass 的定位：** 保留在 `tools/bypass_compare_phase3.py` 作为 dev 诊断工具，仅当验证 Phase3 模块回归时手动运行。从 `main.py` 的产品流程中移除。

### 1.6 遗留代码：Archive 而非 Delete

处理方式：**归档（Archive）而非删除。** 旧函数移入 `legacy/` 目录，保持可导入但不再参与主流程。

```text
legacy/
  main_legacy.py               — 旧 main.py（含旧 Phase4 调用链）
  phase4/
    legacy_analytics.py        — 旧计算函数（assess_risk, identify_inflection 等）
    legacy_generation.py       — 旧生成全路径（generate_report_with_llm 等）
    legacy_markdown.py         — 旧 code-owned markdown（generate_markdown_report）
```

bypass 对比脚本将 import `legacy.phase4.legacy_analytics` 而非 `src.phase4.report_agent`，实现新旧路径的职责分离。

### 2.3 核心原则

1. **Phase4 不允许计算任何风险字段** — 所有 risk_level、inflection_points、agent_stance_matrix 等必须从 `simulation_dataset` 读取

3. **Phase4 可以映射字段格式** — 如 `simulation_dataset` 的 dict 数据 → `Phase4Output` Pydantic 模型（格式转换 ≠ 字段生成）
4. **旧主路径归档，不删除** — legacy 目录保留全部旧代码，bypass 对比可引用
5. **执行层（Hermes/Codex/Claude Code）不做设计判断** — 所有设计决策在这份文档中已确定，执行只做代码搬运和清理

### 2.4 禁止变化

1. 不改 Phase4Output schema 字段语义
2. 不改 Phase3 模块接口
3. 不改 prompt 文本语义（`REPORT_SYSTEM_PROMPT`、`REPORT_USER_PROMPT_SUFFIX`）
4. 不改 Phase 1/2/3 tick simulation
5. 不改 config.py
6. 不改 src/schemas/
7. 不新增外部检索/RAG/MCP
