## 第 1 层：Owner Brief

**1. 这轮干嘛？**

实现全部后端业务 API，对接 v1.5.0a 的前端 8 个页面。替换 mock 数据为真实数据。打通完整链路：贴 seed → 选模型 → 启动推演 → 实时监控 → 审查结果 → 生成报告。

**现实边界补充（2026-06-26 Codex 调查后修正）：**

v1.5.0a 的前端是 mock-first 原型，v1.5.0b 调查发现以下关键差距必须在开工前处理：

- **进程管理无法在白名单约束下实现**：cancel 需要改 `_run_world` 函数体（`subprocess.run` → `Popen`），当前白名单只允许新增 `rerun_world()`。必须**先扩展白名单**再开工。
- **状态值不统一**：后端 `WorldState.status` 用 `success`，前端 `types.ts` 用 `completed`。接真实数据后前端会显示"排队中"。需新增映射表。
- **`saveSettings()` 真实 bug**：前端调了 `getSettings()` 而非 `PUT`，不是 mock 问题，是写错了。需独立修复。
- **ticks 默认 40 vs MAX_TICKS=5**：前后端默认值冲突。
- **API key 存储方案空白**：计划说"不回显明文"但未定义加密方式。
- **Phase 4 输入路径未映射**：report API 不知道 simulation_dataset.json 在哪。
- **`smoke_api.sh` 实际不存在**：smoke 应写内联 Python 而非 shell 脚本。**

**2. 为什么现在做？**

v1.5.0a 造好了前端，但点"开始推演"还是 mock 数据。这轮让它真跑。

### 2. Goal & Boundary

**做什么：**

1. **`serve.py` 冲突修复** — `git mv src/adarian/serve.py src/adarian/_legacy_serve.py`；新建 `serve/__init__.py` 暴露 `run()` 和 `create_app()`；更新 `__main__.py` 导入
2. **Mock-to-real 能力盘点（已完成）** — v1.5.0a Codex 产出了 `docs/iterations/active/v1.5.0b_mock_to_real_inventory.md`；Claude Code agent team 已完成交叉验证，发现 7 项严重漏洞、6 项中等漏洞、3 项轻微漏洞。详见 `tasks/active/v1.5.0b-inventory-investigation/outputs/findings_05_inventory_accuracy_report.md`。盘点结论已内化到此迭代计划。
3. **P0 开工前必修清单**（基于调查发现）：
   - **batch.py 白名单扩展**：明确允许 `start_batch()` 新增 `ticks`/`parallelWorlds`/`focuses` 参数；允许 `_run_world` 改 `subprocess.run` → `Popen`；允许 `WorldState` 新增 `cancelled` 状态值。这些必须**先于**任何代码修改写入白名单。
   - **状态值映射表**：`serve/schemas.py` 定义 `WORLD_STATUS_MAP = {"success": "completed", "failed": "failed", "running": "running"}`，后端统一用 `success`/`failed`/`running`，前端展示时映射。
   - **API key 加密方案**：`model_gateways` 表的 `api_key` 字段用 Fernet 对称加密（`cryptography.fernet`），master key 从环境变量 `ADARIAN_ENCRYPTION_KEY` 读取，不存在则自动生成存 SQLite。
   - **`saveSettings()` bug 修复**：`frontend/src/stores/settings.ts` L23-26 调用 `getSettings()` → 改为调用 `putSettings()`。
   - **ticks 默认值对齐**：前端默认 ticks 从 40 改为 5（与 `MAX_TICKS` 一致）。
4. **SQLite 数据库** — `serve/db.py` 实现四表：

   ```python
   # batches: id(PK), task_name, seed_text, seed_path, models(JSON array),
   #           tag, created_at, completed_at, status(varchar 20),
   #           idempotency_key(UNIQUE)
   # worlds: id(PK), batch_id(FK→batches), world_index, model_name,
   #         status(varchar 20, default 'running'),
   #         run_dir(varchar 500), error_message(text nullable),
   #         started_at, completed_at
   # model_gateways: id(PK), name, base_url, provider, api_key_encrypted,
   #                 enabled(bool), source('env'|'user'),
   #                 created_at, updated_at
   # settings: key(PK varchar 100), value(text)
   ```

   提供 `init_db()` + CRUD 接口。API key 加密存储（见 P0）。
5. **Flask 应用骨架** — app factory + ThreadPoolExecutor(3) + `_SESSIONS` + `_ACTIVE_BATCHES` + `app.run(threaded=True)`
6. **全部业务 API（执行顺序从简到繁）：**
   - 第一阶段（seed → config → models → model_gateways）：
     - `POST /api/seed` — 保存事件材料，返回录入检查结果
     - `GET /api/config` / `POST /api/config` — 读写推演配置（JSON 持久化到 SQLite settings）
     - `GET /api/models` — 模型列表（从 `batch.available_models()` 读取，过滤掉 bge/❌ 等）
     - `POST /api/models/health` — 批量健康检测（调用 `_hello_one` 逻辑）
     - `GET /api/model-gateways` — 返回 `.env` 默认网关 + 用户新增网关；API key 不回显明文
     - `POST /api/model-gateways` — 新增网关；API key 加密存储
     - `PUT /api/model-gateways/<id>` — 更新/禁用网关
     - `POST /api/model-gateways/<id>/discover-models` — 访问 `base_url/models` 发现模型
     - `POST /api/model-gateways/<id>/health` — hello/latency 检测
   - 第二阶段（run → status → history）：
     - `POST /api/run` — 启动真推演（调 `batch.start_batch`），写入 SQLite，idempotency_key 查重，并发上限 3
     - `GET /api/run/<id>/status` — 从 SQLite worlds 表返回状态（通过 `WORLD_STATUS_MAP` 映射后返回）
   - 第三阶段（review → report → cancel/retry — 最后做）：
     - `GET /api/review/<batch_id>` — 聚合跨 world 风险结论（复用 `inspect.py` 的 `inspect_batch()`）
     - `POST /api/report` — 调 Phase 4 报告管线。输入路径：`run_dir/simulation_dataset.json`，run_dir 从 worlds 表读取
     - `POST /api/cancel/<batch_id>` — 遍历 worlds 子进程，SIGTERM → 3s → SIGKILL。**依赖** `WorldState.proc_handle` 和 `_run_world` Popen 改造
     - `POST /api/cancel/<batch_id>/<world_id>` — 单个 world 取消
     - `POST /api/run/<batch_id>/worlds/<world_id>/retry` — 调 `batch.rerun_world()`，可换模型
   - 第四阶段（settings + history + static）：
     - `GET /api/history` — 查 SQLite batches 表，按日期倒序
     - `GET /PUT /api/settings` — 读写 SQLite settings 表
     - SPA catch-all — `static.py` 注册非 `/api/*` GET → `frontend/dist/index.html`
7. **幂等性** — `SELECT batch_id FROM batches WHERE idempotency_key = ?`。idempotency_key 由 `(seed_text, models, tag, base_url)` 的 SHA256 组成。
8. **并发上限** — `_ACTIVE_BATCHES` 计数 ≥ max_concurrent(3) → 429 + active_batches 列表
9. **进程管理** — `process.py` 封装 subprocess 启动（`popen` + `preexec_fn=os.setsid`），Popen handle 存到 WorldState。**不再依赖 batch.py 原有 `_run_world` 函数体。**
10. **白名单修改 batch.py** — 扩展白名单，新增允许：
    - `start_batch()` 新增参数：`ticks: int = 5`、`parallel_worlds: int = 1`、`focuses: list[str] = []`
    - `WorldState` 新增字段：`proc_handle: subprocess.Popen | None`
    - `_run_world` 改造：内部 `subprocess.run` → `Popen`（用以支持 cancel 信号）
    - 已有函数体 `start_batch()`/`run_batch()` 参数签名修改（不删旧参数）
11. **前端接入** — 替换有真实能力支撑的 mock 为真实 API 调用；无真实能力支撑的前端模块必须降级为 disabled / pending / mock-only，并在 UI 或 contract 中明确标注
12. **测试** — pytest 全套 API 测试（每个端点至少 3 断言：状态码、结构、错误路径）
13. **Vite proxy** — `vite.config.ts` 代理 `/api/*` → `http://localhost:9788`

**模型 API 服务管理规则：**

- `.env` 只作为系统启动默认配置来源，不允许前端直接写回 `.env`
- 用户在前端新增的 API 服务地址保存到后端 SQLite/settings 表
- API key 前端可录入，但后端查询时不得回显明文；只返回 `has_api_key: true/false`
- `.env` 默认网关和用户新增网关在 `GET /api/model-gateways` 中合并展示，并标注来源
- 模型列表必须由后端 discover/health 得出，前端不得把 v1.5.0a 的 mock 模型当作真实可用模型

**不做什么：**
- 不改 `phase*/`、`analysis/`、`parser.py`、`llm_client.py`、`schemas/`
- 不改前端 8 页的组件结构（只替换 store 的数据源）
- 不把 v1.5.0a mock-only 的产品设想包装成真实能力；没有后端证据的功能只能保留为 pending/mock-only
- 不做 E2E 测试（v1.5.0c）
