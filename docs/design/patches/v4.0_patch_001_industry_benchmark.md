## 3. 业界方案对比

### 3.1 Microsoft Conductor（2026 年 5 月，MIT 开源）

> https://github.com/microsoft/conductor | https://opensource.microsoft.com/blog/2026/05/14/conductor-deterministic-orchestration-for-multi-agent-ai-workflows/

YAML 定义工作流，路由层零 token 消耗，Jinja2 模板做条件分支。编排层 = 确定性代码（不是 LLM 决策）。

| 维度 | Conductor | Adarian / Hermes PM Runtime |
|------|-----------|-----------------------------|
| 工作流定义 | YAML + Jinja2 模板 | relay dispatch + task_config.yaml + prompt.md |
| 路由 | 确定性（首个匹配条件走） | executor_registry 确定性路由 |
| 并行 | static parallel + dynamic for each | DAG 节点级并行（fan-in） |
| Human Gate | 内置 workflow step | dispatch-approval-gate + observer |
| Agent 隔离 | 独立 session，无对话泄漏 | 独立 tmux session |
| Dashboard | Web DAG 可视化（动画） | Terminal observer + tmux pane |
| 多 Provider | Claude + GitHub Copilot | CC Switch 路由多 provider |
| 恢复 | 无内置 | heartbeat_monitor + Repair Agent（设计） |

**可吸收的方向：**
- prompt.md 引入模板变量（`{{ task_config.expected_outputs }}`）
- Web DAG 状态仪表盘
- Script Step（非 LLM 步骤直接走 shell/subprocess）

### 3.2 Augment Code / Intent（商业产品，2026）

> https://www.augmentcode.com/guides/multi-agent-orchestration-architecture-guide

Coordinator → Implementor → Verifier 三角色模型，"Living Spec" 作为协调机制。BYOA（Bring Your Own Agent）。

| 维度 | Intent | Adarian / Hermes |
|------|--------|------------------|
| 协调机制 | Living Spec（演化文档） | relay dispatch prompt + receipt |
| 角色模型 | Coordinator + Implementor + Verifier | DAG 节点 + Agent Team |
| Context 模式 | accumulate / last_only / explicit | 全上下文注入 prompt.md |
| 并行宽度 | 自适应（AdaptOrch: 3.4） | 可控（DAG parallel fan-in） |
| 框架兼容 | BYOA（Claude/Codex/OpenCode） | CC Switch 支持 Claude/Codex |
| 失败诊断 | 14 种 failure taxonomy | heartbeat + pane capture + receipt |

**可吸收的方向：**
- Context 显式控制（explicit 模式大幅省 token）
- Coordinator-Specialist 子模式（节点内部的任务分解）

### 3.3 Agent Registry 体系（AWS / Microsoft / Google — 2026 年集体发布）

三家云厂商在 2026 年同时推出 Agent Registry：

| 厂商 | 注册内容 | 核心架构 |
|------|---------|---------|
| **Microsoft** (Multi-Agent Ref Arch) | agent 元数据、能力描述、通信端点 | Orchestrator + Classifier + Registry 三层 |
| **AWS** (AgentCore / Agent Registry) | agent/tool/MCP server/skill | AgentCard v0.3.0 标准，IAM 权限控制 |
| **Google Cloud** | MCP server/agent/endpoint | MCP-first，API 查询 |

**我们的 4 张注册表（skill / mcp / hook / executor）** 是同类设计，但多了：
- self-maint drift_check 漂移检测（业界没有）
- executor_registry 执行器多态注册（业界 agent registry 只管"谁是 agent"，不管"怎么执行"）
- gate 模式的权限体系（不是 API 式）
- skill_registry 中的 owner_approval_required / allowed_paths / risk_level 多维属性

### 3.4 GraSP — 图修复原语（学术）

> arXiv:2604.17870v1

5 条图修复原语：
| 原语 | 含义 | 对应我们的 |
|------|------|-----------|
| Rebind | 更新失败节点的参数 | Repair Agent 重调参数 |
| InsertPrereq | 添加缺失前置 | Repair Agent 增补节点 |
| Substitute | 替换 skill 保留接口 | 执行器切换（codex↔claude） |
| Rewire | 局部重连边 | DAG 拓扑修复 |
| Bypass | 跳过已满足条件的节点 | 条件跳过（类似 closeout gate） |

## 4. 独家突破（业界没做的）

1. **Self-maint 漂移检测** — 业界有 Registry 但没有自动化一致性检查
2. **Gate 模式**（skill 写规则 → script 做门 → 人确认）— 业界全是 API 式自动权限
3. **Executor Registry + 多态执行器** — agent registry 业界只管"谁是 agent"，不管"用什么方式执行"
4. **两层 DAG（Goal + Subtask）** — Conductor 一层 DAG；Hermes DAG 管 goal 编排，Claude Code workflow 管内部分解
5. **observer attach（tmux 窗口可见可接管）** — 业界没有人做这个

## 5. 业界可吸收方向（按优先级）

| 优先级 | 方向 | 参考来源 | 预计成本 |
|--------|------|---------|---------|
| P1 | Context 显式控制模式 | Intent / Conductor | 低（改 prompt 模板 + relay runner context 参数） |
| P2 | GraSP 修复原语 | 学术论文 | 中（重构 Repair Agent 逻辑） |
| P3 | Web DAG Dashboard | Conductor | 高（前端项目） |
| P4 | Jinja2 模板变量 | Conductor | 低（加模板引擎） |
| P5 | 拓扑自适应路由 | AdaptOrch | 高（需要 benchmark 数据） |
