## 4. Prompt Weight Assessment

### 4.1 Is REPORT_SYSTEM_PROMPT Too Heavy?

**Verdict: YES (partial)** — ~550-600 tokens packing 10 distinct rule categories:

1. Role assignment (line 60: `你是一位资深的社会舆情分析师`)
2. Simulation disclaimer (line 62)
3. Report structure mandate (lines 64-70: five chapters, no 核心结论, no dual-output)
4. Risk section structure (lines 73-75: 风险等级+风险类型+风险解释)
5. Code-owned data sourcing rules (lines 74-79: risk_level, risk_types, inflection points, stance matrix)
6. Metric grounding rules (line 80)
7. Forbidden phrases — hard ban (lines 82-83)
8. Forbidden phrases — soft avoid (line 83-84)
9. Simulation-vs-reality boundary (line 85)
10. Capability pretense prohibition (line 86)
11. Policy boundary rules (lines 88-90)
12. Output format instruction (line 91)

**Risk**: The prompt loads schema constraints, business rules, writing style, forbidden items, and report template into a single monolithic block. This is a known anti-pattern that can cause:
- Constraint dilution: later rules weaken earlier ones in attention
- Generation conservatism: too many "don't" rules → bland output
- Debug difficulty: hard to isolate which constraint caused a failure

### 4.2 Duplicated Constraints

| Constraint | In REPORT_SYSTEM_PROMPT | In Separate Constant | In Markdown Output |
|---|---|---|---|
| Simulation disclaimer | Line 62 | `SIMULATION_DISCLAIMER` (P2) | `generate_markdown_report()` lines 793, 872 |
| Five-chapter template | Lines 66-70 | `FIVE_CHAPTER_HEADINGS` (P1) | `generate_markdown_report()` lines 790-900 |
| Forbidden phrases | Lines 82-83 | `FORBIDDEN_REALITY_PHRASES` (P3) | N/A (prompt-only) |

The duplication between Python constants and prompt string content is by design (constants serve as documentation and test anchors), but it creates a maintenance risk: updating a constant does not automatically update the prompt string.

### 4.3 Conflicting Rules

None found. The constraints are additive, not contradictory.

### Phase 4 (Report Generation)

**Issue 1: Monolithic system prompt**
The REPORT_SYSTEM_PROMPT packs role, structure, data sourcing, risk rules, forbidden phrases, policy boundaries, capability pretense, and output format into one block.

**Recommendation**: Split into:
- `REPORT_SYSTEM_PROMPT`: role + task description only (~80 tokens)
- `REPORT_STRUCTURE_RULES`: five-chapter template + section requirements (~120 tokens)
- `REPORT_MARKDOWN_GROUNDING_RULES`: data sourcing + metric translation (~100 tokens)
- `REPORT_RISK_EXPRESSION_RULES`: risk section structure + source constraints (~80 tokens)
- `REPORT_FORBIDDEN_PHRASE_RULES`: hard bans + soft avoids + policy boundaries (~100 tokens)
- `REPORT_OUTPUT_FORMAT`: final output instruction (~30 tokens)

This split enables: (a) independent testing of each rule block, (b) easier A/B testing, (c) cleaner version diffs, (d) potential future dynamic assembly based on audience_mode.

**Issue 2: Governance constants are dead weight**
`FIVE_CHAPTER_HEADINGS`, `FORBIDDEN_REALITY_PHRASES`, `FORBIDDEN_EQUIVALENT_PHRASES`, `POLICY_BOUNDARY_FORBIDDEN_PHRASES`, `MARKDOWN_GROUNDING_RULES`, `RISK_EXPRESSION_RULES` are Python constants that are:
- Imported by tests (good — used as test anchors)
- NOT imported by report_agent.py (semantic content duplicated in REPORT_SYSTEM_PROMPT string)
- If the prompt string changes but the constant doesn't, tests pass but prompt drifts

**Recommendation**: Either wire constants into runtime (import in report_agent.py, use in prompt assembly) or accept the duplication as intentional documentation and add a comment in report_prompts.py explaining the relationship.
