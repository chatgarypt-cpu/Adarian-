## 2. 任务背景

### 2.1 当前状态

报告写作助手（`report_writing_assistant` SKILL.md）在撰写"四、风险研判"和"五、对策建议"两个章节时，参照的是：

```
.claude/skills/report_writing_assistant/references/risk_and_countermeasure_angles.md
```

该参照文件是产品侧早期基于 23 份内参范例手工提炼的写作角度汇编，结构为：
- 第一部分：风险研判写作角度（6 大领域、16 个角度）
- 第二部分：对策建议写作角度（8 大类别、24 个角度）
- 第三部分：写作技法提示
- 第四部分：高频关键词

### 2.2 为什么要替换

产品侧已完成 v0.2 版风险分层与等级映射清单（`政府治理视角舆情风险分层与等级映射清单_v0.2.md`），将风险类型重新组织为 **5 个一级风险域、20 个二级风险类型**，每个类型带有 12 个字段（适用场景、触发线索、四档等级表现、不应触发情况、报告表达口径、正例/反例等）。

旧参照存在三个问题：

1. **分类体系不对齐**：旧参照按"政治安全与意识形态 / 社会稳定与公共安全 / 经济安全 / 网络与信息安全 / 制度与治理 / 文化安全"六大领域组织；v0.2 按"治理信任 / 公共安全与民生 / 传播演化 / 信息安全与意识形态 / 治理执行压力"五大领域组织。两套体系不完全对应，导致报告写作助手在参照时产生认知冲突。

2. **缺乏信号映射**：旧参照只有写作角度和关键词，没有说明"在什么系统信号下应触发哪个风险类型"。报告写作助手需要自行判断风险类型归属，容易兜底为"负向叙事风险"。

3. **对策建议不与风险类型挂钩**：旧参照的对策建议是按"舆情监测 / 舆论引导 / 法律完善 / 国际合作 / 教育提升 / 技术治理 / 人文关怀 / 分类施策"八大类别独立组织的，没有说明"哪类风险应对应哪类对策"，导致报告中的风险与建议容易出现错位。

### 2.3 本次要达成的目标

技术侧基于产品侧的 v0.2 风险分层清单或后续迭代清单，产出**两份映射规则**，作为产品侧（report_writing_assistant）后续更新写作参照和表达模板的基础。

技术侧交付物的核心价值是：让报告写作助手在拿到 `final_report.json` + `tick_logs.json` + `entities_and_relations.json` 后，能够：

1. 根据系统中的确定性信号判断应命中的风险类型及其等级
2. 根据命中的风险类型查找应匹配的对策方向

**版本说明**：本任务卡以 v0.2 风险分层清单为基准。若产品侧后续发布 v0.3 或更高版本的清单（如增删类型、调整分类、修改等级表现），技术侧应以**最新版清单**为准更新映射表。v0.2 与后续迭代之间的差异，由产品侧在发布新版时一并标注变更点，技术侧据此修订。

**写作层面的工作（风险研判写作参照、对策建议写作参照、报告表达口径模板）属于产品侧（report_writing_assistant）的待办事项，不纳入本次技术侧交付范围。** 这些事项已记录在 `.claude/skills/report_writing_assistant/references/pending_decisions.md` 第 3-5 条，待技术侧完成映射后由产品侧启动。

## 6. 交付物必须包含的内容

以下内容从产品侧视角定义"报告需要什么"。技术侧负责决定如何组织、如何计算、如何结构化。

### 6.1 风险类型信号映射表（核心交付）

**业务需求**：报告写作助手需要知道"给定这个事件和这批模拟数据，应该命中哪几个风险类型"。

请技术侧设计一张映射表，将 v0.2 中的 20 个二级风险类型，映射到系统中**可确定性获取的信号**。

信号可以来自（但不限）：
- `final_report.json` 中的风险等级、极化指数、立场均值、趋势方向等
- `entities_and_relations.json` 中的实体类型、角色、关系
- `tick_logs.json` 中的群体立场变化、关键发言
- `seed_input.txt` 中的事件原始信息
- 代码侧可直接获取的任何其他确定性信息

对每个风险类型，映射表应回答：
1. **触发条件**：系统检测到什么信号组合时，应判定该风险类型适用？（可以是必要条件、充分条件或加权条件）
2. **排除条件**：什么信号出现时应明确排除该风险类型？（对应 v0.2 中每类的"不应触发情况"）
3. **等级条件**：在什么信号条件下该风险类型为 LOW / MEDIUM / HIGH / CRITICAL？（对应 v0.2 中每类的四档等级表现）
4. **优先级/互斥规则**：当多个风险类型同时命中时，如何确定主风险类型（1 个）和副风险类型（最多 2 个）？

### 6.2 风险-对策映射表

**业务需求**：报告写作助手在确定风险类型后，需要知道"这条风险应对应什么对策方向"，形成"N 条风险 → N 条建议"的闭环。

旧参照中的 8 大对策类别（舆情监测与预警、舆论引导与叙事权争夺、法律与制度完善、国际合作与话语权建设、教育与素养提升、技术与平台治理、人文关怀与民生纾困、分类施策与精准治理）经过 23 份内参验证，仍然有效。

请技术侧设计**风险-对策映射表**：为 v0.2 的 20 个风险类型分别映射 1-3 个最相关的对策方向（从旧参照的 8 大类别及其 24 个子类中选取）。不是每个风险都需要对应所有 8 类对策，但每条风险必须有明确的对策方向。

**注意**：风险-对策映射表只定义"什么风险类型应对应什么对策方向"的对应关系。每条对策方向的写作要点、执行主体、执行机制和通用写作规范，属于产品侧（report_writing_assistant）待办事项（pending_decisions.md 第 4 条）。

## 9. 验收标准

本交付物通过的条件：

1. **覆盖完整**：对 v0.2 中全部 20 个二级风险类型均有信号映射（触发条件 + 排除条件 + 等级条件）和风险-对策映射
2. **信号可计算**：每个风险类型的触发/排除/等级条件均引用了系统中实际存在或可在本补丁中新增的信号（不接受仅依赖 LLM 自行判断的模糊条件）
3. **风险-对策闭环**：每个风险类型至少映射 1 个对策方向，每个对策方向能回指到具体的风险类型
4. **等级有区分度**：同一风险类型的 LOW / MEDIUM / HIGH / CRITICAL 判定条件有实际差异，不依赖模糊副词
5. **与 v0.2 对齐**：不新增或删除 v0.2 已定义的风险类型（如需调整类型定义，应回馈给产品侧更新 v0.2，而不是在技术侧直接修改）
6. **对策类别继承旧参照**：风险-对策映射中使用的对策方向来自旧参照 `risk_and_countermeasure_angles.md` 的 8 大类别及其 24 个子类，不凭空新增对策体系
7. **交付格式为 Markdown**：不是纯代码/Python 文件/JSON schema，而是报告写作助手可读的 Markdown 参照文件

---

## 10. 退回条件

出现以下情况应退回修改：

1. 风险类型信号映射全部依赖 LLM 自行判断，没有引用系统中的确定性信号
2. 等级判定条件没有区分度（如 LOW 和 MEDIUM 的触发条件实质相同）
3. 风险-对策映射缺失：存在风险类型没有对应任何对策方向，回到了旧参照"各自独立"的组织方式
4. 擅自新增、删除或重命名 v0.2 中已定义的风险类型
5. 交付物是纯代码/Python 文件/JSON schema，而不是报告写作助手可读的 Markdown 参照文件
6. 对策映射中的对策方向不是来自旧参照的 8 大类别体系，凭空新建了不相关的对策体系
7. 交付物混入了写作参照内容（写作要点、表达模板、写作规范）——这部分属于产品侧待办

## 11. 使用场景说明（供技术侧理解交付物的消费方式）

报告写作助手的工作流程大致如下：

```
1. 读取 final_report.json → 获取风险等级、极化趋势、立场变化方向
2. 读取 entities_and_relations.json → 获取实体类型、群体构成
3. 读取 tick_logs.json → 获取关键变化点、群体立场轨迹
4. 读取 seed_input.txt → 获取事件原始信息
5. 读取本映射文件 → 根据系统信号确定应命中的风险类型及等级（1 个主类型 + 0-2 个副类型）
6. 读取本映射文件 → 根据风险类型查找应匹配的对策方向
7. 读取 risk_type_writing_reference.md（产品侧待办）→ 按表达模板撰写"四、风险研判"
8. 读取 risk_type_writing_reference.md（产品侧待办）→ 按表达模板撰写"五、对策建议"
```

因此，本交付物最核心的价值是**第 5 步和第 6 步**：让报告写作助手从"自己判断该写什么风险、该匹配什么对策"变为"根据系统信号确认风险类型、根据映射表确认对策方向"。
