# 01 - 概述

## Planner 在整个流水线中的位置

Planner（规划器）位于 ElectionSim-Lab 三层流水线的第 1 层，承接第 0 层"规划代理与意图路由"解析出的用户意图，完成从自然语言需求到结构化 `WorkflowPlan` 的转换，然后将产物递交给下游的第 2 层"计划修复与验证循环"和第 3 层"Skill 自动绑定"继续加工。

在模块层面，Planner 的核心逻辑集中在 `orchestrator/dag/` 包内，入口类是 `engine.py` 中的 `OrchestrationEngine`。

```
用户消息
  |
  v
[第0层] 规划代理与意图路由 ---> ParsedIntent (action, targets, time_range, ...)
  |
  v
[第1层] Planner / OrchestrationEngine   <--- 本层
  |        |
  |        +--> generate_planner_sdk()   (Claude Agent SDK 通道)
  |        +--> generate_llm()           (直接 LLM API 通道)
  |
  v
  WorkflowPlan (nodes[], edges[], rationale)
  |
  v
[第2层] 计划修复与验证循环 ---> canonicalize + validate
  |
  v
[第3层] Skill 自动绑定 ---> DAGNode / DAGEdge (materialized)
```

## 两种生成通道

`OrchestrationEngine` 提供两个异步生成入口，都定义在 `engine_planning_mixin.py` 中：

### 1. SDK 通道 -- `generate_planner_sdk()`

- 入口：`engine_planning_mixin.py` 的 `_generate_dag_planner_sdk()`
- 使用 `WorkflowPlannerSDKStrategy`（定义在 `planning_strategies.py`）
- 底层调用 `plan_generator.py` 的 `generate_with_planner_sdk_request()`
- 实际传输层在 `plan_transport.py` 的 `query_planner_sdk()`：通过 Claude Agent SDK (`ClaudeSDKClient`) 在临时目录中启动一个**仅允许 Skill 工具**的沙箱，注入 `dag-planner` Skill 及其参考文件 `rules-and-examples.md`
- 特点：模型通过 Agent SDK 内部闭环，系统 prompt 为 `claude_code` preset，不使用 structured outputs beta

### 2. LLM 通道 -- `generate_llm()`

- 入口：`engine_planning_mixin.py` 的 `_generate_dag_llm()`
- 使用 `WorkflowLLMPlanningStrategy`（定义在 `planning_strategies.py`）
- 底层调用 `plan_generator.py` 的 `generate_with_llm_request()`
- 实际传输层在 `plan_transport.py` 的 `query_llm_transport()`：通过 `httpx.AsyncClient` 直接 POST 到 LLM Gateway 的 `/v1/messages`
- 特点：使用 OpenAI-compatible structured outputs（`json_schema`），需要 `anthropic-beta: <structured_outputs_beta>` 头；支持 thinking mode；支持 `request_with_retries` 重试策略

### 双通道选择逻辑

通道选择由 `workflow_planner_mode` 设置控制（`workflow_planner_mode` 为 planner 类值时走 SDK 通道，否则走 LLM 通道），调用方在 `OrchestrationEngine` 上层根据配置决定调用哪个方法。两通道共享相同的 prompt 构建、repair loop、compiler 和 validator，仅 transport 层不同。

## OrchestrationEngine 类的职责

`OrchestrationEngine`（定义在 `engine.py`）是整个编排入口，继承 `EnginePlanningMixin`（定义在 `engine_planning_mixin.py`）。其职责包括：

| 职责范围 | 关键方法/属性 | 所属文件 |
|---------|-------------|---------|
| 配置读取 | `_resolve_workflow_gen_model()`, `_workflow_gen_timeout_s()`, `_intent_parse_timeout_s()`, `_workflow_planner_mode()` | `engine.py` |
| Prompt 构建 | `_build_workflow_plan_prompt()`, `_build_workflow_planner_prompt()` | `engine_planning_mixin.py` -> `engine_prompts.py` |
| Repair prompt 构建 | `_build_workflow_plan_repair_prompt()`, `_build_workflow_planner_repair_prompt()` | `engine_planning_mixin.py` -> `engine_prompts.py` |
| Plan 正规化 | `_canonicalize_workflow_plan()` | `engine_planning_mixin.py` -> `plan_validator.py` |
| Plan 验证 | `_validate_generated_plan()` | `engine_planning_mixin.py` -> `plan_validator.py` |
| DAG 校验 | `_validate_plan_dag()` | `engine_planning_mixin.py` -> `workflow_materializer.py` |
| 分层排序 | `_assign_layers_orders()` | `engine_planning_mixin.py` -> `workflow_materializer.py` |
| 策略工厂 | `_planner_sdk_strategy()`, `_llm_planning_strategy()` | `engine_planning_mixin.py` |
| Skill 注册表 | `_skill_entries()` | `engine_planning_mixin.py` |
| JSON 提取 | `_extract_json_object()` | `engine.py` -> `plan_generator_support.py` |
| Planning richness | `_planning_richness()` | `engine_planning_mixin.py` -> `chat/config.py` |

## 输入

Planner 的输入是一组经过第 0 层意图解析后组装的结构化数据：

1. **用户意图** (`ParsedIntent`)：包含 `action`（动作类型，如 `analyze`）、`targets`（目标实体列表）、`time_range`（时间范围）、`output_format`（输出格式要求）、`raw_query`（用户原始自然语言输入）
2. **资源审计** (`resource_audit`)：可选的 `dict`，包含 `localDataStatus`（本地数据是否存在及覆盖度）、`externalData`（外部数据源开关状态）、`dataGap`（数据缺口描述）、`evidenceFrame`（证据框架）、`matchedPaths`（匹配到的数据文件路径）
3. **Skill 注册表** (`SkillRegistry`)：来自 `orchestrator/dag/types.py` 的 `SkillRegistry`，提供系统中所有可用 Skill 的元数据、blockProfile（stage/archetype/predecessor/successor）和 planning snapshot

## 输出

Planner 的输出是一个 `WorkflowPlan`（定义在 `workflow_models.py`），包含：

- `schema_version`: 固定 `"1"`
- `name`: 工作流名称（≤120 字符）
- `nodes`: `list[WorkflowPlanNode]` -- 最少 1 个，运行时上限 `RUNTIME_WORKFLOW_MAX_NODES`（200）
- `edges`: `list[WorkflowPlanEdge]` -- 可选，运行时上限 `RUNTIME_WORKFLOW_MAX_EDGES`（2000）
- `rationale`: 可选规划思路说明（≤800 字）

每个 `WorkflowPlanNode` 包含 `id`、`label`、`description`、`kind`（`AGENT`/`INTERNAL`）、`enabled`、`critical`、`skill_id`、`skills`、`external_search`、`requires_knowledge_search` 等字段。

## 关键设计原则

1. **通道隔离**：SDK 通道与 LLM 通道共享 prompt 构建与验证逻辑，仅在 transport 层分叉，确保两种路径的输出结构一致
2. **Plan 为正则化前驱**：LLM/SDK 输出的 JSON 先经 `WorkflowPlan` Pydantic 模型校验，再经 `canonicalize_workflow_plan()` 正规化，最后通过 `validate_generated_plan()` 语义校验
3. **Repair loop 内置**：生成失败时自动进入修复循环（`WorkflowPlanningRepairLoop`），由 `workflow_plan_repair_attempts` 配置最大尝试次数，每次修复携带上次的 `validation_error`
4. **Richness 驱动的拓扑控制**：通过 `planning_richness` 参数（minimal/standard/detailed/comprehensive）控制 DAG 的节点数、并行度和结构复杂度
