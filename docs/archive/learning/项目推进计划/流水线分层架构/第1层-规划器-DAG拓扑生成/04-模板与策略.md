# 04 - 模板与策略

## planning_strategies.py 的策略模式

`orchestrator/dag/planning_strategies.py` 定义了 Planner 的两种生成策略。文件极为精简（共 29 行），体现了清晰的策略模式设计：

```
PlanningStrategy (Protocol)
    |
    +-- WorkflowLLMPlanningStrategy   --> generator.generate_with_llm_request()
    +-- WorkflowPlannerSDKStrategy    --> generator.generate_with_planner_sdk_request()
```

两个策略都是 `frozen=True` dataclass，各持有一个 `WorkflowPlanGenerator` 实例。区别仅在于调用生成器的哪个方法 -- 方法的差异意味着不同的 transport 层和不同的模型交互方式。策略由 `EnginePlanningMixin._planner_sdk_strategy()` 和 `_llm_planning_strategy()` 工厂方法创建。

## Skill 注册表与摘要体系

Planner 不直接读取每个 Skill 的完整 `SKILL.md`（那会耗费大量 token），而是通过 `SkillRegistry`（定义在 `orchestrator/dag/types.py`）提供的两份**摘要数据**来指导节点选择。

### planning_snapshot() -- Skill 模板摘要

`SkillRegistry.planning_snapshot()` 返回所有已注册 Skill 的摘要列表，每个 Skill 摘要包含以下字段：

| 字段 | 说明 | 在 prompt 中的体现 |
|------|------|------------------|
| `id` | Skill 唯一标识符（如 `agenda_setter`） | `skill_id` 列 |
| `label` | 中文标签（如"议题设定"） | `label` 列 |
| `layer` | 常见流水线层号 | 用于 `stage` 推导 |
| `blockProfile.stage` | 阶段：entry/evidence/synthesis/deepening/output/verification/review | `stage` 列 |
| `blockProfile.archetype` | 积木原型：collector/analyzer/synthesizer/reporter/exporter/verifier/reviewer | `archetype` 列 |
| `blockProfile.preferredPredecessors` | 推荐前驱阶段列表 | `predecessor_stages` 列 |
| `blockProfile.preferredSuccessors` | 推荐后继阶段列表 | `successor_stages` 列 |
| `trigger.when` / `trigger.keywords` | 触发条件和关键词 | `trigger` 列（前 48 字符） |
| `description` | 简要说明 | 后备 trigger 文本 |

prompt 中呈现为 8 列 Markdown 表格（`engine_prompts.py` 的 `_skill_catalog_row()`）：

```
| skill_id | label | stage | archetype | predecessor_stages | successor_stages | trigger | summary |
```

`summary` 列格式：`skill_id（label；阶段=xxx；前驱=xxx；后继=xxx；适用=<trigger>）`

### planning_block_catalog() -- 节点积木目录

`SkillRegistry.planning_block_catalog()` 返回抽象积木结构（archetypes + recipes），不绑定具体 Skill：

**Archetypes（积木原型）**：每种原型对应一个流水线阶段，包含：
- `stage`: 流水线阶段名
- `label`: 中文标签
- `purpose`: 职责说明
- `successor_stages`: 允许的后继阶段
- `structural_behaviors`: 结构行为特征（如 `root`/`singleton`/`fanout`/`converge`）

**Recipes（拓扑配方）**：预设的结构模式，包含：
- `label`: 配方名称
- `pattern`: 结构模式描述
- `use_when`: 适用条件

prompt 中呈现为（`_node_block_lines()`）：

```text
- entry_point: 入口节点（阶段=entry；下游=evidence；行为=root/singleton；...）
- evidence_collector: 证据收集节点（阶段=evidence；下游=synthesis；...）
...
- 配方 recipe_a: xxx（pattern；适用=xxx）
```

### filter_skill_snapshot_for_report_scope()

在 `engine_prompts.py` 的 `_skill_lines()` 中，`planning_snapshot()` 的结果会经过 `orchestrator/export/report_scope.py` 的 `filter_skill_snapshot_for_report_scope()` 按用户需求文本（`raw_query`）过滤，移除与当前报告范围不相关的 Skill。

## Skill 按功能分类

系统内 35+ Skill 按功能分为以下大类（对应 `blockProfile.stage` 字段）：

### entry（入口层）

| Skill ID | 中文标签 | 说明 |
|----------|---------|------|
| `agenda_setter` | 议题设定 | 解析用户意图，定义分析范围和口径 |
| `data_discovery` | 数据发现 | 扫描本地和外部数据源，定位可用数据 |
| `issue_scoping` | 议题界定 | 在 open 模式下使用，明确分析对象与范围 |

### evidence（取证层 / collection 收集）

包括数据采集、查询、API 调用等 Skill，负责从各种数据源获取原始数据。典型节点积木为 `evidence_collector`，阶段 = `evidence`，前驱阶段通常是 `entry`，后继阶段通常是 `synthesis`。

### synthesis（综合分析层 / analysis 分析）

包括跨源数据整合、统计计算、模式识别等 Skill，负责将多路证据汇拢并产出中间结论。典型积木为 `evidence_synthesizer`，前驱 = `evidence`/`deepening`，后继 = `deepening`/`output`/`verification`。

### deepening（深化层）

在标准分析基础上进行专题深化、情境推演、风险评估等 Skill。典型积木前驱 = `synthesis`，后继 = `output`/`synthesis`。

### output（报告层 / reporting）

负责生成最终交付物（报告、可视化、摘要等）。典型积木为 `report_prep`/`report_writer`，前驱 = `synthesis`/`deepening`/`verification`，后继 = `review`。

### verification / review（审校层）

- **verification**：交叉验证、数据一致性检查
- **review**：终审和质量把关

### export（导出层）

负责将结果导出为文件或推送到外部系统。

## when_to_use 字段如何指导节点选择

`engine_prompts.py` 的 `_skill_when_to_use()` 函数从 Skill 元数据中提取"何时使用"信号，优先级如下：

1. **`trigger.when`**：如果存在，取前 48 字符作为触发条件描述（如"当用户需要分析选举数据时"）
2. **`trigger.keywords`**：如果存在，取最多 3 个关键词用 `/` 连接（如"选举/分析/民调"）
3. **`description`**：回退到 description 的前 48 字符
4. **默认**：`"职责高度吻合时复用"`

此字段在 prompt 的 Skill 模板目录中以 `适用=<when_to_use>` 形式呈现，让 LLM/Agent 能快速判断每个 Skill 是否适用于当前任务。`planning.triggerWhen/triggerKeywords` 仅用于职责匹配参考；prompt 中明确标注"只有当节点职责高度吻合时才复用对应 skill"。

## workflow_topology_guidance.py 的拓扑结构指导

`orchestrator/dag/workflow_topology_guidance.py` 是本层的拓扑约束引擎，独立于 Skill 目录，专注于 DAG 的结构维度。

### 核心数据结构

#### _RECOMMENDED_NODE_RANGES

```python
{
    "minimal": (2, 4),
    "standard": (5, 8),
    "detailed": (10, 16),
    "comprehensive": (15, 25),
}
```

#### _ASSEMBLY_RULES（组装规则）

| Richness | 规则 |
|----------|------|
| minimal | 优先形成"问题界定 -> 1-2 个必要执行节点 -> 输出/确认"的最小可执行结构 |
| standard | 优先形成"问题界定 -> 2-3 路轻并行取证 -> 综合分析 -> 输出"的单次分流结构，至少 5 个节点 |
| detailed | 优先形成两段结构，必须至少 10 个节点 |
| comprehensive | 优先形成多级结构，必须至少 15 个节点，保持多级推进 |

#### _TOPOLOGY_TARGETS

四个档位的 `WorkflowTopologyTarget` 结构，包含：

| 字段 | 说明 | 示例（comprehensive） |
|------|------|---------------------|
| `min_node_count` | 最低节点数 | 15 |
| `enforce_min_node_count` | 是否强制要求 | True |
| `min_parallel_layers` | 最少并行层数 | 2 |
| `min_max_width` | 最宽层最少节点数 | 4 |
| `min_convergence_nodes` | 最少汇聚节点数 | 2 |
| `min_fanout_nodes` | 最少扇出节点数 | 2 |
| `require_wide_narrow_wide` | 是否要求"宽-窄-宽"结构 | True |

#### _TOPOLOGY_GUIDES

每个档位的四类指导语：

```python
{
    "principles": ("核心原则1", "核心原则2", ...),
    "preferred": ("推荐结构1", "推荐结构2", ...),
    "acceptable": ("可接受结构1", ...),
    "mistakes": ("常见误区1", ...),
}
```

### 关键函数

| 函数 | 用途 |
|------|------|
| `resolve_topology_target()` | 根据 richness + user_input 解析拓扑目标。检测"最小冒烟/自检/链路验证"关键词时自动降级为 minimal |
| `topology_target_text()` | 生成档位门槛提示文本（如"必须至少 15 个节点...建议至少 2 个并行层...优先呈现宽-窄-宽结构"） |
| `topology_assembly_rule_text()` | 返回当前档位的组装规则文本 |
| `topology_node_strategy_rule()` | 生成节点策略规则文本，综合 richness、allowed_mode 和反模板警告（如 comprehensive 模式下明确禁止 [1,N,1] 单层扇形） |
| `topology_prompt_guidance_lines()` | 生成完整拓扑指导行，注入到 prompt 的第 3 层 |
| `topology_repair_guidance_lines()` | 解析校验错误中的拓扑失败信息，生成针对性修复建议 |
| `topology_failure_user_message()` | 生成面向用户的中文失败消息 |

### 自动降级机制

`_topology_target_key()` 检测用户输入中的诊断/自检关键词（`_EXPLICIT_MINIMAL_WORKFLOW_HINTS` 如"最小可执行"、"最小工作流"、"smoke test"、"self-check" 等）和 `_MINIMAL_SCOPE_HINTS` + `_DIAGNOSTIC_SCOPE_HINTS` 的组合。命中时自动将拓扑目标设为 `minimal`，覆盖 planning_richness 设置。

### 反模板警告

在 comprehensive 和 detailed 档位下，`topology_node_strategy_rule()` 会明确注入反模板警告：

- `⚠️ 反模板：不要生成 [1,N,1] 单层扇形，也不要退化成全串行单链`
- comprehensive open 模式：优先采用"首轮并行取证 -> 中间汇聚 -> 二次专题展开 -> 最终综合/交付"的多级结构
- 即使用户要求最小可执行，也不要在第一轮汇聚后直接结束

### Repair 中的拓扑诊断

`topology_repair_guidance_lines()` 通过解析 `validation_error` 字符串（格式为 `workflow topology below target; richness=xxx; mismatches=node_count|parallel_layers|...; widths=[...]`）生成多维修复建议：

- 检测到 `[1,N,1]` 单层扇形时，建议在采集层与最终输出之间补中间综合节点
- 根据 `mismatches` 中的具体缺失维度（node_count/parallel_layers/max_width/convergence_nodes/fanout_nodes/wide_narrow_wide）给出对应的补全建议
