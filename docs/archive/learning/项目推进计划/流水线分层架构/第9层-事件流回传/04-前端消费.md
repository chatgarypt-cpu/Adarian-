# 04 - 前端消费

前端通过双路径消费后端推送的事件流：Chat 流关注消息级别的实时交互，Monitor 流关注运行级别的状态变更。两者最终都汇入 Zustand Store，驱动 React 组件的更新。

## Chat 流 SSE 连接：`useChatStreaming.ts`

文件位置：`frontend/src/hooks/useChatStreaming.ts`

### 架构概览

`useChatStreaming` 是一个 React Hook，管理完整的聊天气流生命周期：

```
sendMessage() → generation.jobId
                  │
                  ▼
           connectStream(sessionId, generationId, connector, pushError)
                  │
                  ├─ connector = (onEvent, onError, onClose) =>
                  │     chatApi.subscribeGeneration(generationId, onEvent, onError, {lastEventId, onClose})
                  │
                  ▼
           SSE → handleEvent(event) → chatStreamingEvents.ts
                  │
                  ├─ handleNonTerminalChatStreamEvent()
                  │   ├─ message.start
                  │   ├─ message.delta       → pendingDeltaRef += content → scheduleFlush()
                  │   ├─ message.reasoning   → pendingReasoningRef += reasoning → scheduleFlush()
                  │   ├─ workflow.created    → setCurrentWorkflow()
                  │   ├─ workflow.update     → setCurrentWorkflow() + progress
                  │   ├─ phase.change        → updateProgress()
                  │   ├─ tool.start          → upsertToolCall(status="running")
                  │   └─ tool.end            → upsertToolCall(status="completed"/"error")
                  │
                  ├─ error                   → cancelFlush() + persistStreamingSnapshot(status="error")
                  └─ message.end             → completeStreamingSession()
```

### 核心状态

| state | 类型 | 说明 |
|-------|------|------|
| `streamingContent` | `string` | 当前正在流式输出的 LLM 文本 |
| `streamingMessageId` | `string \| null` | 当前 assistant message ID |
| `isStreaming` | `boolean` | 是否有活跃的 SSE 连接 |
| `streamingReasoning` | `string` | 推理过程文本 |
| `reasoningDuration` | `number \| null` | 推理持续时间（秒） |
| `workProgress` | `WorkProgress \| null` | 当前工作进度（phase + message + toolCalls） |
| `currentWorkflow` | `WorkflowPreviewState \| null` | 当前工作流预览状态 |

### 流式文本合并策略

为避免高频 `setState` 导致性能问题，`useChatStreaming` 使用 **requestAnimationFrame 批量刷新**策略：

1. `handleMessageDelta` / `handleReasoning` 将 delta 追加到 `pendingDeltaRef` / `pendingReasoningRef`
2. 调用 `scheduleFlush()` 调度一个 `requestAnimationFrame` 回调
3. 在 `flushPending()` 中一次性将累积的 delta 提交到 state

```typescript
const flushPending = useCallback(() => {
    flushRef.current = null;
    const deltaChunk = pendingDeltaRef.current;
    const reasoningChunk = pendingReasoningRef.current;
    if (!deltaChunk && !reasoningChunk) return;

    if (deltaChunk) {
        pendingDeltaRef.current = "";
        streamingContentRef.current += deltaChunk;
    }
    if (reasoningChunk) {
        pendingReasoningRef.current = "";
        streamingReasoningRef.current = `${streamingReasoningRef.current}${reasoningChunk}`;
        liveSnippet = buildReasoningSnippet(streamingReasoningRef.current);
    }

    startTransition(() => {
        if (deltaChunk) setStreamingContent(streamingContentRef.current);
        if (reasoningChunk) setStreamingReasoning(streamingReasoningRef.current);
        setWorkProgress(mergePendingWorkProgress({deltaChunk, liveSnippet, reasoningChunk, toolCalls}));
    });
}, []);
```

### 断线重连机制

`connectStream` 中的 `handleError` 和 `handleClose` 实现了自动重连：

1. **handleError**：如果错误不是 `AbortError`，通过 `chatApi.getGeneration(generationId)` 查询 generation 当前状态：
   - 状态为 `completed`/`canceled`：正常结束
   - 状态为 `queued`/`starting`/`running`/`cancel_requested`：**自动重连**，携带 `lastEventIdRef.current`
   - 其他：显示错误

2. **handleClose**（SSE 连接正常关闭）：同样查询 generation 状态，若仍处于活跃状态则重连。

```typescript
// handleError 中的重连逻辑
if (LIVE_ACTIVE_GENERATION_STATUSES.has(status)) {
    streamHadErrorRef.current = false;
    connectStream(
        failedSessionId, failedGenerationId,
        (onEvent, onStreamError, onStreamClose) =>
            chatApi.subscribeGeneration(failedGenerationId, onEvent, onStreamError, {
                lastEventId: lastEventIdRef.current,
                onClose: onStreamClose,
            }),
        undefined,
        generation.assistantMessageId
    );
    return;
}
```

### Stream Lease 机制

为防止过期的 SSE 回调干扰当前活跃流，每次 `connectStream` 都创建一个新的 `ChatStreamLease`，包含递增的 `epoch`、`sessionId`、`generationId`。所有 `handleEvent` / `handleError` / `handleClose` 回调首先检查 `matchesChatStreamLease()` / `matchesChatStreamEpoch()`，不匹配则直接返回。

## Chat 流事件处理：`chatStreamingEvents.ts`

文件位置：`frontend/src/hooks/chatStreamingEvents.ts`

### `handleNonTerminalChatStreamEvent()` -- 事件路由

```typescript
export function handleNonTerminalChatStreamEvent(event: MessageStreamEvent, ctx: ChatStreamEventContext): boolean {
    switch (event.type) {
        case "message.start":     handleMessageStart(event, ctx);              return true;
        case "message.delta":     return handleMessageDelta(event, ctx);
        case "message.reasoning": return handleReasoning(event, ctx);
        case "workflow.created":  return handleWorkflowCreated(event, ctx);
        case "workflow.update":   return handleWorkflowUpdate(event, ctx);
        case "phase.change":      return handlePhaseChange(event, ctx);
        case "tool.start":        return handleToolStart(event, ctx);
        case "tool.end":          return handleToolEnd(event, ctx);
        case "thinking":          ctx.updateProgress("thinking", ...);         return true;
        default:                  return false;
    }
}
```

返回 `true` 表示事件已在 Chat 流中处理，`useChatStreaming.ts` 不会继续走后续的 `switch(event.type)` 分支（`error` 和 `message.end` 由外层处理）。

### 工具调用状态追踪

`upsertStreamingToolCall()` 维护工具调用列表的状态合并：

```
tool.start → upsert({id, name, arguments, status: "running", startedAt})
tool.end   → upsert({id, name, result, status: "completed"/"error", finishedAt})
```

当 `tool.end` 到达但尚未匹配到 `id` 时，回退到按 `name + status="running"` 匹配（处理 Agent SDK 中 tool_use_id 可能不连续的情况）。

### workProgress 阶段

| phase | 说明 | 触发事件 |
|-------|------|----------|
| `connecting` | 正在建立连接 | `connectStream()` 初始化 |
| `parsing_intent` | 正在理解需求 | `message.start` |
| `generating_workflow` | 规划任务完成 | `workflow.created` |
| `queued` | 工作流排队等待 | `workflow.update(status="queued")` |
| `executing` | 正在执行 | `workflow.update(status="executing")` |
| `thinking` | LLM 正在思考 | `thinking` / `tool.start` |
| `writing` | LLM 正在输出文本 | `message.delta` |
| `completed` | 生成完成 | `message.end` 或 `workflow.update(status="completed")` |
| `error` | 出错 | `error` 事件 |

## Monitor 流：`useRunEventStream.ts`

文件位置：`frontend/src/features/monitor/useRunEventStream.ts`

### 初始化流程（Bootstrap）

```
1. fetchRunSummary(runId)
   └─ 获取 run 摘要（status, progress_pct, node_count, latest_seq 等）

2. applySummary(summary)
   └─ 用摘要数据初始化 nodeStatuses, workflowStatus, progressPct

3. 分页回溯历史事件
   while cursor < latest_seq:
       fetchRunEvents(runId, {afterSeq: cursor, limit: 200})
       appendHistoryBatch(events)
       cursor = lastEventSeq(events)

4. gapDetector.prime(latest_seq)
   └─ 初始化丢包检测器

5. openStream(latest_seq)
   └─ 建立 SSE 连接，携带 afterSeq 参数
```

### `EventSource` 连接

```typescript
const stream = new EventSource(apiUrl(buildMonitorStreamPath(runId, {
    historyLimit: null,
    lastEventId: String(afterSeq),
})));

stream.onmessage = (ev) => {
    const parsed = safeParseEvent(ev.data, runId);
    const seqNum = eventSeq(parsed);
    const gapResult = gapDetector.ingest(seqNum);
    if (gapResult.hasGap) {
        pendingGapRef.current = mergePendingGapRange(pendingGapRef.current, [gapResult.gapStart, gapResult.gapEnd]);
    }
    pendingRef.current.push(parsed);
    // 通过 requestAnimationFrame 批量提交
    rafIdRef.current = requestAnimationFrame(() => { ... });
};
```

同样使用 `requestAnimationFrame` 批量提交策略，避免高频重渲染。

### 丢包检测与填补（Gap Detection）

`GapDetector` 类监控序列号的连续性。当检测到序列号跳跃时：
1. 记录 gap 范围 `[gapStart, gapEnd]`
2. 通过 REST API `fetchRunEvents(runId, {afterSeq: gapStart - 1, limit})` 填补缺失事件
3. 填补成功后清除 gap 标记

## `runEventStore` (Zustand) 状态管理

文件位置：`frontend/src/features/monitor/runEventStore.ts`

### 核心数据结构

```typescript
interface RunEventStoreState {
    events: Map<number, MonitorStreamEvent>           // seq → event 全量事件
    nodeStatuses: Map<string, NodeSnapshot>            // nodeId → {status, message}
    workflowEvents: MonitorEventView[]                 // workflow 级事件（最多 WORKFLOW_EVENTS_MAX）
    nodeEventHistoryById: Record<string, MonitorEventView[]>  // nodeId → 节点事件历史（最多 NODE_EVENTS_MAX）
    streamingTextByNodeId: Record<string, string>      // nodeId → 累积的 LLM 流式文本
    streamingThinkingByNodeId: Record<string, string>  // nodeId → 累积的推理文本
    workflowStatus: string                             // idle / executing / completed / error
    progressPct: number                                // 整体进度百分比
    lastSeq: number                                    // 最新事件序列号
    gapRanges: Array<[number, number]>                 // 丢包间隙
    streamStatus: MonitorConnectionStatus              // idle / connecting / connected / error
    isReplaying: boolean                               // 是否正在重放
    totalEvents: number                                // 事件总数提示
    duplicateCount: number                             // 重复事件计数
    divergences: RunEventDivergence[]                  // 分歧事件列表
}
```

### `applyEvents()` -- 批量事件追加

```typescript
applyEvents: (raws: Record<string, unknown>[]) => {
    for (const raw of raws) {
        const event = toMonitorStreamEvent(raw);
        const seq = getEventSeq(event);

        // 无序列号的事件：追加到 workflowEvents + nodeEventHistoryById
        if (seq === null) { ... continue; }

        // 去重：检测相同 seq 的已有事件
        if (existing) { duplicateCount++; warnDuplicate(); continue; }

        // 存入 events Map
        nextEvents.set(seq, event);

        // 分类追加
        workflowEvents = appendMonitorEvent(workflowEvents, event, 'workflow', MAX);
        nodeEventHistoryById[nodeId] = appendMonitorEvent(..., 'node', MAX);

        // LLM token delta 特殊处理：累积到 streamingText/streamingThinking
        if (event.type === 'llm_token_delta') streamingTextByNodeId[nodeId] += text;
        if (event.type === 'llm_thinking_delta') streamingThinkingByNodeId[nodeId] += thinking;

        // 判定是否需要重放
        if (eventAffectsReplay(event)) replayRequired = true;
    }

    // 如有重放需求：执行增量或全量 replayEvents()
    const result = replayRequired ? replayEvents(...) : null;

    // 事件窗口裁剪：保留最多 RUN_EVENT_RETAINED_MAX (5000) 条
    const retainedEvents = trimRunEventWindow(nextEvents);

    set({ events: retainedEvents, nodeStatuses: result?.nodeStatuses, ... });
}
```

### 事件窗口裁剪策略

`trimRunEventWindow()` 在事件数量超过 `RUN_EVENT_RETAINED_MAX`（5000）时移除最旧的非重放影响事件（`eventAffectsReplay()` 返回 `false` 的事件优先移除）。重放影响的事件类型包括：

```
node.canceled, node.complete, node.error, node.progress,
node.skipped, node.start, run_status,
workflow.complete, workflow.error, workflow.start
```

### 去重与分歧检测

对相同 `seq` 的事件比对 `eventSignature()`（稳定 JSON 序列化），不一致时记录为 `RunEventDivergence`。这在事件被重新发布或 SQLite 与 Redis 数据不一致时提供诊断线索。

### 工作流状态映射

`_RUN_STATUS_TO_WORKFLOW_STATUS` 将 run 状态映射为 workflow 状态：

```
starting/started/running → executing
pending/queued           → queued
completed/success        → completed
completed_with_issues    → completed_with_issues
error/failed/timeout/canceled → error
```

### 运行时状态叠加

`overlay_workflow_runtime_state()` 从 Redis 读取 run meta 和 node states，将实际运行时状态叠加到 draft workflow 的快照上。这使得前端展示的 workflow 节点状态能实时反映容器执行进度。

`overlay_message_panel_metadata()` 在 Chat 消息的 metadata 中叠加面板快照，供前端在历史消息中展示执行进度。

## 前端重连和错误处理

### Chat 流

1. **主动断开**：`detachStreaming()` → 递增 epoch → `abort()` → 清理 timer
2. **被动断开**：`handleClose()` → 查询 generation 状态 → 若仍活跃则 `connectStream()` 重连
3. **错误**：`handleError()` → 持久化流式快照（状态 `"error"`）→ 查询 generation 状态 → 重连或展示错误
4. **组件卸载**：`useEffect(() => () => detachStreaming(), [])` 确保清理

### Monitor 流

1. **SSE `onerror`**：根据 `EventSource.readyState` 判断是重连中（`CONNECTING`）还是永久失败（`CLOSED`），更新 `streamStatus`
2. **丢包恢复**：`GapDetector` 检测序列号跳跃 → `handleGap()` 通过 REST API 填补
3. **页面隐藏**：`window.addEventListener('pagehide', flushPending)` 确保页面隐藏前提交未处理的事件
4. **手动重连**：`reconnect()` 关闭现有 EventSource，清除 gap 信息，等待 `reconnectToken` 变化触发重新 bootstrap
