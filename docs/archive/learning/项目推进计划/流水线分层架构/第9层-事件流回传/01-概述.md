# 01 - 事件流概述

## 事件流在整个流水线中的位置

本系统采用三层流水线架构，事件流回传位于整个流水线的**最后一段**，负责将 Agent 容器内的运行时数据实时回传到前端展示层。完整流水线如下：

```
[用户输入] → [chat/planning 规划层] → [DAG/workflow 调度层] → [Agent 容器执行层] → [事件流回传层] → [前端展示]
                                                                                          ▲
                                                                                          │
                                                                                    本节关注范围
```

事件流回传层不参与业务逻辑计算，而是作为**实时数据总线**，确保前端能够以低延迟感知后端运行状态。它的核心价值在于：让"黑盒"的容器执行过程变为可观测。

## 端到端事件链路

事件从产生到消费跨越 5 个进程边界，完整链路如下：

```
Agent 容器 (Python 进程)
  │ event_recorder.py → append_sdk_message() → sdk_messages.jsonl
  │
  ▼ (Redis Pub/Sub 或 Pipeline XADD)
Orchestrator 调度器 (Python 进程)
  │ launcher_events.py → sdk_message_handler() → _publish_parent_run_event()
  │ dependencies.py → publish_run_event_async() / publish_run_event()
  │ event_classification.py → annotate_run_event() → 分类 & 序列号
  │
  ▼ (Redis Streams: run:{run_id}:events)
Orchestrator SSE 端点 (Python FastAPI)
  │ event_stream.py → stream_run_events() → StreamingResponse
  │ event_stream_hub.py → subscribe_run_events() → 多客户端广播
  │ sse.py → sse_data() → 格式化 SSE 帧
  │
  ▼ (HTTP SSE: text/event-stream)
前端浏览器 (TypeScript React)
  │ useChatStreaming.ts → connectStream() → subscribeGeneration()
  │ useRunEventStream.ts → EventSource → EventSource.onmessage
  │
  ▼ (Zustand Store)
  │ runEventStore.ts → applyEvents() → 节点状态 / LLM token delta
  │
  ▼ (React 组件)
  │ ReactFlow 更新 → 节点变色 / 执行进度条 / 消息面板
```

## 三个关键阶段

### 阶段一：容器内记录

位置：`agent/event_recorder.py`

Agent 容器内运行的 Claude Agent SDK 产生 raw SDK message，由 `append_sdk_message()` 逐条追加到工作区 `sdk_messages.jsonl` 文件。同时 `compact_sdk_message()` 将冗长的原始消息压缩为结构化的 compact 摘要，供事件管道传输。

关键函数：
- `append_sdk_message(ws, entry, lock)` -- 追加原始 SDK 消息
- `compact_sdk_message(message)` -- 将 SDK 消息压缩为 compact 结构
- `append_audit_event(ws, entry, lock)` -- 追加审计日志到 `audit.jsonl`

### 阶段二：Redis 中转

位置：`orchestrator/dag/launcher_events.py` 和 `orchestrator/dependencies.py`

调度器的 `sdk_message_handler()` 监听来自容器的 compact 消息，通过 `_publish_parent_run_event()` 将事件写入 Redis Streams。`publish_run_event_async()` 执行两件事：

1. **写入 Redis Stream**：`XADD run:{run_id}:events`，按 `run_event_stream_maxlen` 配置限制 stream 长度（默认 5000）
2. **写入 SQLite**：`persist_run_event_to_sqlite()` 持久化事件历史

每个事件经过 `annotate_run_event()` 获得：
- `event_schema_version`：事件结构版本号（当前为 1）
- `event_class`：事件分类（`audit_critical` / `display_delta` / `state_snapshot` / `debug_verbose`）
- `payload_size_bytes`：负载大小

### 阶段三：SSE 推送与前端消费

位置：`orchestrator/runs/event_stream.py` 和 `frontend/src/hooks/useChatStreaming.ts`

Orchestrator 暴露 SSE 端点 `GET /api/runs/{run_id}/stream`。该端点通过 `RunEventStreamHub` 订阅 Redis Stream，将事件广播到所有连接的 SSE 客户端。前端通过两种路径消费：

1. **Chat 流**：`useChatStreaming.ts` → `subscribeGeneration()` → 消息级事件（`message.delta`, `tool.start`, `workflow.created` 等）
2. **Monitor 流**：`useRunEventStream.ts` → `EventSource` → 运行级事件（`node.start`, `node.complete`, `llm_token_delta` 等）

## 关键设计决策

1. **双路径设计**：Chat 流关注"消息级"语义事件（理解用户意图、工具调用、工作流生成），Monitor 流关注"运行级"状态事件（节点进度、token 消耗、工作流生命周期）。两者共享 `run:{run_id}:events` 下的同一 Redis Stream，但前端通过不同的 Consumer 逻辑分流处理。

2. **三层持久化**：事件同时存在于 (1) Agent 容器内的 `sdk_messages.jsonl`（原始记录），(2) Redis Streams（实时热数据，有容量上限），(3) SQLite（冷数据持久化，支持历史回溯）。

3. **compact 而非 raw**：传输链路中使用 `compact_sdk_message()` 压缩过的消息而非完整 SDK message，大幅减少事件体积，同时保留前端展示所需的关键字段（`kind`, `event_group`, `text_preview`, `input_preview` 等）。

4. **SSE 而非 WebSocket**：选择 SSE 因其单向推送特性正好匹配事件流回传的需求，且原生支持 `Last-Event-ID` 断线重连机制，无需额外协议层。
