# 02 - 事件管道

事件管道覆盖从 Agent 容器内的原始 SDK 事件记录，到 Orchestrator 端的事件转换和发布逻辑。本章聚焦事件的数据结构和分类体系。

## 容器内事件记录：`event_recorder.py`

文件位置：`agent/event_recorder.py`

### `append_sdk_message()` -- 追加 SDK 原始消息

```python
async def append_sdk_message(ws: Path, entry: dict[str, Any], lock: asyncio.Lock) -> None:
    await _append_jsonl_row(ws / "sdk_messages.jsonl", entry=entry, lock=lock)
```

将 Claude Agent SDK 产生的每一条原始消息追加到工作区根目录的 `sdk_messages.jsonl` 文件。写入操作通过 `asyncio.to_thread()` 委托到独立线程执行，避免阻塞事件循环。底层 `_append_jsonl_row()` 使用 `common/runtime_files.py` 中的 `append_jsonl_line()` 保证原子写入。

同类函数 `append_audit_event()` 将工具调用的审计记录写入 `audit.jsonl`。

### `compact_sdk_message()` -- 压缩消息

原始 SDK message 可能包含数 KB 的文本内容（如完整的 tool result），不适合在事件管道中全量传输。`compact_sdk_message()` 对三类消息执行压缩：

| 输入类型 | 处理函数 | 输出 |
|----------|----------|------|
| `dict` 含 `subtype` | `compact_sdk_subtype_message()` | `kind: "subtype"`，如 `init`/`task_started`/`task_progress`/`success`/`error` |
| `dict` 含 `event` | `compact_sdk_stream_event_message()` | `kind: "message_start"/"message_delta"/"message_stop"/"stream_delta"` |
| `dict` 含 `content` | `compact_sdk_content_message()` | `kind: "tool_call"/"tool_result"/"text"` |
| `str` | 直接截断 | `kind: "text"`, `event_group: "assistant"` |

每个 compact 输出都包含：
- `kind`：消息类别
- `event_group`：分组标识（`assistant` / `tool` / `task` / `session`）
- 预览字段：`text_preview`、`input_preview`、`content_preview` 等，均受 `SDK_MESSAGE_*_PREVIEW_MAX_CHARS` 常量限制

关键常量（定义于 `agent/output_limits.py`）：
- `SDK_MESSAGE_TEXT_PREVIEW_MAX_CHARS`：文本预览上限
- `SDK_MESSAGE_JSON_PREVIEW_MAX_CHARS`：JSON 预览上限
- `SDK_MESSAGE_TOOL_INPUT_PREVIEW_MAX_CHARS`：工具输入预览上限
- `SDK_MESSAGE_TOOL_RESULT_PREVIEW_MAX_CHARS`：工具结果预览上限
- `SDK_MESSAGE_ASSISTANT_TEXT_PREVIEW_MAX_CHARS`：助手文本预览上限
- `SDK_MESSAGE_STATUS_TEXT_PREVIEW_MAX_CHARS`：状态文本预览上限

### 流式 delta 事件压缩

`compact_sdk_stream_event_message()` 处理 Anthropic SDK 标准的 stream events：

```
event.type = "message_start"  → compact_sdk_message_start_event()
  ├─ message.id, model, role, usage (input_tokens, output_tokens)
  └─ session_id

event.type = "message_delta"  → compact_sdk_message_delta_event()
  ├─ delta.stop_reason, stop_sequence
  ├─ usage (input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens)
  └─ session_id

event.type = "content_block_start" → compact_sdk_stream_start_event()
  └─ 仅处理 thinking/redacted_thinking block

event.type = "content_block_delta"
  ├─ delta.type = "text_delta" → stream_delta_payload(delta_type="text_delta", field_name="delta_text")
  └─ delta.type = "thinking_delta" → stream_delta_payload(delta_type="thinking_delta", field_name="delta_thinking")
```

## DAG 调度事件类型：`launcher_events.py`

文件位置：`orchestrator/dag/launcher_events.py`

### `build_event_handlers()` -- 事件处理器工厂

为每个 DAG node 创建三个事件处理器：

| 处理器 | 触发时机 | 功能 |
|--------|----------|------|
| `on_container_started` | Docker 容器启动 | 写入 node run meta + parent active node |
| `on_audit_event` | Agent 内工具调用 | 发布 `tool_use` 事件到 parent run stream |
| `on_sdk_message_event` | Agent 内 SDK 消息 | 分解为 stream_delta / tool_stream / progress 三类子事件发布 |

### `sdk_message_handler()` -- SDK 消息处理

这是事件管道的**核心转换点**。接收到来自容器回调的 compact 消息后，执行以下流程：

1. **条件发布 parent 消息**：`should_publish_parent_sdk_message()` 判定该消息是否值得广播到父 run stream。`stream_delta`、`tool_call`、`tool_result`、`tool_result_missing_content` 及 `progress` notification 不在此发布（它们有专用子事件通道）。

2. **分解为子事件**：通过三个工厂函数生成专用事件：
   - `sdk_stream_delta_event()` → `llm_token_delta` / `llm_thinking_delta`
   - `sdk_tool_stream_event()` → `llm_tool_start` / `llm_tool_result`
   - `sdk_progress_event()` → `node.progress`

3. **MCP 故障检测**：调用 `failed_mcp_servers()` 检查 init 消息中的 MCP 服务器状态，对 `status == "failed"` 的服务发布 `capability.degraded` 事件。

4. **父 run 活动更新**：`touch_parent_runtime_activity()` 更新 parent run 的 `updated_at`、`last_runtime_activity_at`、`last_progress_at`。

### 事件类型枚举

**Published 到 parent run stream 的事件**：

| 事件 type | 来源 | 说明 |
|-----------|------|------|
| `sdk_message` | `should_publish_parent_sdk_message()` | 重要的 SDK 消息（message_start, message_stop, init, 各类 task/subagent 事件） |
| `llm_token_delta` | `sdk_stream_delta_event()` | LLM 文本输出 delta |
| `llm_thinking_delta` | `sdk_stream_delta_event()` | LLM 推理输出 delta |
| `llm_tool_start` | `sdk_tool_stream_event()` | 工具调用开始（含 toolName, inputPreview） |
| `llm_tool_result` | `sdk_tool_stream_event()` | 工具调用结果（含 preview, isError） |
| `node.progress` | `sdk_progress_event()` | 节点执行进度（含 progress%, message） |
| `tool_use` | `audit_event_handler()` | 审计工具调用（compact tool use payload） |
| `capability.degraded` | `publish_mcp_degraded()` | MCP 服务器初始化失败 |

**DAG 调度层事件**（由 scheduler 直接发布，非来自 Agent 回调）：

| 事件 type | 说明 |
|-----------|------|
| `workflow.start` | 工作流开始执行 |
| `workflow.complete` | 工作流执行完成 |
| `workflow.error` | 工作流执行失败 |
| `node.start` | 节点开始执行 |
| `node.complete` | 节点执行完成 |
| `node.error` | 节点执行失败 |
| `node.canceled` | 节点被取消 |
| `node.skipped` | 节点被跳过 |
| `run_status` | 运行状态变更 |

## SSE 事件格式定义：`sse_payloads.py`

文件位置：`orchestrator/chat/sse_payloads.py`

```python
def iter_sse_json_payloads(raw_chunk: str) -> Iterator[dict[str, Any]]:
```

解析 SSE 数据块的标准格式。SSE 协议中每个事件以 `\n\n` 分隔，每行以 `data: ` 为前缀。该函数：
1. 按 `\n\n` 分割多事件块
2. 提取 `data: ` 前缀的行
3. 将 data 文本拼接后 `json.loads` 解析为 dict
4. 对解析失败的行静默跳过

输出由 `orchestrator/utils/sse.py` 的 `sse_data()` 编码，该函数将 JSON payload 按行分割并逐行添加 `data: ` 前缀：

```python
def sse_data(data: str) -> str:
    s = str(data or "").replace("\r\n", "\n").replace("\r", "\n")
    lines = s.split("\n")
    return "".join(f"data: {line}\n" for line in lines) + "\n"
```

### 序列号分配

事件序列号由 `annotate_run_event()` → `persist_run_event_to_sqlite()` 流程中自动分配。SQLite 表使用自增主键作为 `seq`，同时作为 SSE `id` 字段的值。`sequence_id` 在事件持久化到 SQLite 时写入 event 字典。

序列号的作用：
- SSE `Last-Event-ID` 断线重连：客户端重连时携带最后收到的 `seq`，服务端从该位置继续推送
- `after_seq` / `before_seq` 分页查询：REST API 支持按序列号范围查询历史事件
- `gapDetector` 丢包检测：前端通过序列号连续性检测事件丢失
