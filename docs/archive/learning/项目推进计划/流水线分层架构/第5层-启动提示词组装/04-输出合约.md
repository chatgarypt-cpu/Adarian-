# 04 - 输出合约

## `required_outputs` 生成机制

`required_outputs` 是在 `build_node_prompt()` 之外生成并作为参数传入的列表，来源于 DAG 拓扑合约对每个节点的输出约定。在 `launcher_executor.py` 第964行的调用点和 `scheduler.py` 第450行的包装调用点，`required_outputs` 从节点级别的 `execution_contract` 或 workflow plan 的 `required_outputs` 字段中提取。

`required_outputs_prompt_block()` 函数（`launcher_prompt.py` 第278-296行）将列表转化为强制性的自然语言约束。

### 非空时的输出格式

```
- 本节点本轮至少要真实写出以下具名业务文件：`output/report.md`、`output/evidence_map.json`。
- 这些具名业务文件才是本轮主交付；不要再把 `output/result.json` 当作默认必写项。
- 如果当前节点是 agenda_setter 且 required outputs 中包含 `output/task_spec/..._todo.csv`，
  必须通过 `Skill(csv-task-spec)` fork 生成下游 CSV，并确保这些 CSV 真实存在且格式正确。
- 如果你确实需要写 JSON 协议文件，`Write.content` 仍必须是字符串：先序列化，再写入。
```

### 空时的降级约束

```
- 本节点必须真实写出至少一个业务文件；不得只留下协议骨架、空目录或只推进 progress CSV。
- 除非 `execution_contract` 或显式 required outputs 要求，否则不要把 `output/result.json` 当作主交付。
- 如果你确实需要写 JSON 协议文件，`Write.content` 仍必须是字符串：先序列化，再写入。
```

## `task_prompt.md` 最终格式

`task_prompt.md` 是 `build_node_prompt()` 的返回值，由 `common/runtime_files.py` 第19行定义为 `TASK_PROMPT_REL = "input/task_prompt.md"`。它在工作区同步后被写入容器的 `input/` 目录，作为 Agent 会话启动后的第一条用户消息。

### 路径常量

所有在 prompt 中引用的路径均通过 `common/runtime_files.py` 的常量定义，保证 orchestrator 和 agent 容器两侧的一致性：

| 常量 | 值 | 用途 |
|------|-----|------|
| `TASK_PROMPT_REL` | `input/task_prompt.md` | 当前节点的任务 prompt |
| `TASK_SPEC_DIR_REL` | `output/task_spec` | CSV 进度文件目录 |
| `NODE_CONTEXT_REL` | `meta/node_context.json` | 节点上下文 |
| `TIME_CONTEXT_REL` | `meta/time_context.json` | 时间基准 |
| `NODE_EXECUTION_CONFIG_REL` | `meta/node_execution_config.json` | 冻结执行配置 |
| `PARENT_RUN_REL` | `meta/parent_run.json` | 父运行引用 |
| `RESULT_REL` | `output/result.json` | 通用结果文件 |

### Prompt 中的硬编码路径

在 `build_node_prompt()` 中，以下路径被硬编码并注入到 prompt 文本中（第356行、第380-381行、第407行）：

```python
node_execution_config_path = NODE_EXECUTION_CONFIG_REL  # "meta/node_execution_config.json"
node_workspace = "/workspace/current"
node_context_file = f"{node_workspace}/meta/node_context.json"
time_context_file = f"{node_workspace}/meta/time_context.json"
```

这些路径作为"已知 workspace 真值路径"直接嵌入 prompt，Agent 必须用 `Read(file_path="...")` 直接读取，不得先用 `Glob`、`LS` 或 `Bash` 去定位。

## `node_context.json` 的 `execution_contract` 字段

`node_context.json` 是每个节点启动前由调度器写入的核心运行时文件，位于 `common/runtime_files.py` 第21行定义的路径。它在 prompt 中被反复引用，是 Agent 获取运行时真值的**唯一来源**。

`execution_contract` 字段包含以下关键子字段（在 `build_node_prompt()` 中引用的）：

| 子字段 | 作用 |
|---|---|
| `execution_contract` | 当前节点的执行合约（控制权第2优先级） |
| `resource_hints` | 包含 `seed_paths` 和 `bootstrap_discovery_prefixes` |
| `workspace_contract` | 包含 `node_workspace` 和 `target_output_dir` |
| `upstream_inputs` | 上游节点 workspace 指针和 `upstream_file_map` |
| `downstream_nodes` | 下游真实节点列表（agenda_setter 使用） |
| `mcp` | MCP profile 配置（knowledge/search 的启停和工具别名） |
| `expected_task_spec_outputs` | 预期 CSV 进度文件列表 |

Path constants defined in `common/runtime_files.py` (lines 19-37) ensure consistency between the orchestrator and agent container sides.

## `expected_task_spec_outputs` 和 CSV 进度规范

每个节点的 CSV 进度文件遵循严格规范：

### 文件位置
- 当前节点自己的进度 CSV：`meta/node_execution_config.json.progress_csv_path` 指向
- 位于 `output/task_spec/<node_id>_todo.csv`

### 格式规范
- Header 固定为 `id,item,status`，**禁止改写**
- status 列为枚举值：`pending` / `in_progress` / `done` / `blocked` / `error`
- 禁止修改 `id` 和 `item` 列

### 操作规范
- runtime 只创建当前节点自己的 `_todo.csv`
- agenda_setter 的下游 CSV 必须通过 `Skill(csv-task-spec)` fork 生成
- 下游节点更新自身进度时，用 `Edit` 改自己 CSV 中对应行的 `status` 列
- 除 `csv-task-spec` 生成下游任务清单外，**禁止手写新建 CSV 文件**

### `expected_task_spec_outputs`
agenda_setter 生成下游 CSV 后，必须读取 `execution_contract.expected_task_spec_outputs` 中的 CSV 列表，确认每个文件真实存在且 header 为 `id,item,status`；缺失必须暴露为错误。

## `time_context.json` 的时间基准注入

`time_context.json` 与 `node_context.json` 并列，是 Agent 启动后必须首先读取的两个文件之一。它包含：

- 当前 run 的 UTC 时间戳（`now_iso_z()` 格式，来自 `common/runtime_files.py` 第41行）
- 选举相关的时间窗口基准
- 确保所有节点使用一致的时间参考（防止 Agent 使用自身系统时间导致不一致）

Prompt 中的引用（第392行）：

```
先阅读以下文件并严格按文件交接协议执行：
- `/workspace/current/meta/time_context.json`
- `/workspace/current/meta/node_context.json`
```

## `resource_hints.seed_paths` 和 `upstream_file_map` 的使用

### seed_paths

`resource_hints.seed_paths` 是在第4层 DAG 物化器阶段由资源搜索审计产出的已验证 `/public/` 绝对路径列表，最多6条（`MAX_RESOURCE_HINT_PATHS`）。

在 `resource_hints.py` 中：
- `extract_resource_seed_paths()`（第68-76行）从 `resource_audit["matchedPaths"]` 和 `resource_audit["deepExploration"]["matchedFiles"]` 提取
- `merge_seed_paths()`（第100-105行）支持合并多个来源的 seed_paths
- `build_resource_hint_payload()`（第29-52行）构建包含 `seed_paths`、`bootstrap_discovery_prefixes`、`copy_paths_verbatim` 等字段的 payload

注入到 prompt 时的要求（引自 prompt 文本第411-412行）：

```
若当前 node context 含有 resource_hints.seed_paths，把这些字符串视为
可直接复制的候选绝对路径；引用时必须逐字复制，不得重新拼接目录段。

若工具结果里已经出现完整 /public/... 路径或 absolute_path 字段，
优先直接把该值原样传给下一次读取工具，不要手打相似文件名。
```

### upstream_file_map

`upstream_file_map` 是上游节点的输出文件绝对路径索引表，存储在上游节点的 `node_context.json` 中。当前节点读取上游文件时必须：

1. 从 prompt 上方的上游摘要中获取索引表中的绝对路径
2. **原样复制**索引表中的路径传给 `Read()`
3. 严禁按 `/workspace/upstream/<id>/output/...` 模板自行拼接猜测路径

Prompt 中对应的约束（第413行）：

```
上游交接摘要与上游产出文件索引表已在本 prompt 上方给出；
读取上游文件时必须原样复制索引表中的绝对路径，禁止自行拼接或猜测路径
（包括禁止按 /workspace/upstream/<id>/output/... 模板盲猜未验证路径）。
```

## `REPORT_FINAL_NODES` 和 `REPORT_CHAIN_VISUAL_NODES` 的最终输出定义

定义于 `launcher_prompt.py` 第18-19行：

```python
REPORT_FINAL_NODES = {"report_generator", "report_reviewer_and_polisher"}
REPORT_CHAIN_VISUAL_NODES = {"html_report_builder", "election_visualizer"}
```

这些集合在 `report_chain_prompt_block()`（第299-337行）中用于匹配当前节点的 skill_id，注入对应的报告链专项约束。

### REPORT_FINAL_NODES 约束

**`report_generator`**（13条）：
- 职责：生成可交给终审节点的正式初稿，不要为了追逐终稿级字数而在本节点反复自循环
- 内容要求：每个一级章节至少有一个 `判断 -> 证据 -> 机制 -> 含义` 的长自然段
- `output/evidence_map.json` 必须区分 `fact` / `inference` / `scenario`，写明 `confidence` 与 `source_paths`
- 图表要求：优先补 1-4 张支撑性 PNG 图表到 `output/figures/`，写出 `chart_manifest.json`
- 标题编号统一：一级 `一二三`，二级 `（一）（二）（三）`，三级 `①②③`
- 正文至少保留 2 张 Markdown pipe table
- 附录拆为 A/B/C，分别保留风险矩阵、来源清单和工件索引表

**`report_reviewer_and_polisher`**（9条）：
- 必须读上游 `report.md`、`evidence_map.json` 及 HTML/manifest
- `review_report.json` 中只保留"章节位置 + 问题/修复动作"短摘要，不逐段引用原文
- 润色遵循 **Improve, Don't Replace**：保留已验证结论与有效结构
- 不得删除已有图表引用；若上游已有图表而正文未引用，优先补入
- 终稿必须补足 `事实 -> 推论 -> 含义` 链条
- 如果终稿有效行数低于上游初稿的 80%，必须在 `review_report.json` 记录删除理由
- 附录 A/B/C 任一部分缺少表格必须补齐

### REPORT_CHAIN_VISUAL_NODES 约束

适用于 `html_report_builder` 和 `election_visualizer`（3条）：
- 产物被下游终审节点消费；标题、关键数字、候选人名单与主报告保持一致
- `report.html` / `visualization.html` 只呈现已验证结论，不得新增未在主报告或上游证据中出现的数字
- 若补生成 fallback 图表，PNG 写到 `output/figures/`，并写出 `chart_manifest.json` 或 `figures/index.json`

## 业务文件写入纪律（收尾）

Prompt 末尾的强制约束（第428-434行）：

```
- 业务输出只能写入当前 node-local output/
- 严禁把业务文件写到 /workspace/upstream/**、/public/** 或任何 /workspace/current/output 之外的位置
- 除非当前节点 required outputs 明确要求，否则不需要额外补 output/result.json
- 写完约定业务文件后，最多只做一次轻量核对（例如 ls output 或读取前几行确认文件存在）；
  不要反复 cat、grep、head 自己刚写出的 output 文件
- 不要把待执行的工具调用写成 <tool_call>、XML、伪代码或叙述；需要工具就直接调用
- 在没有写出约定 output 文件前，不得以 success/completed 结束当前节点
```

这些收尾规则确保：
1. **写入隔离**：节点不能写脏上游或公共只读区
2. **交付验收**：以具名业务文件为完成标准，不是以空目录或协议骨架冒充
3. **效率预算**：限制自我核对次数，防止 Agent 在交付后浪费推理资源
4. **行为实效**：禁止用自然语言描述工具调用代替真正执行
