# 03 - 作用域约束

Launcher Prompt 中定义了一套完整的 SCOPE_LINES 体系，用于将模糊的 LLM 行为约束为确定性的、可验收的节点执行。所有约束以 Python 字符串元组（`tuple[str, ...]`）形式定义在 `orchestrator/dag/launcher_prompt.py` 中，由 `build_node_prompt()` 按条件选择性注入。

## SCOPE_LINES 体系总览

| SCOPE_LINES 常量 | 定义位置 | 触发条件 | 约束对象 |
|---|---|---|---|
| `AGENDA_SETTER_SCOPE_LINES` | 第59-69行 | `skill == "agenda_setter"` | 范围界定节点 |
| `CANDIDATE_REGISTRY_SCOPE_LINES` | 第70-76行 | `skill == "candidate_registry_searcher"` | 候选人核验节点 |
| `TASK_SCOPE_LINES` | 第30-35行 | 所有节点（始终注入） | 通用任务范围 |
| `EXECUTION_AUTHORITY_LINES` | 第77-81行 | 所有节点（始终注入） | 控制权优先级 |
| `PUBLIC_DATA_PROTOCOL_LINES` | 第20-27行 | 非 agenda_setter 节点 | 公共数据读取 |
| `LOCAL_ONLY_READ_PROTOCOL_LINES` | 第55-58行 | 非 agenda_setter 且无 knowledge MCP | 纯本地读取 |
| `TOOL_SEARCH_LINES` | 第45-54行 | 所有节点（始终注入） | 工具调用纪律 |
| `READ_PROTOCOL_LINES` | 第36-44行 | 非 agenda_setter（有 knowledge MCP 时） | 数据读取协议 |

## AGENDA_SETTER_SCOPE_LINES（范围界定节点约束）

定义于 `launcher_prompt.py` 第59-69行，共9条。触发条件：`agenda_setter_scope_prompt_block(skill)` 检查 `skill == "agenda_setter"`。

核心约束分类：

### 职责边界
- **起点节点限定**：只负责范围界定、候选人口径、下游分工与输出规格，不是完成最终事实核验或整篇报告
- **立即结束原则**：完成范围收敛和下游 CSV 生成核对后必须立即结束；不升级成资料发现节点

### 下游 CSV 生成规范
- 必须调用 `Skill(csv-task-spec)` fork 生成下游 CSV
- `csv-task-spec` 是零上下文 haiku subagent，不具备选举知识，只做机械 CSV 写入
- 禁止在 agenda_setter 主上下文中直接手写下游 CSV
- 每个下游 CSV 包含 2-5 条可验收任务项，从下游节点的 `label`、`description` 与 `required_outputs` 推导
- 生成后必须读取 `execution_contract.expected_task_spec_outputs` 中的 CSV 并确认真实存在

### 禁止行为
- 禁止读取超大候选人总表（如 `candidates/all.json`）
- 禁止大范围人名穷举
- 不得改写 `_todo.csv` 的 header 或自造 schema
- 不得将 `downstream_nodes` 中的真实 node_id 改写成抽象职责名

## CANDIDATE_REGISTRY_SCOPE_LINES（候选人核验节点约束）

定义于第70-76行，共5条。触发条件：`candidate_registry_scope_prompt_block(skill)` 检查 `skill == "candidate_registry_searcher"`。

### 事实边界
- **上游 progress CSV 摘要为事实边界**：不扩展到未点名县市/选区/政党
- 若 agenda/framework 只给出候选人口径与潜在名单，就把这些名字当作第一轮事实边界

### 搜索限制
- 每位候选人最多执行**一轮精确搜索 + 1-3 个文件读取**，不升级成全国性人海补搜
- 禁止把 `/public/candidates` 做成人海穷举
- 只允许基于已验证 seed path、上游已确认路径或精确关键词 `Glob`/`Grep` 后读取必要文件

### 终止条件
- 若第一轮精确核验后仍有字段缺失，必须标记为 `证据不足` 或 `未见最新记录`
- 立即写出 `output/candidate_registry_report.md`，不得为了补齐所有字段继续无限检索

## TASK_SCOPE_LINES（通用任务范围约束）

定义于第30-35行，共4条。对所有节点始终注入（`task_scope_prompt_block()` 无条件调用）。

```
- 任务范围以本 prompt 的"任务"描述、meta/node_context.json.execution_contract
  与已验证上游产物为准；upstream_inputs 摘要只是范围索引，不得自行扩展分析对象、
  行政区、选区层级或时间窗口。

- 如果任务写的是某个单一选区或对象（例如"2026 台北市长选举"），就只能围绕
  该对象执行；禁止顺手扩展到其他县市、六都或全国盘点。

- 对单一县市/单一对象任务，外县市或外对象材料只能作为次级背景；拿到主体证据后
  不得继续为了"补背景"穷举同类文件。

- 不要为了"验证相邻文件名"或"快速看一眼目录"而对 /public 写 Bash 探测脚本；
  路径发现使用 knowledge MCP、Glob、Grep、Read 或上游已验证路径。
```

## EXECUTION_AUTHORITY_LINES（执行权威层级）

定义于第77-81行，共4条。对所有节点始终注入（`execution_authority_prompt_block()` 无条件调用）。

控制权顺序（高到低）固定为：

1. **当前 `任务` 描述** —— 最高权威
2. **`meta/node_context.json.execution_contract`** —— 运行时合约
3. **`upstream_inputs` 摘要 / 已验证上游产物 / 共享工作区事实**
4. **project skill 文档** —— 最低权威

关键设计意图：
- Project skill 文档是方法库与检查表，不是当前节点的默认身份目标
- 若 skill 文档的默认目标、示例语气或历史习惯与当前任务冲突，必须忽略 skill 默认目标
- 防止 skill 文档中自带的"常规职责"覆盖掉特定任务的具名要求

## PUBLIC_DATA_PROTOCOL_LINES（公共数据读取协议）

定义于第20-27行，共6条。对非 agenda_setter 节点注入。由 `public_data_prompt_block()` 控制：

- 当 knowledge MCP 启用时，前缀为 `PUBLIC_DATA_KNOWLEDGE_NOTE`（"优先用 knowledge MCP 定位语义线索"）
- 当 knowledge MCP 未启用时，前缀为 `PUBLIC_DATA_LOCAL_ONLY_NOTE`（"不要调用 WebSearch/WebFetch 代替内部数据"）

核心规则：

| 规则 | 内容 |
|------|------|
| 读取边界 | 内部 `/public` 是只读文件树；容器挂载成功就是读取边界 |
| 定位方法 | 未知资料用 knowledge MCP 语义定位 → Glob/Grep 收敛 → Read |
| 已知路径 | 直接 `Read(file_path="...")`；不要手写相似文件名 |
| 目录分层 | 结构化 seed path → `03_清洗后数据/`；原始记录 → `01_选举结果数据/`；民调 → `02_民调数据/文本资料/` |
| 大文件 | 用 `offset`/`limit` 分段，不要用 Bash 脚本绕过 |

## LOCAL_ONLY_READ_PROTOCOL_LINES（纯本地数据读取协议）

定义于第55-58行。通过 `*READ_PROTOCOL_LINES[1:]` 语法从完整版 `READ_PROTOCOL_LINES` 删除第0条（"2. `/public` 是只读文件树" 从第0条变成 `LOCAL_ONLY` 版的第1条，因为原本的 READ 协议第0条是 MCP 相关引用被剔除）。

实质内容与 `READ_PROTOCOL_LINES` 的第1-6条相同，但去掉了任何 knowledge MCP 的引用。

## TOOL_SEARCH_LINES（工具调用纪律）

定义于第45-54行，共7条。对所有节点始终注入。

核心约束链：

```
init 暴露的工具 → prompt 渲染的 MCP 别名 → ToolSearch → 直接调用
```

1. **工具真值来源顺序**：`init` 暴露 > prompt MCP 别名 > `ToolSearch`
2. **ToolSearch 非预热步骤**：已知确切别名/签名时直接调用目标工具
3. **避免猜名**：不拼 `mcp__<provider>__*` 变体，不逐名试错
4. **搜到即用**：`ToolSearch` 返回 `tool_reference` 后同一轮立即调用
5. **参数名纪律**：`Read` 必须传 `file_path`，`Write` 必须传 `file_path` + `content`
6. **Agent 工具**：只在局部、可摘要、隔离性强的侧向工作上使用；不把主流程交给子代理
7. **序列化纪律**：`Write.content` 必须是字符串；写 JSON 时先 `json.dumps()`

## discovery_policy.py 的搜索触发策略

`orchestrator/dag/discovery_policy.py` 定义了两套 MCP（Model Context Protocol）工具的激活判断逻辑，决定哪些节点能使用 knowledge MCP 和 web search MCP。

### Knowledge MCP 触发规则

`default_knowledge_trigger_node()`（第64-69行）判断节点是否应挂载知识库 MCP：

1. **白名单 skill_id**：`KNOWLEDGE_HEAVY_SKILL_IDS`（第9-17行）
   - `agenda_setter`
   - `evidence_synthesizer`
   - `history_data_collector`
   - `library_context_retriever`
   - `polls_collector`

2. **Archetype 匹配**：`KNOWLEDGE_HEAVY_ARCHETYPES`（第18行）
   - `scope_anchor`
   - `data_scout`
   - `evidence_collector`

匹配优先级：先检查 skill_id 白名单，再通过 `node_block_profile()` 检查节点 block_profile 中的 `archetype` 字段。

### Web Search MCP 触发规则

`default_search_trigger_node()`（第72-77行）判断节点是否应挂载网络搜索 MCP：

1. **白名单 skill_id**：`WEB_SEARCH_TRIGGER_SKILL_IDS`（第19-23行）
   - `candidate_registry_searcher`
   - `realtime_status_researcher`

2. **Archetype 匹配**：
   - `realtime_research`
   - `candidate_tracking`

### 配置覆盖

在 `launcher_prompt.py` 中，`is_search_trigger_node()`（第154-161行）和 `is_knowledge_trigger_node()`（第164-171行）提供配置级别的覆盖：

- `node.agent_config.external_search` → 直接返回 True/False
- `node.agent_config.requires_knowledge_search` → 直接返回 True/False
- `trigger_node_types` 配置列表 → 按 node_id 或 skill 精确匹配
- 配置未设置或列表为空 → 回退到 `default_*_trigger_node()` 的启发式判断

### 向后兼容别名

`DISCOVERY_HEAVY_SKILL_IDS` 和 `DISCOVERY_HEAVY_ARCHETYPES`（第27-28行）是旧命名的别名，指向同名的新常量，用于保证旧代码和测试的兼容性。
