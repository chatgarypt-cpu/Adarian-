# 01 概述：Planning Agent 在流水线中的位置与数据流

## 1. 系统入口：用户消息如何进入

用户在前端发送消息后，请求到达 FastAPI 后端，最终由 `orchestrator/chat/planning_api.py` 中的 `stream_generate_workflow_response()` 函数处理。该函数是第 0 层的核心调度函数，负责整个规划阶段的 SSE（Server-Sent Events）流式输出。

调用入口位于 `chat_api.py` 的 `/chat/send` 端点。函数签名如下：

```python
async def stream_generate_workflow_response(
    runtime: PlanningRuntime,
    ctx: MessageRequestContext,
    state: MessageStreamState,
) -> AsyncGenerator[str, None]:
```

该函数接收三个核心参数：
- **`runtime: PlanningRuntime`** -- 封装了存储层、编排引擎、Planning Agent 适配器、日志器等全部依赖。
- **`ctx: MessageRequestContext`** -- 请求上下文，包含原始请求 `req`、session ID、消息内容、plan mode 开关状态等。
- **`state: MessageStreamState`** -- 流式输出的会话状态追踪器，负责累积 reasoning 文本和 timing 记录。

## 2. Planning Agent 在整个流水线中的位置

Planning Agent 是流水线的**最前端入口**，而不是执行者。它在整个系统中的定位是：

> **意图解析与规划决策层** -- 理解用户输入、评估信息充分性、决定是否进入 DAG 生成。

Planning Agent 位于第 0 层，负责处理管道的前三个阶段：

1. **资源审计 (Resource Audit)** -- 对本地数据目录做 metadata 级别的预检，识别数据覆盖范围和缺口。
2. **信息充分性评估 (Information Sufficiency)** -- 基于用户已提供的信息和 Planning Gear 档位，评估是否足以生成 DAG。
3. **多轮决策 (Round Policy)** -- 根据当前轮次、force_execute 标志、Planning Gear 等，决定本轮为 `ask` 还是 `ready`。

下游的第 1 层（DAG 生成与验证）仅在 Planning Agent 返回 `ready` 时才会被触发。

## 3. 三种输出状态

Planning Agent 的最终输出由 `orchestrator/chat/planning_contract.py` 中的 `PlanningAgentResult` 定义：

```python
@dataclass
class PlanningAgentResult:
    status: Literal["ask", "ready", "chat"]
    ...
```

三种状态的含义：

| 状态 | 语义 | 触发条件 | 下游行为 |
|------|------|----------|----------|
| **`chat`** | 纯对话回复 | 用户输入为解释/讨论/顾问式问题，无需生成工作流 | 直接返回 `assistantReply` 文本，不进入 DAG 流程 |
| **`ask`** | 需要澄清 | 信息不足以生成 DAG，或尚未达到最低轮数 | 返回 `questions` 列表，前端展示澄清表单，等待用户回复 |
| **`ready`** | 可以生成 DAG | 信息充分，或达到最大轮数，或 force_execute 激活 | 进入 DAG 生成流程 (`generate_dag`)，输出 `WorkflowPlan` |

## 4. 关键数据流

以下按时间顺序描述一次用户请求的完整数据流：

### 4.1 用户消息进入

用户消息通过 `ChatMessage` 到达 `stream_generate_workflow_response()`。函数首先从 `MessageRequestContext` 中提取：
- `content_for_planning` -- 规划模式下的格式化用户输入
- `force_execute` -- 强制生成标志
- `plan_mode_enabled` -- Plan Mode 开关

### 4.2 配置解析与能力评估

```python
planning_richness = _effective_request_planning_richness(...)
mcp_capabilities = build_planning_capabilities(...)
```

`planning_richness` 决定规划档位（standard / detailed / comprehensive）。`mcp_capabilities` 评估外部数据（搜索 MCP、知识库 MCP）的可用性。

### 4.3 资源审计 (Resource Audit)

系统调用 `runtime.audit_resources()`，对 public/ 数据目录做 **metadata 预检**，不读取正文。审计结果包含：
- 本地数据覆盖率（`localDataStatus.coverage`）
- 匹配路径列表（`matchedPaths`）
- 外部数据状态

审计过程通过 SSE 输出 `tool.start` / `tool.end` 事件，前端可实时展示。

> 注意：resource audit 只是 metadata 预审，不等于真实检索。实际检索由 Planning Agent 内的 Skill（如 `search` MCP）在执行规划时完成。

### 4.4 信息充分性评估

`orchestrator/chat/planning/sufficiency.py` 中的 `evaluate_information_sufficiency()` 根据以下要素评估信息是否充分：

- 用户已回答的关键维度数量（`answer_lookup`）
- 当前 Planning Gear 对应的最低答案数阈值（standard=2, detailed=4, deep=5）
- 焦点上下文（`focus_context`）

输出为 `InformationSufficiency` 实例，包含 `is_sufficient` 标志和 `rationale` 说明。

### 4.5 多轮决策

`orchestrator/chat/planning_round_policy.py` 中的 `build_planning_round_policy()` 综合以下因素决定本轮策略：

- 当前轮数 vs. 最大轮数（按 Gear 档位：standard=2, detailed=3, deep=4）
- `force_execute` 标志 -- 直接强制 ready
- 信息充分性 -- 信息充分且达到最低轮数时自动转为 ready
- `use_plan_mode` -- Plan Mode 关闭时直接走直接回复

输出为 `PlanningRoundPolicy`，核心字段：
- `require_ready: bool` -- 是否需要强制生成 DAG
- `should_continue_asking: bool` -- 是否应继续澄清
- `gear: PlanningGear` -- 当前规划档位
- `reason: str | None` -- 决策原因（如 `max_rounds_reached`）

### 4.6 Planning Agent 调用

最终，系统构造 `PlanningAgentConfig` 并调用 `run_planning_agent()`：

```python
async for planning_update in runtime.run_planning_agent(
    router=planning_agent_adapter,
    user_input=planning_user_input,
    conversation=convo,
    resource_audit=resource_audit,
    mcp_capabilities=planning_mcp_capabilities,
    planning_richness=planning_richness,
    target_mode=target_mode,
    require_ready=round_policy.require_ready,
    config=agent_config,
    ...
):
```

Planning Agent 内部通过 Claude Agent SDK 启动一次性 session，限定只能调用 `chat-planner-guide` 和 `dag-planner` 两个 Skill，禁止所有文件/Shell/Web 工具。

## 5. PlanningRuntime dataclass

`orchestrator/chat/planning_api.py` 中定义的 `PlanningRuntime` 是依赖注入的载体：

```python
@dataclass(frozen=True)
class PlanningRuntime:
    storage: Any                    # 消息和状态存储（Redis/内存）
    orchestration_engine: Any       # 编排引擎（超时、LLM 网关等配置来源）
    planning_agent_adapter: Any     # PlanningAgentAdapter -- Skill 快照/对话压缩/结果构建
    logger: logging.Logger          # 结构化日志
    admin_config_store: Any | None  # 管理员配置（MCP provider 等）
    audit_resources: Any            # 资源审计函数引用
    format_resource_audit_tool_result: Any  # 审计结果格式化函数
    normalize_workflow_payload: Any # DAG 规范化函数
    data_accessor: Any | None       # 数据访问层
    run_planning_agent: Any         # run_planning_agent 函数引用
```

## 7. 关键源文件索引

| 文件 | 职责 |
|------|------|
| `orchestrator/chat/planning_api.py` | 顶层调度：`stream_generate_workflow_response()`，三种分支处理 |
| `orchestrator/chat/planning_agent.py` | Planning Agent SDK session 管理与多轮修复 |
| `orchestrator/chat/planning_contract.py` | 数据契约：`PlanningAgentResult`、`PlanningDecisionPayload` |
| `orchestrator/chat/planning_round_policy.py` | 多轮决策：`PlanningRoundPolicy`、`InformationSufficiency`、`PlanningGear` |
| `orchestrator/chat/planning_intent.py` | 用户意图文本构造（deliverable 承上启下逻辑） |
| `orchestrator/chat/planning_modes.py` | 超时与模型配置：按 richness 分档的 timeout 策略 |
| `orchestrator/chat/planning_agent_adapter.py` | `PlanningAgentAdapter`：Skill 快照、对话压缩、repair prompt 构建 |
| `orchestrator/chat/planning/sufficiency.py` | 信息充分性评估 |
| `orchestrator/chat/planning/request_pipeline.py` | `PlanningAgentConfig` 构造、MCP 配置解析 |
| `orchestrator/chat/planning_response.py` | SSE 响应构造（`build_ready_response_content` 等） |
| `orchestrator/chat/planning_repair.py` | 校验失败时的 repair prompt 构造 |
