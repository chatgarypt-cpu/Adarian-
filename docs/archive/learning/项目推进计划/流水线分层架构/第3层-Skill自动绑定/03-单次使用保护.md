# 03 - 单次使用保护（Single-Use Protection）

## 概述

某些 skill 被设计为**在一个 WorkflowPlan 中只能出现一次**——这类 skill 代表不可扇出（fan-out）的专项能力，重复使用会引入冗余计算和语义冲突。Auto-Binder 通过 `blockProfile.canFanOut` 字段识别这类 skill，并对重复绑定实施**自动降级保护**。

## `blockProfile` 结构

每个 skill 在 `skills_registry.yaml` 中可声明 `block_profile` 字段（经 `common/skills_registry.py` 的 `_normalized_block_profile()` 方法规范化为 camelCase `blockProfile`）。完整结构如下：

| 字段 | 类型 | 说明 |
|------|------|------|
| `canFanOut` | `bool` | 是否允许多实例并行（`true` = 可以扇出多个副本，`false` = 单次使用） |
| `canConverge` | `bool` | 是否可以作为汇聚节点（接收多条上游边的输入） |
| `stage` | `str` | DAG 阶段标签：`entry`、`evidence`、`synthesis`、`deepening`、`verification`、`output`、`review` |
| `archetype` | `str` | 结构原型：`scope_anchor`、`data_scout`、`evidence_collector`、`data_transformer`、`thematic_deepener`、`scenario_branch`、`synthesis_hub`、`cross_validator`、`output_drafter`、`quality_gate` |
| `preferredPredecessors` | `list[str]` | 偏好的上游阶段列表 |
| `preferredSuccessors` | `list[str]` | 偏好的下游阶段列表 |
| `preferredRecipes` | `list[str]` | 推荐的 DAG 模式（如 `layered_diamond`、`waterfall_chain`） |

## `canFanOut` 与 `_is_single_use_skill()`

**代码位置**：`skill_auto_binder.py` 第 181-183 行

```python
def _is_single_use_skill(skill_id: str, *, skills: dict[str, dict]) -> bool:
    block_profile = (_skill_entry(skills=skills, skill_id=skill_id) or {}).get("blockProfile") or {}
    return block_profile.get("canFanOut") is False
```

**判断逻辑**：

1. 从 `skills` 字典查找 `skill_id` 对应的 skill 条目
2. 提取 `blockProfile` 字段（不存在时默认为空 dict）
3. 返回 `blockProfile.get("canFanOut") is False`

**关键语义**：

- `canFanOut: true` 或 `canFanOut` 字段缺失 → `_is_single_use_skill()` 返回 `False`（允许多实例）
- 只有显式设置 `canFanOut: false` → 返回 `True`（单次使用）

这意味着**默认情况下所有 skill 允许多实例**，只有显式标记 `can_fan_out: false` 的 skill 才受 single-use 保护。

## 保护机制详解

**核心逻辑**：`_auto_bind_node()`（`skill_auto_binder.py` 第 96-107 行）

```python
def _auto_bind_node(*, node, used_single_use, skills):
    if not _is_executable_agent(node):
        return node
    candidate = _candidate_skill_id(node, skills=skills)
    if not candidate:
        return node
    if not _is_single_use_skill(candidate, skills=skills):
        return _bind_node(node, skill_id=candidate)
    if candidate in used_single_use:
        return _genericize_node(node)
    used_single_use.add(candidate)
    return _bind_node(node, skill_id=candidate)
```

**保护流程**：

```
  候选 skill_id 确定后
         │
         v
  _is_single_use_skill(candidate)?
         │
     yes │              no
         v                v
  candidate in         _bind_node() 直接绑定
  used_single_use?     （无需保护）
    │yes       │no
    v          v
 _genericize  used_single_use.add(candidate)
 _node()      _bind_node() 首次绑定
```

**执行细节**：

1. **追踪状态**：`used_single_use: set[str]` 在 `auto_bind_workflow_plan_skills()` 的入口初始化（第 68 行），在整个 plan 的 node 遍历中共享（第 69 行 `for node in plan.nodes`）。

2. **绑定顺序**：按照 `plan.nodes` 的原始遍历顺序依次处理——**第一个**绑定到某 single_use skill 的 node 获得该 skill，**后续**同名 node 被降级。

3. **非 single_use skill**：`_is_single_use_skill()` 返回 `False` 时，直接调用 `_bind_node()`，不做 any 记录。

## `_genericize_node()` —— 降级为通用 Node

**代码位置**：`skill_auto_binder.py` 第 196-205 行

```python
def _genericize_node(node: WorkflowPlanNode) -> WorkflowPlanNode:
    description = str(node.description or "").strip() or str(node.label or "").strip() or None
    if (
        not str(node.skill_id or "").strip()
        and not str(node.skill or "").strip()
        and not list(getattr(node, "skills", []) or [])
        and description == node.description
    ):
        return node
    return node.model_copy(update={"skill_id": None, "skill": None, "skills": [], "description": description})
```

**降级行为**：

1. **description 兜底**：若 node 有 `description`，保留原值；若无 description，使用 `label` 作为 description。
2. **清空 skill 引用**：`skill_id → None`、`skill → None`、`skills → []`。
3. **不修改 id/label/kind/enabled/critical**：node 的其他身份字段保持不变。
4. **不可变性检查**：若 node 已经是 generic 状态（所有 skill 字段为空），直接返回原对象。

降级后的 node 在 Materializer 中会被赋予 `"__generic__"` skill，成为一个通用 agent 节点。通用 agent 使用容器内的默认 Claude Code 行为，不加载特定 SKILL.md，仅执行系统 prompts 和基本工具权限。

## 实际案例

### 案例 1：两个 realtime_status_researcher

**来源**：`test_workflow_payload_validation.py` 第 239-268 行

```python
# Planning Agent 生成了两个绑定到 realtime_status_researcher 的 node
nodes = [
    WorkflowPlanNode(id="candidate_tracker", skill_id="realtime_status_researcher",
                     description="追踪候选人公开表态、参选动作与联盟变动。"),
    WorkflowPlanNode(id="news_monitor", skill_id="realtime_status_researcher",
                     description="追踪选举相关最新新闻、突发事件与舆情影响。"),
]
```

`realtime_status_researcher` 的 `canFanOut` 为 `false`（单次使用）。

**Auto-Binder 处理结果**：

| node | 处理 | 最终 skill |
|------|------|-----------|
| `candidate_tracker` | 第一个，used_single_use 为空，正常绑定 | `realtime_status_researcher` |
| `news_monitor` | 第二个，`realtime_status_researcher` 已在 used_single_use 中，降级 | `__generic__`（description 保留为"追踪选举相关最新新闻、突发事件与舆情影响。"） |

### 案例 2：有 label 无 description

第二个节点 `news_monitor` 没有 `description` 但有 `label="实时新闻与事件监控"`。

**降级后**：`description` 被设置为 `"实时新闻与事件监控"`（从 label fallback），skill 为 `"__generic__"`。

## `blockProfile` 的其他字段在流水线中的用途

虽然 `_is_single_use_skill()` 只检查 `canFanOut`，但 `blockProfile` 的其他字段在 Materializer 阶段被使用：

- **`stage`**：Materializer 使用 `stage` 字段进行 DAG 分层（layer），相同 `stage` 的 node 被分配到同一 layer
- **`preferredPredecessors` / `preferredSuccessors`**：`validate_plan_dag()` 中使用这些字段进行拓扑校验——检查 fan-in/fan-out 是否合理，以及 skill 是否被放在合适的 DAG 位置
- **`archetype`**：`validate_plan_dag()` 中的 `_validate_required_predecessor_presence()` 使用 archetype 信息验证节点是否有必要的前驱

## 设计约束与注意事项

1. **Single-use 仅影响绑定，不影响 scheduling**：DAG 中可以有多个 `__generic__` node，它们在拓扑上仍然是独立节点可以并行执行。

2. **语义不变性**：降级操作保证 node 在 DAG 中的位置（id、edges）不变，只有 skill binding 被改变。下游节点对降级 node 的依赖关系完全不受影响。

3. **顺序敏感性**：绑定顺序由 `plan.nodes` 列表顺序决定。Planning Agent 可以通过调整 node 在 JSON 数组中的顺序来影响哪个 node 获得 single_use skill。

4. **Layer 1 显式绑定的优先性**：如果 Planning Agent 在 Layer 1 显式指定了 `skill_id`，即使该 skill 是 single-use 的也会被接受（如果是第二个则被降级）。但如果通过 Layer 2 或 Layer 3 自动匹配得到同一个 single_use skill，同样的保护机制生效。
