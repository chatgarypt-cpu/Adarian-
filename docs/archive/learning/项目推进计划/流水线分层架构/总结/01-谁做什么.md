## 逐层详细说明

### Layer 0：规划代理与意图路由

**执行者做什么**：Planning Agent 是整个流水线的第一道门。它接收用户的原始输入，结合对话历史和资源审计结果，判断用户的意图是闲聊（`chat`）、信息不足需要澄清（`ask`），还是已经可以直接开工（`ready`）。这个判断由一个 Claude SDK 驱动的 agent 完成，它拥有调用 Skill 和 MCP 工具的能力，可以在规划阶段就提前探查系统状态（例如检查数据文件是否存在、确认选举年份范围等），确保进入 DAG 生成之前信息是充分的。

**模型选择**：使用 `WORKFLOW_GEN_MODEL`——这是系统配置中专门用于工作流规划场景的模型，通常选型为具有强推理能力的高容量模型（如 Opus 系列），因为意图判断和任务分解是整个流水线的根基，这里的错误会向下逐层放大。

**输入详情**：
- **用户消息**：前端 Chat UI 中的原始文本输入（如"分析 2026 台北市长选举"）。
- **对话历史**：当前 session 的完整历史消息列表，用于多轮澄清上下文。
- **资源审计（resource_audit）**：在规划前扫描 `public/` 数据目录，生成可用数据文件、年份范围、选举类型等结构化审计报告，作为 Planning Agent 的 system prompt 上下文的组成部分。

**输出详情**：`PlanningAgentResult` 是一个枚举结构，包含三种状态：
- `chat`：纯闲聊，不走 DAG，直接由 Planning Agent 回复。
- `ask`：信息不足，生成澄清问题返回用户，等待下一轮回复。
- `ready`：信息充分，携带提取出的意图结构（包含选举年份、选举类型、分析维度等），传递给 Layer 1。

**核心文件路径**：`orchestrator/chat/planning_agent.py`（SDK 会话管理）、`orchestrator/chat/planning_api.py`（`stream_generate_workflow_response` 入口函数）、`orchestrator/chat/planning_round_policy.py`（多轮澄清决策策略）、`orchestrator/chat/utils.py`（资源审计等辅助函数）。

### Layer 1：规划器 — DAG 拓扑生成

**执行者做什么**：`OrchestrationEngine` 拿到 `ready` 状态的 `PlanningAgentResult` 后，组装一个巨大的 system prompt（七层组装：角色定义 → Skill 目录摘要 → 策略模板 → 输出格式约束 → 可用数据摘要 → 规划启发式 → 用户任务），调用 LLM 生成一个结构化的 `WorkflowPlan`。该 Plan 描述了要运行哪些节点（nodes）、节点之间依赖关系（edges）、每个节点的任务描述和期望输出类型。

**模型选择**：同样使用 `WORKFLOW_GEN_MODEL`。与 Layer 0 的区别在于，这里对结构化输出的一致性要求极高——模型必须严格按照 `WorkflowPlan` 的 JSON schema 输出，否则 Layer 2 的编译阶段会失败。

**输入详情**：
- `PlanningAgentResult`：Layer 0 输出的意图结构，包含具体任务描述和资源约束。
- Skill 注册表：35+ 个可用 Skill 的功能摘要表，每个 Skill 包含名称、描述、`single_use` 标记、`canFanOut` 标记。
- Recipe 模板：`planning_strategies.py` 中定义的策略模板，引导 LLM 对不同类型任务（选举模拟、数据查询、报告生成）采用不同的节点分解模式。

**输出详情**：`WorkflowPlan` 是一个 Pydantic 模型，包含：
- `nodes: list[WorkflowPlanNode]`：每个节点有 `node_id`、`task`（自然语言描述）、`expected_output_type`（`csv` / `text` / `json` / `report_md`）、`allowed_mode`（`open` 或 `restricted`）。
- `edges: list[WorkflowPlanEdge]`：描述节点间的依赖关系（`from_node` → `to_node`）。

**核心文件路径**：`orchestrator/dag/engine.py`（`OrchestrationEngine` 主入口）、`orchestrator/dag/plan_generator.py`（`generate_planner_sdk()` / `generate_llm()` 双通道生成）、`orchestrator/dag/engine_prompts.py`（七层 Prompt 组装）。

---

### Layer 2：修复与验证循环

**执行者做什么**：LLM 的原始输出是文本字符串，其中嵌入了 JSON 片段。这一层负责把它变成可信任的结构化数据。流程是：`PlanCompiler` 提取 JSON → `PlanValidator` 做两层校验（Pydantic schema 校验 + 业务规则校验：无环检测、无孤立节点、边引用完整性、输出类型合法性） → 任何校验失败触发 `PlanRepairLoop`，将错误信息反馈给 LLM 要求修正，重试最多 N 次（由 `workflow_plan_repair_attempts` 配置控制）。

**模型**：确定性的代码逻辑，不调用 LLM。但 `PlanRepairLoop` 内部会重新调用 LLM（同样使用 `WORKFLOW_GEN_MODEL`）来修正上一轮的错误——这严格来说不是"计划生成"，而是"计划修复"。

**输入详情**：LLM 的原始文本响应（通常是一个包含 JSON 代码块的 markdown 字符串）。

**输出详情**：一个经过完整验证的 `WorkflowPlan` 对象——确保 JSON 结构正确、DAG 无环、所有引用合法、所有节点语义合理。

**核心文件路径**：`orchestrator/dag/plan_compiler.py`（JSON 提取与 Pydantic 构造）、`orchestrator/dag/plan_validator.py`（schema 校验 + 业务规则校验）、`orchestrator/dag/plan_repair_loop.py`（修复循环控制器）、`orchestrator/dag/workflow_validation.py`（辅助校验函数）。

---

### Layer 3：Skill 自动绑定

**执行者做什么**：`SkillAutoBinder` 遍历 `WorkflowPlan` 中所有 `allowed_mode="open"` 的节点，自动为其匹配合适的 `skill_id`。匹配采用四层优先级策略：（1）LLM 已在节点中显式指定了 `skill_id` → 直接使用；（2）节点 `task` 字段精确匹配 Skill 注册表中的技能名称 → 绑定；（3）节点 ID 包含双下划线前缀（如 `candidate_registry_searcher__xxx`）→ 按前缀匹配；（4）前三种都未命中 → 降级到 `_NODE_ID_SKILL_FALLBACKS` 关键词规则表（21 条中英文规则），用正则匹配。此外还会检查 `single_use` 约束——被标记为单次使用的 Skill 如果已被前面的节点绑定，后续同名匹配会降级为 `generic`。

**模型**：纯正则规则引擎，零 LLM 调用。原因：确定性、低延迟、零 token 成本。

**输入详情**：Layer 2 产出的已验证 `WorkflowPlan`。

**输出详情**：每个 node 的 `skill_id` 字段被填充了的 `WorkflowPlan`。未匹配到的节点 `skill_id` 保持为空，后续 Layer 4 会为其分配默认值。

**核心文件路径**：`orchestrator/dag/skill_auto_binder.py`（核心匹配逻辑）、`orchestrator/dag/skill_binding.py`（绑定数据结构）、`orchestrator/dag/types.py`（`SkillRegistry` 数据模型）。

---

### Layer 4：DAG 物化器

**执行者做什么**：`Materializer`（核心函数 `build_generated_dag()`）将 `WorkflowPlan` 编译为可供执行引擎直接消费的 `GeneratedDAG`。关键操作包括：（1）**拓扑排序**：用 Kahn 算法确定节点执行顺序；（2）**层级分配**：`assign_layers_orders()` 为每个节点分配 `layer_index`，控制并行度和调度批次；（3）**搜索子节点注入**：`_inject_search_sub_nodes()` 检测标记了 `external_search` 或 `knowledge_search` 需求的节点，在它们前面自动插入一个搜索子节点，并将父节点的描述和期望输出格式注入为搜索策略模板；（4）**agent_config 构建**：为每个节点组装 `agent_config`——包含模型配置、工具白名单、Skill bundle 路径等运行时参数。

**模型**：确定性编译，不调用 LLM。

**输入详情**：经过验证和 Skill 绑定的 `WorkflowPlan`。

**输出详情**：`GeneratedDAG` 是运行时可直接消费的数据结构，包含：
- `nodes: list[DAGNode]`：每个节点有完整的 `layer_index`、`skill_id`、`agent_config`、`upstream_nodes`。
- `entry_node_id` / `exit_node_id`：DAG 入口和出口。
- 搜索子节点（如果父节点有搜索需求，这里已内联展开）。

**核心文件路径**：`orchestrator/dag/workflow_materializer.py`（`build_generated_dag`、`_inject_search_sub_nodes`、`assign_layers_orders`）。

---

### Layer 5：启动提示词组装

**执行者做什么**：`LauncherPrompt` 为 `GeneratedDAG` 中的每个节点生成一份 `task_prompt.md`。组装顺序是七层叠加：（1）执行权威层级声明（`EXECUTION_AUTHORITY_LINES`）；（2）节点级作用域约束（`SCOPE_LINES`——每种节点类型有不同的行为边界，例如 `agenda_setter` 只负责设定模拟参数、不能替代 `candidate_registry_searcher` 做搜索）；（3）节点具体任务描述；（4）上游节点输出摘要；（5）期望输出格式与合约（`execution_contract` / `required_outputs`）；（6）工具调用纪律；（7）进度 CSV 写入规范。此外还会注入 `resource_hints`——即资源审计阶段获取的数据文件路径和结构提示。

**模型**：纯模板字符串拼接，不调用 LLM。

**输入详情**：`GeneratedDAG` + `resource_hints`（来自 Layer 0 的资源审计结果）。

**输出详情**：每个 DAG 节点对应一份 `task_prompt.md` 文件，写入执行工作区供 Agent SDK Session 读取。

**核心文件路径**：`orchestrator/dag/launcher_prompt.py`（`build_node_prompt()` 主函数）、`orchestrator/dag/resource_hints.py`（资源提示构建）。

---

### Layer 6：工作区同步

**执行者做什么**：`WorkspaceSync` 将宿主机的 `claude-runtime/` 目录通过 `shutil.copytree` 复制到容器的 `.claude/` 目录。这包括三个子目录的投影：（1）`claude-runtime/skills/` → `.claude/skills/`（所有 Skill 定义文件）；（2）`claude-runtime/agents/` → `.claude/agents/`（8 个 Subagent 角色定义）；（3）`claude-runtime/settings.json` → `.claude/settings.json`（Agent 共享配置）。同时执行 MCP 模板变量替换：将 `{{MCP_*}}` 占位符替换为运行时的实际 MCP 服务地址和凭据。

**模型**：确定性文件复制，不调用 LLM。

**输入详情**：宿主机上 `claude-runtime/` 目录的完整内容 + MCP 配置模板。

**输出详情**：容器内 `.claude/` 目录，结构完全符合 Claude Agent SDK 标准布局，Agent 进程启动后可直接读取。

**核心文件路径**：`orchestrator/agent/workspace_skills.py`（`sync_workspace_skills()`）、`common/claude_runtime_assets.py`（路径解析与常量定义）。

---

### Layer 7：Docker 容器启动

**执行者做什么**：`DAGScheduler` 负责协调节点的执行顺序，`Launcher`（在 `execute_api.py` 中）负责容器的实际生命周期管理。关键设计是**长生命周期容器复用**：不是每个节点启动一个新容器，而是启动一个容器后通过 `docker exec` 依次在其中执行多个 Agent Session，直到 DAG 完成或容器退出。两种执行模式：（1）**DAG 调度模式**：`execute_with_dag_scheduler()` 按拓扑顺序调度节点，`DAGScheduler` 管理批次并发；（2）**单 Agent 模式**：`execute_single_agent()` 跳过 DAG 直接执行简单任务，无节点调度开销。容器通过 `RunContainerMonitor` 监控健康状态和生命周期。

**模型**：Docker SDK（`docker-py`）操作，不调用 LLM。

**输入详情**：`GeneratedDAG` + 每节点的 `task_prompt.md` + 容器配置（镜像名称、网络名称、卷挂载路径）。

**输出详情**：一个运行中的 Docker 容器，内部已准备好工作区、Skill bundle、MCP 配置，等待 Layer 8 的 Agent SDK Session 接入。

**核心文件路径**：`orchestrator/chat/execute_api.py`（`execute_workflow()` 主入口）、`orchestrator/dag/scheduler.py`（`DAGScheduler` 调度逻辑）、`orchestrator/container_monitor.py`（`RunContainerMonitor` 生命周期监控）。

---

### Layer 8：Agent 会话执行

**执行者做什么**：这是系统的核心计算层。每个 DAG 节点在容器内独立启动一个 Agent SDK Session——入口是 `election_agent.py`，它初始化 Claude SDK 客户端，加载节点专属的 `task_prompt.md` 作为首个 user message，挂载完整的工具集（Read / Write / Edit / Bash / Skill / Agent / MCP），然后进入推理循环（`max_turns=300`）。Session 的 system prompt 由 `system_prompt.py` 注入时间基准、运行时约束（`runtime_required_outputs`）、Subagent 可见性（`runtime_custom_agent_visibility`）等信息。如果节点需要调用子任务，Agent 可以通过 `Skill` 工具或 `Agent` 工具（Subagent 委派）分派给 8 个预定义角色之一。每个节点的执行输出写入工作区：`result.json`（结构化结果）、`report.md`（自然语言报告）、`sdk_messages.jsonl`（完整会话记录）。

**模型**：节点级独立配置——不同节点可以使用不同模型。模型配置由 `GeneratedDAG` 的 `agent_config` 字段指定，在 Layer 4 物化阶段根据节点类型和 `skill_id` 分配（例如简单搜索节点可用性价比模型，复杂分析节点用高容量模型）。

**输入详情**：`task_prompt.md` + 完整工具清单（Read / Write / Edit / Bash / Skill / Agent / MCP） + Skill bundle + `node_context.json`（上游节点的输出路径和摘要）。

**输出详情**：每个节点产出三个文件：
- `result.json`：结构化执行结果，包含状态、数据、统计信息。
- `report.md`：人类可读的报告文本，供下游节点和最终报告使用。
- `sdk_messages.jsonl`：完整的 SDK 消息流日志，每行一个 JSON 对象，记录每一轮 user/assistant message、tool_use、tool_result。

**核心文件路径**：`agent/election_agent.py`（Agent 入口脚本）、`agent/sdk_session.py`（SDK Session 管理）、`agent/system_prompt.py`（系统提示词注入）、`agent/skill_bundle_loader.py`（Skill 加载器）、`agent/sdk_runtime_mcp.py`（运行时 MCP 配置挂载）、`agent/session_lifecycle.py`（会话生命周期钩子）、`agent/native_terminal_runner.py`（原生终端执行器）。

### Layer 9：事件流回传

**执行者做什么**：Agent Session 在执行过程中持续输出 `sdk_messages.jsonl`。`EventRecorder` 实时读取该文件，将 SDK 原始事件（`message_start`、`message_delta`、`tool_use`、`tool_result` 等）转化为统一的监控事件格式，推送到 Redis Streams。后端的 SSE endpoint（`/api/runs/{run_id}/events`）从 Redis Streams 消费事件并推送到前端。前端通过 `useChatStreaming.ts` hook 接收 SSE 流，解析事件类型，更新 `runEventStore`（Zustand store），最终驱动 ReactFlow 画布上的节点状态实时变化——已完成节点变绿、运行中节点闪烁、失败节点变红。SSE 连接支持通过 `Last-Event-ID` header 断线重连。

**模型**：事件管道，不调用 LLM。

**输入详情**：`sdk_messages.jsonl`（Agent Session 实时写入的会话日志）。

**输出详情**：SSE 事件流 → 前端 Zustand store → ReactFlow 实时渲染的 DAG 可视化。每种事件类型对应不同的 UI 更新：
- `message_start` / `message_delta`：节点状态更新和 token 流式显示。
- `tool_use` / `tool_result`：工具调用记录展示在运行详情面板。
- `node_complete`：ReactFlow 节点变绿。
- `node_error`：ReactFlow 节点变红，错误信息展示。

**核心文件路径**：`agent/event_recorder.py`（事件录制与 Redis 推送）、`orchestrator/routers/runs.py`（SSE endpoint）、`frontend/src/hooks/useChatStreaming.ts`（前端 SSE 消费）、`frontend/src/pages/` 中的 `runEventStore`（Zustand store）和 ReactFlow 组件。

## 模型使用总览

| Layer | 是否使用 LLM | 模型名称 | 备注 |
|-------|-------------|---------|------|
| 0 | 是 | `WORKFLOW_GEN_MODEL` | 意图分析，需要工具调用能力 |
| 1 | 是 | `WORKFLOW_GEN_MODEL` | DAG 生成，需要结构化输出能力 |
| 2 | 否（但 Repair 内部调用 LLM） | （同上） | 编译和校验为纯代码；Repair 调用 LLM |
| 3 | 否 | — | 纯正则规则引擎 |
| 4 | 否 | — | 确定性编译 |
| 5 | 否 | — | 模板字符串拼接 |
| 6 | 否 | — | 文件复制 |
| 7 | 否 | — | Docker SDK 调用 |
| 8 | 是 | 节点级独立配置 | 每个节点可指定不同模型 |
| 9 | 否 | — | 事件管道 |

系统在单次端到端执行中的 LLM 调用次数大致为：Layer 0 (1 次) + Layer 1 (1 次) + Layer 2 Repair (0 至 N 次) + Layer 8 (每个节点 1 次 Session，Session 内部可能有多次 LLM 轮次)。一个典型的 5 节点 DAG 大约产生 7-9 次 LLM 调用的总开销（含 Plan 阶段的 2 次和每节点 1 次 Session 的多次推理轮次）。
