# 03 — 关键设计决策

> 汇总系统架构中的 10 项关键设计决策，每条涵盖决策内容、选择原因、以及由此产生的权衡（trade-off）。

---

## 决策 1：Planning Agent 使用 Claude SDK 而非直接 API 调用

**决策内容**：Layer 0 的 Planning Agent 通过 Claude Agent SDK Session（而非裸 HTTP API 调用）执行意图分析和任务分解。SDK Session 提供完整的工具调用环境，Planning Agent 可以在规划阶段调用 Skill 和 MCP 工具来探查系统状态。

**原因**：裸 API 调用只能"想"，不能"查"。Planning Agent 需要回答的最关键问题是"系统是否有足够的数据来完成用户请求的任务"，这要求它能实际探查数据目录的内容。SDK 提供的 Read 和 Bash 工具让它可以在规划前验证数据文件是否存在、年份范围是否正确、选举类型是否匹配。此外，SDK 的 Skill 工具让 Planning Agent 了解每个 Skill 的功能边界，从而做出更准确的任务分解——它会知道"候选人资料搜索"是一个 Skill 可以完成的原子任务，不需要进一步拆分。

**权衡**：SDK Session 的初始化比单次 API 调用慢（需要建立 WebSocket 连接、加载工具定义、注入 system prompt）。此外，SDK 的推理循环增加了复杂度——Planning Agent 可能在单次规划中调用多个工具，每轮工具调用都增加延迟。但相比"生成一个错误 DAG 然后在执行阶段才发现数据缺失"的成本，这个延迟是值得的。Plan 阶段的错误成本远高于 Plan 阶段的延迟成本。

## 决策 2：Skill Auto-Binder 使用纯正则规则引擎而非 LLM

**决策内容**：Layer 3 的 `SkillAutoBinder` 使用纯正则规则引擎（四层匹配策略 + 21 条中英文关键词规则表）将 `skill_id` 绑定到 DAG 节点上，完全不调用 LLM。

**原因**：这是一个确定性映射问题，不需要语义推理。输入（节点 ID 和 task 描述）和输出（skill_id）之间的映射规则是预先定义好的——`agenda_setter` 节点绑定 `agenda_csv` Skill、`candidate_registry_searcher` 节点绑定 `candidate_registry_searcher` Skill。这个映射不需要 LLM 的"理解"能力。使用正则规则引擎带来三个优势：（1）**确定性**——相同的节点 ID 总是绑定到相同的 Skill，不会因为 LLM 的温度参数而产生不同的绑定结果；（2）**低延迟**——正则匹配是微秒级的，而 LLM 调用需要数秒；（3）**零 token 成本**——Skill 绑定发生在每次 DAG 编译中，如果用 LLM 每次都要产生 token 消耗。

**权衡**：正则规则的覆盖率受限于规则表的大小。如果一个新 Skill 加入系统，或者 LLM 生成了一种规则表中没有覆盖的节点 ID 命名模式，Auto-Binder 会匹配失败并回退到空值。这需要在 Rulebook（`_NODE_ID_SKILL_FALLBACKS`）中持续维护关键词映射，增加了维护负担。但考虑到 Skill 集合的增长速度远低于 LLM 调用的调用频率，这个权衡是划算的。

## 决策 3：多轮澄清机制（planning_round_policy）

**决策内容**：`planning_round_policy.py` 实现了一个多轮澄清循环——当 Planning Agent 判断用户信息不足时，不立即生成 DAG，而是返回澄清问题等待用户回复，然后重新进入 Planning Agent 评估。这个循环有最大轮次限制和信息增量检测。

**原因**：信息不足时生成 DAG 是灾难性的。如果用户只说"分析选举"而不指定年份和地点，LLM 生成的 DAG 要么基于错误的假设（"2024 总统选举？"），要么包含大量模糊节点（"搜索所有选举数据"）。前者产生错误结果，后者导致执行效率极低。与其在执行阶段发现错误，不如在规划阶段多花一轮对话来澄清需求。"先问清楚再动手"的策略将不确定性收敛在成本最低的 Layer 0，而不是让它向下传播到 Layer 8 的高成本执行阶段。

**权衡**：增加了用户交互轮次。对于已经明确知道需求的高级用户，多轮澄清可能显得冗长。系统通过 `InformationSufficiency` 评分和 `PlanningGear` 控制来平衡：当信息充分性评分高于阈值时跳过澄清直接进入 ready 状态；只有当关键维度（年份、地点、选举类型、分析目标）有缺失时才触发 ask。此外，`planning_round_policy` 还包含信息增量检测——如果用户在第二轮中提供的信息与第一轮完全重叠（没有增加任何新维度），系统会主动降级为"尽最大努力执行"而不是无限追问，防止对话陷入死循环。

## 决策 4：Docker 容器复用而非一次性容器

**决策内容**：Layer 7 采用长生命周期容器策略——一个 DAG 的所有节点复用同一个 Docker 容器，通过 `docker exec` 依次执行多个 Agent Session，而非为每个节点启动一个新容器。容器在 DAG 开始前启动，在所有节点完成后删除。

**原因**：减少启动延迟。Docker 容器冷启动时间（包括镜像拉取、文件系统初始化、网络配置）在 2-5 秒之间，如果为每个节点启动一个新容器，一个 5 节点 DAG 仅容器启动就累积 10-25 秒的额外延迟。复用容器将这部分延迟压缩为一次性开销。此外，复用容器使得上游节点的输出文件天然可被下游节点访问（因为所有节点共享同一个 `/workspace` 卷），不需要额外的文件传输步骤。

**权衡**：状态隔离更复杂。一次性容器有天然的隔离性——每个节点在干净的文件系统中开始，不会受前一节点的残留状态影响。复用容器需要更谨慎的工作区管理：每个节点写入自己的 `output/` 子目录，下游节点通过 `upstream/` 只读挂载访问上游输出。此外，如果一个节点的执行损坏了容器的共享状态（如修改了 Python 环境、改变了系统配置），会影响后续节点的执行。`RunContainerMonitor` 通过健康检查和异常检测来缓解这个风险，但不能完全消除。对于安全敏感的场景，一次性容器仍然是更安全的选择——但在本系统的应用场景（数据分析流水线）中，复用的性能收益大于隔离性的损失。

## 决策 5：Redis Streams + SSE 事件管道

**决策内容**：Layer 9 的事件回传使用 Redis Streams 作为中间缓冲层——Agent Session 将事件推送到 Redis Streams，SSE endpoint 从 Redis Streams 消费事件并推送到前端。而不是 Agent Session 直接写 SSE socket。

**原因**：三个关键需求驱动了这个设计：（1）**断线重连**——用户可能关闭浏览器标签页再重新打开，前端需要从上次断开的位置继续接收事件，而不是重头开始。Redis Streams 的消费者组机制和消息 ID 天然支持这个需求——前端通过 `Last-Event-ID` header 告知断点，后端从 Redis Streams 的相应位置恢复推送。（2）**多消费者**——同一个运行的 DAG 可能有多个前端连接在监听（用户在多个标签页中打开了同一个运行）。Redis Streams 的消费者组确保每个连接都能独立消费事件流，互不干扰。（3）**解耦**——Agent 容器在 Docker 网络中运行，不能直接写 FastAPI 的内存队列。Redis 作为独立服务，提供了跨网络边界的事件传递通道。

**权衡**：增加了 Redis 依赖。系统需要运行一个 Redis 实例，且 Redis Streams 的配置（消费者组创建、ACK 机制、消息 TTL）增加了运维复杂度。此外，Redis Streams 引入了一层额外的序列化/反序列化开销——事件从 Agent 的 Python dict → JSON → Redis Streams → JSON → FastAPI Python dict → SSE text → 前端 JSON。每一层转换都增加微量延迟。但对于一个端到端延迟以秒而非毫秒计的系统来说，这个延迟是微不足道的。相比之下，如果使用直连方案，任何网络抖动都会直接导致事件丢失，这对于需要完整审计追踪的选举分析系统是不可接受的。

## 决策 6：搜索子节点自动注入

**决策内容**：在 Layer 4（DAG 物化器）中，`_inject_search_sub_nodes()` 检测标记了 `external_search` 或 `knowledge_search` 需求的父节点，自动在其前面插入一个搜索子节点。这个搜索子节点使用搜索 Agent Skill 执行联网搜索或知识库检索，结果自动流入父节点的工作区。

**原因**：让 Planning Agent 专注于"做什么"而非"怎么做"。Planning Agent 只需要在节点描述中标记"这个节点需要搜索外部信息"，而不需要手动创建搜索节点、定义搜索策略、管理搜索结果的传递。将这些细节下沉到 Materializer 层，使得 WorkflowPlan 保持简洁，同时搜索子节点的注入逻辑集中在一处，便于统一优化搜索策略（如并发搜索、来源优先级、去重逻辑）。此外，这也允许搜索策略的独立演进——当搜索 Agent 升级到新版本或切换搜索引擎时，不需要修改 Planning Agent 的 prompt 或 Skill 注册表。

**权衡**：DAG 节点数膨胀。如果一个 DAG 中有 5 个节点都标记了搜索需求，Materializer 会将其膨胀为 10 个节点（5 个搜索子节点 + 5 个原始节点）。每个搜索子节点都启动一个 Agent SDK Session，增加了总执行时间和 token 消耗。系统通过两个机制缓解这个问题：（1）搜索子节点使用轻量级模型和简化的 system prompt，降低单个搜索节点的成本；（2）搜索策略模板（在 Materializer 中预定义）尽可能将多个搜索目标合并为单次搜索，减少子节点数量。但在搜索密集型任务中，节点膨胀仍然是主要的性能瓶颈之一。

## 决策 7：DAG 调度 vs 单 Agent 两种执行模式

**决策内容**：系统提供两种执行模式——**DAG 调度模式**（`execute_with_dag_scheduler()`）和**单 Agent 模式**（`execute_single_agent()`）。DAG 调度模式走完整的 10 层流水线，适用于"分析 2026 台北市长选举"这类复杂多步骤任务；单 Agent 模式跳过 Layer 1-7，直接在一个 Agent Session 中完成简单任务。

**原因**：简单任务不需要 DAG 的开销。如果用户问"列出系统中 2024 年的所有选举数据文件"，这个任务可以被一个 Agent Session 通过 Read 和 Bash 工具在 5 秒内完成。如果走完整 DAG 流程，Layer 0-7 的准备阶段就要花费 10-20 秒，DAG 本身只有一个节点，调度器、容器管理、事件管道的开销完全浪费。单 Agent 模式通过 Planning Agent 的 `chat` 状态或显式的 `mode="single"` 参数触发，跳过了所有不必要的中间层，将"思考+执行"压缩在一个 Session 中。

**权衡**：两套代码路径增加了维护负担。DAG 调度模式和单 Agent 模式的执行入口、错误处理、容器管理、事件回传都有差异。当一段核心逻辑需要修改时（如 Session 超时策略），需要同时评估两种模式是否都需要更新。系统通过将共同逻辑（如 Agent SDK Session 的初始化、工具清单的组装、system prompt 的构建）抽取到共享模块（`sdk_session.py`、`system_prompt.py`）来减少重复，但两套执行路径的差异仍然存在于 `execute_api.py` 和 `election_agent.py` 中。

## 决策 8：claude-runtime/ 分离于 .claude/

**决策内容**：项目的 Agent 配置（Skill 定义、Subagent 角色、共享 settings）存放在 `claude-runtime/` 目录而非 `.claude/` 目录。在 Layer 6（工作区同步）中，`sync_workspace_skills()` 将 `claude-runtime/` 复制到容器的 `.claude/` 路径。

**原因**：`.claude/` 是 Claude Code 官方项目配置目录，其内容会被 Claude Code CLI 在仓库根目录启动时自动加载。将 ElectionSim 专用的 Agent 配置放在 `.claude/` 中会产生两个问题：（1）**冲突**——Claude Code 用户（开发者）可能有自己的 `.claude/skills/` 和 `.claude/settings.json`，与项目提供的配置冲突；（2）**语义混乱**——`.claude/` 中的配置是针对 Claude Code IDE 的本地开发环境，而 ElectionSim 的 Agent 配置是针对 Docker 容器内的 Claude Agent SDK 运行时环境的。两者的使用场景、依赖、权限模型完全不同。

**权衡**：需要一个额外的 sync 步骤。每个 DAG 运行开始时，`sync_workspace_skills()` 必须完整复制 `claude-runtime/` 的内容。对于大型项目，这个复制操作可能涉及数百个文件。系统通过使用 `shutil.copytree` 的增量复制（`dirs_exist_ok=True`）和长生命周期容器（只在容器首次启动时执行完整 sync，后续节点复用已有文件）来减少开销。此外，`common/claude_runtime_assets.py` 支持通过 `ELECTIONSIM_CLAUDE_RUNTIME_DIR` 环境变量自定义目录名，为不同部署环境提供了灵活性。

## 决策 9：节点级 SCOPE_LINES（作用域约束）

**决策内容**：Layer 5 的 `build_node_prompt()` 为每种节点类型注入专属的 `SCOPE_LINES`——一段精确描述该节点行为边界的自然语言指令。例如 `agenda_setter` 的 SCOPE_LINES 规定它只负责生成 agenda CSV 文件，不能搜索候选人资料或运行模拟。

**原因**：通用的 system prompt 不够精确。如果所有节点共享相同的 system prompt（"你是一个选举分析专家，请完成分配给你的任务"），模型可能会在任务范围之外"过度协助"——一个负责搜索候选人资料的 Agent 可能在搜索结果中就开始分析选情，侵入了模拟运行和分析报告节点的职责。这导致（1）重复工作——多个节点做了相同的事；（2）结果不一致——同一件事在不同节点中被不同方式处理，产生矛盾结论；（3）错误传播——上游节点的错误判断进入下游节点的视野，影响下游推理。节点级 SCOPE_LINES 将每个 Agent 的职责边界精确划定，配合执行权威层级（`EXECUTION_AUTHORITY_LINES`）声明上下级关系，形成了一层"主管-下属"式的职责分工体系。

**权衡**：维护多个 scope 模板的成本。随着系统节点类型的增加（目前已有 10+ 种节点类型，包括 agenda_setter、candidate_registry_searcher、simulation_runner、report_writer、data_visualizer、external_searcher 等），SCOPE_LINES 模板的数量也在增长。每个新节点类型都需要精心设计作用域约束——过宽会导致职责渗透，过窄会导致 Agent 在边界处无所适从。系统通过模板继承和模块化组合来管理这个复杂性——基础层的"工具调用纪律"和"输出合约规范"被所有节点共享，只有特定于节点类型的约束才在 SCOPE_LINES 中单独定义。

## 决策 10：幂等性执行

**决策内容**：系统在执行层面实现了幂等性保护——同一个节点的相同输入多次执行产生相同输出，不会因为重复提交而创建重复结果。这由两个机制实现：（1）**DAG 级去重**——`DAGScheduler` 在执行前检查节点的输出目录是否已存在有效的结果文件（`result.json` + `report.md`），如果存在且校验通过则跳过执行；（2）**节点级去重**——Agent SDK Session 在执行前检查工作区状态，如果检测到上一次执行的中断点（如进度 CSV 中的未完成标记），从断点继续而非重头开始。

**原因**：防止重复提交。在分布式系统中，消息重复投递是常见现象——用户可能多次点击发送按钮、SSE 重连可能导致事件重复消费、容器意外重启可能触发调度器的重试逻辑。如果没有幂等性保护，重复执行会导致：（1）LLM token 浪费——同一个任务多次推理产生额外成本；（2）结果覆盖——第二次执行的结果覆盖第一次的结果，可能导致下游节点看到不一致的数据；（3）副作用重复——如果节点涉及数据库写入或 API 调用，重复执行产生重复的副作用。幂等性保护确保即使重复提交发生，系统也只执行一次实际工作。

**权衡**：需要额外的状态检查和 Redis 依赖。幂等性检查需要读取节点的工作区状态（文件是否存在、内容是否有效），这增加了每次节点执行的启动延迟（通常 <100ms，可忽略）。对于需要强制重新执行的场景（如用户修改了参数后要求重新运行），系统需要通过 `node_overrides` 参数显式标记"跳过幂等性检查"。此外，在容器复用的场景下，前一次运行的残留文件可能被误判为有效结果——系统通过在每个节点的 `result.json` 中包含 `node_id` 和 `run_id` 字段，并在幂等性检查时比对这两者，确保残留文件不会伪装成当前运行的输出。
