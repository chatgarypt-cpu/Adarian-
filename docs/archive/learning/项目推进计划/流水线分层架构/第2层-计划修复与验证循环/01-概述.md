# 01 - 概述

## 修复循环在整个流水线中的位置

第 2 层"计划修复与验证循环"位于 Planner 生成 `WorkflowPlan` 之后、Materializer（第 4 层）将 plan 物化为 `GeneratedDAG` 之前。它承接第 1 层的 LLM 原始输出，负责将其转化为一个结构合法、语义正确的 `WorkflowPlan`，然后交给下游做 Skill 自动绑定（第 3 层）和 DAG 物化（第 4 层）。

```
[第1层] Planner (LLM/SDK) 输出原始 JSON 文本
    |
    v
[第2层] 计划修复与验证循环    <--- 本层
    |     |
    |     +--> Compile   (plan_compiler.py)
    |     +--> Validate  (plan_validator.py + workflow_validation.py)
    |     +--> Repair    (plan_repair_loop.py + planning_repair.py)
    |
    v
  CompiledWorkflowPlan (plan + validation_warnings)
    |
    v
[第3层] Skill 自动绑定 ---> canonicalize + auto_bind
    |
    v
[第4层] DAG 物化器 ---> GeneratedDAG
```

在模块层面，本层的核心逻辑分布在以下文件中：

| 文件 | 职责 |
|------|------|
| `orchestrator/dag/plan_compiler.py` | `WorkflowPlanCompiler`：JSON 提取 + Pydantic 校验 + Skill 白名单检查 |
| `orchestrator/dag/plan_validator.py` | `validate_generated_plan()`：业务校验 + 选举周期检测 + 拓扑评估 |
| `orchestrator/dag/workflow_materializer.py` | `validate_plan_dag()`：DAG 语义校验核心（去重、无环、边合法、扇出限制等） |
| `orchestrator/dag/workflow_validation.py` | `normalize_workflow_payload()`：工作流通用校验与规范化入口 |
| `orchestrator/dag/plan_repair_loop.py` | `WorkflowPlanningRepairLoop`：Compile-Validate-Repair 主循环 |
| `orchestrator/chat/planning_repair.py` | `build_planning_repair_prompt()`：修复提示词构建逻辑 |

## Plan -> Compile -> Validate -> Repair 循环四阶段

整个修复循环可以抽象为四个阶段：

1. **Prompt** -- `WorkflowPlanningRequest.prompt()` 构建初始 prompt，发送给 LLM/SDK 模型。
2. **Compile** -- `WorkflowPlanCompiler.compile()` 从模型原始输出文本中提取 JSON，反序列化为 `WorkflowPlan`，做 Skill 白名单和规模检查。
3. **Validate** -- 通过 `request.validate_plan()`（内部调用 `validate_generated_plan()` 和 `validate_plan_dag()`）执行业务校验。
4. **Repair** -- 若 Compile 或 Validate 抛出异常，`_repair_prompt_or_raise()` 构建修复 prompt，将校验错误注入，要求 LLM 重新输出。

成功则产出 `CompiledWorkflowPlan`，交给 Materializer 物化；失败则在达到最大重试次数后抛出异常。

## 为什么需要修复循环：LLM 输出不可靠

LLM 生成的 JSON 存在多种不可靠因素：

- **格式问题**：LLM 可能在 JSON 前添加解释性文字（"这是建议的 DAG 结构..."），或用 Markdown 代码围栏包裹 JSON，导致直接 `json.loads()` 失败。
- **字段缺失/类型错误**：LLM 可能遗漏必填字段（如 `rationale`、`status`），或字段类型不匹配 Pydantic schema。
- **业务规则违反**：即使 JSON 结构合法，也可能违反业务约束——重复 node_id、边引用不存在的节点、Skill 不在注册表中、存在环、超出扇出限制等。
- **选举情景知识错误**：LLM 可能生成不符合选举周期的计划（如 2026 年台湾总统大选）。

修复循环通过"校验 + 定向反馈 + 重试"的模式，将 LLM 的不确定性输出收敛为合法结构，避免下游（Agent 执行、报告生成）因非法 DAG 而崩溃。

## `workflow_plan_repair_attempts` 配置

修复重试次数由 `workflow_plan_repair_attempts` 控制，定义在 `orchestrator/settings.py`：

```python
# orchestrator/settings.py:234
workflow_plan_repair_attempts=_int_env("WORKFLOW_PLAN_REPAIR_ATTEMPTS", 2, minimum=1, maximum=5),
```

- **默认值**：2 次（即初次生成 + 最多 2 次修复重试 = 最多 3 次交互）
- **最小值**：1，**最大值**：5
- **环境变量**：`WORKFLOW_PLAN_REPAIR_ATTEMPTS`
- 在 `OrchestrationEngine._workflow_plan_repair_attempts()` (`orchestrator/dag/engine.py:73`) 和 `_run_planning_attempts()` (`orchestrator/chat/planning_agent.py:171`) 两处读取。

配置值通过 `WorkflowPlanGeneratorConfig.max_attempts` 传递给 `WorkflowPlanningRepairLoop`。

## 与其他层的接口

- **上游（第 1 层）**：`WorkflowPlanGenerator` 调用 `WorkflowPlanningRepairLoop.generate()`，传入 `request`（含 `intent`、`prompts`、`normalize_plan`、`validate_plan`）、`transport`（LLM 或 SDK 调用函数）、`generation_source`、`generation_details_builder`。
- **下游（第 3-4 层）**：`WorkflowPlanCompiler.materialize()` 调用 `build_generated_dag()`，产出 `GeneratedDAG`。
