# 02 - 计划编译器

## 概述

计划编译器 (`WorkflowPlanCompiler`) 是修复循环中的 Compile 阶段，负责将 LLM 返回的原始文本转换为一个结构合法的 `CompiledWorkflowPlan`。它位于 `orchestrator/dag/plan_compiler.py`，是整个 Compile-Validate-Repair 流水线的第一道防线。

```python
# orchestrator/dag/plan_compiler.py:23-27
@dataclass(frozen=True)
class CompiledWorkflowPlan:
    plan: WorkflowPlan
    validation_warnings: list[str]

@dataclass(frozen=True)
class WorkflowPlanCompiler:
    allowed_mode: str
    custom_prefix: str
```

## `PlanCompiler.compile()` 完整流程

`compile()` 方法（`plan_compiler.py:34-44`）按以下顺序执行六个步骤：

```
raw_text (LLM 原始输出)
    │
    ├── 1. _extract_workflow_plan_json(raw_text)
    │       调用 extract_json_object() 从文本中提取 JSON 字符串
    │
    ├── 2. _workflow_plan_from_json(extracted)
    │       json.loads() → WorkflowPlan.model_validate()
    │
    ├── 3. _validate_explicit_skill_whitelist(plan)
    │       遍历所有节点的 skill_id/skills，验证是否在 SkillRegistry 中
    │
    ├── 4. _validate_planner_size(plan)
    │       检查节点数 ≤ 30、边数 ≤ 200
    │
    ├── 5. request.normalize_plan(plan)
    │       调用 canonicalize_workflow_plan() 规范化节点 ID/kind/enabled
    │
    └── 6. request.validate_plan(normalized_plan, user_input)
            调用 validate_generated_plan() + validate_plan_dag() 做业务校验
            └──→ CompiledWorkflowPlan(plan, validation_warnings)
```

六个步骤中任何一步失败都会抛出异常（`ValueError`、`json.JSONDecodeError` 或 `ValidationError`），触发修复循环进入 Repair 阶段。

## 步骤 1：`extract_json_object()` -- 从 LLM 原始输出中提取 JSON

`extract_json_object()` 定义在 `orchestrator/dag/plan_generator_support.py:17-22`，核心逻辑在 `_try_extract_json()` 函数中。

**提取策略（三阶段降级）**：

1. **直接解析**（第 91-93 行）：如果整个文本就是一个合法 JSON 对象，直接返回。
2. **括号平衡扫描**（第 95-97 行）：调用 `_scan_balanced_braces()`，从文本中找到第一对完整、可解析为 JSON 对象的 `{}` 括号块。这是 LLM 在前言后输出 JSON 的最常见情况。
3. **Markdown 代码围栏提取**（第 98-104 行）：用正则 `` ```(?:json)?\s*([\s\S]*?)``` `` 匹配代码块，对每个匹配块做括号平衡扫描。

`_scan_balanced_braces()` (`plan_generator_support.py:108-126`) 的核心算法：逐字符遍历，维护括号深度计数器。每次回到深度 0 时，尝试将 `text[start:index+1]` 解析为 JSON 对象。取最后一个成功解析的候选结果。

如果提取结果为空对象 `{}`，`_extract_workflow_plan_json()` 会抛出 `ValueError`：
```python
# plan_compiler.py:88-92
extracted = extract_json_object(raw_text)
if extracted.strip() == "{}":
    raise ValueError(f"Workflow generation output is not JSON. raw={raw_text[:1000]}")
```

## 步骤 2：Pydantic 校验 -- JSON 反序列化为 `WorkflowPlan`

`_workflow_plan_from_json()` (`plan_compiler.py:95-103`) 分两步：

```python
def _workflow_plan_from_json(extracted: str) -> WorkflowPlan:
    try:
        payload = json.loads(extracted)           # 第 1 步：JSON 语法解析
    except json.JSONDecodeError as exc:
        raise ValueError(f"WorkflowPlan JSON 语法错误：{exc.msg}，位置 {exc.pos}") from exc
    try:
        return WorkflowPlan.model_validate(payload)  # 第 2 步：Pydantic schema 校验
    except ValidationError as exc:
        raise ValueError(_workflow_validation_message(exc)) from exc
```

- **第 1 步** `json.loads()`：检查 JSON 语法合法性（括号匹配、引号、逗号等）。
- **第 2 步** `WorkflowPlan.model_validate()`：Pydantic v2 校验，检查字段类型、必填项、长度限制等。`WorkflowPlan` 定义在 `workflow_models.py:198-201`，要求 `nodes` 至少 1 个，最多 `PLANNER_WORKFLOW_MAX_NODES`（30）个，`edges` 最多 `PLANNER_WORKFLOW_MAX_EDGES`（200）个。每个 `WorkflowPlanNode` 的 `skills` 字段最多 `WORKFLOW_NODE_MAX_SKILLS`（6）个。

`_workflow_validation_message()` (`plan_compiler.py:106-112`) 将 Pydantic 校验错误格式化为人类可读的中文消息，最多取前 8 条错误，格式为 `"loc字段: 错误消息"`。

## 步骤 3：Skill 注册表白名单校验

`_validate_explicit_skill_whitelist()` (`plan_compiler.py:115-118`) 遍历 plan 中的所有节点：

```python
def _validate_explicit_skill_whitelist(plan: WorkflowPlan) -> None:
    skills = skill_registry_entries()                    # 加载当前 SkillRegistry
    for node in plan.nodes:
        _validate_node_skills(node, skills=skills)       # 逐节点检查
```

`_validate_node_skills()` (`plan_compiler.py:121-129`) 的逻辑：

- 通过 `_raw_node_skill_values()` 收集节点上所有的 skill 原始值（`skill_id`、`skill`、`skills[]`），过滤掉空值和 `GENERIC_AGENT_SKILL_ID`。
- 通过 `canonical_skill_id()` 将原始值规范化为 Skill 注册表中的正式 ID（定义在 `skill_binding.py:16-20`，委托给 `canonical_skill_like_node_id()` 做大小写纠正和别名解析）。
- 如果规范化后的 ID 不在 SkillRegistry 中，抛出 `ValueError`，并附带可用 Skill 示例（前 20 个）。

## 步骤 4：Planner 规模校验

`_validate_planner_size()` (`plan_compiler.py:71-84`) 检查 Planner 原始输出是否在 schema 限制内：

```python
def _validate_planner_size(plan: WorkflowPlan) -> None:
    node_count = len(plan.nodes)
    if node_count > PLANNER_WORKFLOW_MAX_NODES:       # 30
        raise ValueError(...)
    edge_count = len(plan.edges)
    if edge_count > PLANNER_WORKFLOW_MAX_EDGES:       # 200
        raise ValueError(...)
```

注意：这是 Planner 阶段的限制（`PLANNER_WORKFLOW_MAX_NODES=30`, `PLANNER_WORKFLOW_MAX_EDGES=200`），与运行时限制（`RUNTIME_WORKFLOW_MAX_NODES=200`, `RUNTIME_WORKFLOW_MAX_EDGES=2000`）不同。注释明确指出："System-injected runtime nodes are allowed later"，搜索子节点注入是物化阶段的事。

## 步骤 5：规范化（Normalize）

`request.normalize_plan()` 是一个由各 planning 策略注入的 `PlanNormalizer` 回调。在 `engine_planning_mixin.py` 中，它绑定到 `canonicalize_workflow_plan()` （`plan_validator.py:32-54`），做以下规范化：

- **节点 ID 规范化**：通过 `canonical_skill_like_node_id()` 将 LLM 可能输出的大小写变体、带空格变体统一为 SkillRegistry 中的正式 ID。
- **节点 kind 规范化**：若 ID 在 SkillRegistry 中 → `AGENT`；若 `allowed_mode=skills_plus_custom` 且 ID 以 `custom_prefix` 开头 → `INTERNAL`。
- **节点 enabled 规范化**：Skill 节点强制 `enabled=true`；`INTERNAL` 节点强制 `enabled=false`。
- **Skill 规范化**：通过 `resolve_node_skill_id()` 和 `resolve_node_skill_ids()` 解析 `skill` 和 `skills` 字段。
- 最后调用 `auto_bind_workflow_plan_skills()` 做一轮自动绑定。

## 步骤 6：业务校验（Validate）

`request.validate_plan()` 是一个 `PlanValidator` 回调，绑定到 `validate_generated_plan()` (`plan_validator.py:63-108`)。它依次执行：

1. **Canonicalize**（如果尚未 canonicalize）。
2. **`validate_plan_dag()`** -- DAG 结构校验（详见下文）。
3. **`validate_report_workflow_plan()`** -- 报告意图的语义校验（检查 report 模式所需的特定结构）。
4. **`_validate_generic_candidate_node_descriptions()`** -- 通用候选人节点不应硬编码候选人名单。
5. **选举周期校验** -- 检测 `(2026, 台湾, 总统)` 等时间线冲突，产出 warning。
6. **拓扑评估** -- 通过 `assess_workflow_plan_topology()` 和 `collect_workflow_plan_topology_warnings()` 产出结构建议。

## `validate_plan_dag()` 函数详解

`validate_plan_dag()` 定义在 `orchestrator/dag/workflow_materializer.py:51-83`，是 DAG 语义校验的核心。它接收一个（可选的已 auto_bind 的）`WorkflowPlan`，执行以下校验项：

### 校验项清单

| 序号 | 函数 | 校验内容 | 失败条件 |
|------|------|----------|----------|
| 1 | `_ensure_unique_node_ids()` | 唯一 node_id | `len(node_ids) != len(set(node_ids))` |
| 2 | `_validate_node_semantics()` | INTERNAL 节点语义 | INTERNAL 节点 enabled=true |
| 3 | `_validate_node_allowlist()` | 节点 ID 白名单 + 可执行 Skill 绑定 | 存在不在 SkillRegistry 且不符合 mode/prefix 策略的节点；或 AGENT 节点既无 Skill 绑定也无 description |
| 4 | `_validate_skill_fan_out()` | Skill 扇出限制 | `blockProfile.canFanOut=false` 的 Skill 被多个节点使用 |
| 5 | `_validate_node_skill_set_size()` | 节点 Skill 集大小 | 单节点 skills 超过 `WORKFLOW_NODE_MAX_SKILLS`（6） |
| 6 | `_validate_edges()` | 边引用合法性 | `edge.from_` 或 `edge.to` 不在 node_set 中；自环；edge_type 不在 `WORKFLOW_EDGE_TYPES` 中；conditional edge 缺少 condition |
| 7 | `_validate_max_blocking_fan_out()` | 最大阻塞扇出 | 单节点阻塞型出边 > `_MAX_BLOCKING_FAN_OUT`（10） |
| 8 | `_validate_agenda_setter_wide_fan_out()` | agenda_setter 扇出限制 | agenda_setter 的阻塞扇出 > 3 且目标不是 search/data_discovery |
| 9 | `_validate_master_analyst_presence()` | master_analyst 强制存在 | 可执行 Agent 节点 ≥ 10 但未包含 `master_analyst` |
| 10 | `_validate_required_predecessor_presence()` | 必需前驱存在性 | `stage=evidence` 的节点缺少 `preferredPredecessors` 中指定的前驱 |
| 11 | `_ensure_acyclic()` | 无环检测 | 基于 Kahn 拓扑排序算法：若处理节点数 < 总节点数则存在环 |

### 关键常量

所有常量定义在 `workflow_materializer.py` 顶部（第 32-48 行）：

| 常量 | 值 | 说明 |
|------|-----|------|
| `_MAX_BLOCKING_FAN_OUT` | 10 | 单节点最大阻塞型出边数 |
| `_AGENDA_SETTER_WIDE_FAN_OUT_LIMIT` | 3 | agenda_setter 宽扇出阈值，超出需检查目标是否为搜索/数据发现节点 |
| `_MASTER_ANALYST_REQUIRED_NODE_COUNT` | 10 | 触发强制 master_analyst 的节点数阈值 |
| `WORKFLOW_NODE_MAX_SKILLS` | 6 | 单节点最大 Skill 数量 |
| `PLANNER_WORKFLOW_MAX_NODES` | 30 | Planner 阶段最大节点数 |
| `PLANNER_WORKFLOW_MAX_EDGES` | 200 | Planner 阶段最大边数 |
| `RUNTIME_WORKFLOW_MAX_NODES` | 200 | 运行时（物化后）最大节点数 |
| `RUNTIME_WORKFLOW_MAX_EDGES` | 2000 | 运行时最大边数 |

### 无环检测算法

`_ensure_acyclic()` (`workflow_materializer.py:385-397`) 使用 Kahn 算法：

1. 构建 indegree（入度）和 outgoing（邻接表）图结构（仅考虑"阻塞型"边，即非 `EDGE_TYPE_REFERENCE` 的边）。
2. 将入度为 0 的节点入队。
3. 每次出队一个节点，将其所有后继的入度减 1，若后继入度变为 0 则入队。
4. 若处理的节点数 ≠ 节点总数 → 存在环 → 抛出 `ValueError("workflow plan has a cycle")`。

## `workflow_validation.py` 中的规范化步骤

`normalize_workflow_payload()` (`workflow_validation.py:304-388`) 是工作流 payload 的通用校验+规范化入口，用于前端/API 提交的工作流编辑场景（非 Planner 场景）。其流程为：

1. **类型校验**：payload 必须是 dict。
2. **通用节点描述填充**：`_normalize_generic_node_descriptions()` 对 `allowed_mode=open` 下无 Skill 绑定且有 label 但无 description 的节点，将 label 复制为 description。
3. **ID 编译**：`compile_workflow_payload()` 委托给 `workflow_payload_compiler.compile_workflow_payload_ids()` 做节点/边 ID 的规范化编译。
4. **DAG 构建与校验**：`_build_workflow_plan_from_compiled_payload()` 从编译后的 payload 构建 `WorkflowPlan`，做 schema + semantic 校验。
5. **节点属性回填**：将规范化后的 skill、enabled、critical、blockProfile 等属性写回 payload。
6. **布局计算**：通过 `normalize_nodes_edges()` 计算确定性 layer/order，用于可视化。
7. **兼容性处理**：保留非 schema 字段（如 `workflowId`、`agentConfig`），处理 camelCase/snake_case 互转。

`build_workflow_plan_from_payload()` (`workflow_validation.py:179-189`) 提供更精简的入口，直接从任意 payload 提取 `WorkflowPlan`。它先做 ID 编译，再调用 `_build_workflow_plan_from_compiled_payload()`，内部执行 id 猜测 (`_guess_plan_node_id`)、skill 绑定、Pydantic 校验、canonicalize、`validate_plan_dag()` 等完整链路。
