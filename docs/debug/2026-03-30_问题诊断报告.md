## 二、Phase 3 发言同质化问题

### 2.1 症状

同一 agent 在多轮中重复完全相同的发言：

| Agent | Tick 1 | Tick 2 | Tick 3 | Tick 4 | Tick 5 |
|-------|--------|--------|--------|--------|--------|
| Agent 5 (情感批评者) | "胖貓，你到底在想什么？！" | "胖貓，你到底在想什么？！" | "胖貓，你到底在看什么？！" | "胖貓，你到底有没有人性？！" | "胖貓，你到底在想什么？！" |
| Agent 10 (专家评论员) | "胖貓事件折射出..." | "胖貓事件折射出..." | "胖貓事件折射出..." | "胖貓事件折射出..." | "胖貓事件折射出..." |
| Agent 7 (中立观察者) | "理性看待事件本質" | "理性看待事件本質" | "理性看待事件本質" | "理性看待事件本質" | "理性看待事件本質" |

### 2.2 根本原因

**原因 1：视野太窄**
- 每个 agent 每轮只看到自己关注对象的**最新 1 条**发言
- `MAX_POSTS_PER_TICK = 3`（config.py 第 131 行），但实际只取 followee 的最后一条
- 3/4 的 spreader agent 只看 Core 节点（胖貓、譚竹、重慶警方）
- Core 节点发言基本不变，导致所有人的上下文趋同

**原因 2：无全局记忆**
- Agent 不知道自己上一轮说了什么
- Agent 不知道其他人在同一轮说了什么
- 无法避免重复表达

**原因 3：同一观点被多人重复**
- "'譚竹让雙方冷靜 = 逃避责任'" 被 Agent 8、12 说了 4 次
- "'重慶警方不立案'" 被 Agent 6、9 说了 5 次
- 没有"角度覆盖"的感知机制

### 2.3 解决方案方向

**推荐方案：GraphRAG 记忆层**

在每轮发言前，检索本轮已说过的内容：
1. 告诉 LLM："这些观点已被覆盖，请找另一个角度"
2. 同时检索"同立场的人说了什么"，避免同义重复
3. 检索"哪些角度还没人提过"

技术选型：
- Embedding API：硅基流动（待配置）
- 向量库：ChromaDB（项目已有）
- 检索维度：话题相似度（主）+ 立场相似度（辅）

## 三、stance_score 计算诡异问题

### 3.1 完整流转链路

```
Phase 1 生成 archetype
    stance_score = 9.2（情感批评者）
         ↓
Phase 2 apply_individual_jitter
    stance_score = 9.2 × (1 ± 15%) = 8.24（加了随机扰动）
         ↓
Phase 3 SimulationEngine 初始化
    agent_stances[5] = 8.24（从 social_graph.json 加载）
         ↓
Phase 3 Tick 1
    Agent 5 previous_stance = 8.24 ✓
    LLM 提议 new_stance = 8.24（完全不变）
    apply_stance_constraint: delta = 0.0，在 ±0.3 内，直接通过
         ↓
Phase 3 Tick 2-N
    Agent 5 stance 完全不变：8.24 → 8.24 → 8.24 → 8.24 → 8.24
```

### 3.2 问题一：数值不一致

| 数据源 | Agent 5 stance |
|--------|---------------|
| Phase 1 archetype（entities_and_relations.json） | 9.2 |
| Phase 2 social_graph.json | 8.24 |
| Phase 3 tick_1.json previous_stance | 8.24 ✓ |
| 最终报告 final_report.md | 9.2 ✗ |

**结论**：最终报告用的是 Phase 1 的 archetype 值，不是 Phase 3 真实模拟的值。

### 3.3 问题二：数值被扰动了两次

1. Phase 1 LLM 生成 archetype 时 stance_score = 9.2
2. Phase 2 `apply_individual_jitter` 又加了一次 ±15% 随机扰动 → 8.24

同一个 agent 的立场在 Phase 1 → Phase 2 之间发生了随机漂移，且没有任何记录。

### 3.4 问题三：susceptibility 字段从未使用

`entities_and_relations.json` 里每个 archetype 都有 `susceptibility`：

```json
{
  "group_name": "情感批评者",
  "stance_score": 9.2,
  "susceptibility": 0.85,  // 从未被使用
  "confirmation_bias_level": "strong"
}
```

在 phase3 的代码里：
- 只用了 `confirmation_bias_level` 来约束 stance 变化
- `susceptibility` 本应是"这个 agent 多容易被别人影响"，但实现里完全没用到

**设计的本意可能是**：
- `susceptibility` 高 → 更容易被别人的发言影响立场
- `confirmation_bias_level` → 影响立场变化的方向和幅度

但当前代码只实现了后者，前者被忽略。

### 3.5 问题四：Agent 视野太窄导致 stance 锁死

以 Agent 5（情感批评者）为例：
- `saw_posts_from = [0]`（只看 Agent 0 - 胖貓）
- 胖貓的 `can_speak = false`，Agent 5 永远只看到"（该实体不可发言）"
- 结果：Agent 5 的 stance 5 轮完全不变

### 3.6 问题五：confirmation_bias 约束过于宽松

`strong` 级别的 agent 变化幅度限制是 ±0.3。但 LLM 提议值基本都在这个范围内，导致：
- LLM 提议 new_stance = 9.5，previous = 9.2，delta = 0.3 → 直接通过
- Agent 可以逐渐单向漂移（9.2 → 9.5 → 9.8 → ...）

### 3.7 解决方案方向

1. **统一 stance 数据源**：最终报告应从 tick_log 读取最终立场，而非 archetype
2. **移除或记录 Phase 2 的随机扰动**：扰动应该被记录，或在 Phase 3 初始化时重置
3. **启用 susceptibility**：根据 susceptibility 动态调整 stance 变化幅度上限
4. **扩大 Agent 视野**：每轮让 agent 看到更多发言（包括同群体其他 agent）

## 四、最终报告数据来源错误

### 4.1 报告数字 vs 实际 tick_log

| 指标 | 报告说 | tick_log 实际 |
|------|--------|--------------|
| 理性支持者立场变化 | +1.0 | Agent 9: +2.81 |
| 情感支持者立场变化 | +0.2 | Agent 11: +0.12 |
| 网络暴力批评者立场变化 | -0.2 | Agent 8: -1.5 |

报告的立场变化数字是**凑出来的近似值**，不是从 tick_log 真实计算。

### 4.2 根本原因

Phase 4 的报告生成 Prompt 拿了 `entities_and_relations.json` 里的 archetype 初始值做对比，而不是从 tick_log 里读取真实数据。

## 五、communication_style 未体现

### 5.1 症状

| 群体设定 | 设定风格 | 实际发言 |
|---------|---------|---------|
| 网络蹭热度者 | "寻找流量机会" | "譚竹让雙方冷靜，这话听起来像在避重就轻" |
| 情感批评者 | "充满情绪化的感叹和质问" | "胖貓，你到底在想什么？！" |
| 法律关注者 | "理性分析法律程序" | "重慶警方不予立案，需进一步核实" |

网络蹭热度者的发言是批评譚竹的内容，不是在"寻找流量机会"。

### 5.2 根本原因

`communication_style` 在 prompt 里只是背景描述，不是强制指令。LLM 更关注"说什么"（由 stance 和 related_entity 决定），而非"怎么说"（communication_style）。

## 七、auto-correction 逻辑错误（已修复）

### 7.1 Bug 描述

Phase 1 的 `auto_correct_entities` 函数（第 458-471 行）使用"附近 50 字检测死亡关键词"来判断实体是否已故：

```python
# 错误逻辑
context = seed_text[idx-50:idx+50]
if any(kw in context for kw in death_keywords):
    entity["can_speak"] = False
```

**问题**：譚竹出现在胖貓"跳江身亡"的同一句中，被错误标记为不可发言。

### 7.2 修复方案

改为正则匹配"实体 + 死亡动词"的模式，只有实体被明确描述为死亡主体时才标记：

```python
# 修复后逻辑
pattern1 = f"{name}[.　]{{0,10}}(已故|去世|死亡|...)"
pattern2 = f"(已故|...)的{name}"
if re.search(pattern1, seed_text) or re.search(pattern2, seed_text):
    entity["can_speak"] = False
```

### 7.3 修复验证

test2 重新运行：
- ✅ 胖貓、劉傑：不可发言（正确，已故）
- ✅ 譚竹：可以发言（正确，活人）
