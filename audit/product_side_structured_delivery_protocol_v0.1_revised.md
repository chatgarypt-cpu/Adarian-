## 2. Control Decision

### 2.1 Gate

- [x] GO for trial use
- [ ] CONDITIONAL_GO
- [ ] HOLD
- [ ] FAIL

### 2.2 决策理由

```text
本协议用于解决产品侧交付物与技术侧需求之间的结构错位问题。

当前核心痛点不是“产品侧没有产出”，而是：
1. 需求方提出结构化交付需求；
2. 产品侧容易理解成内容生产或实现设计；
3. AI 辅助交付时容易一次性全量脑补；
4. 交付物缺少阶段、类型、颗粒度和退回标准；
5. 后续无法稳定转译为 report contract / prompt / prefill / whitebox / 工程迭代。

因此 v0.1 允许试运行，但不作为强制管理制度。
```

### 2.3 启用条件

```text
一次性问题，不走协议。
可复用交付，才走协议。
```

启用本协议的任务必须满足至少一项：

```text
1. 会沉淀为结构、规则、模板、范式、案例库或验收标准。
2. 会影响后续产品路线或工程转译。
3. 需要产品侧输出可复用判断，而不是一次性观点。
4. 需要多轮人机确认，防止 AI 一次性跑偏。
```

## 3. Goal & Boundary

### 3.1 本协议主目标

```text
建立一套轻量、可复用、可退回的产品侧结构化交付机制，
让产品侧交付物能够稳定服务 Owner 的产品判断、技术转译和后续工程治理。
```

---

### 3.2 本协议要解决的问题

```text
1. 需求方说“结构 schema”，交付方却写成完整正文或实现说明。
2. 产品侧过早进入 JSON / 字段 / tick_logs / whitebox 等技术实现细节。
3. 产品侧交付物缺少目标读者、模块职责、读者判断和验收口径。
4. 双方使用 AI / DS 时，Agent 容易一次性全量生成，缺少逐步确认。
5. 交付物无法被 Owner 稳定转译为 report contract / prompt / prefill / whitebox / 迭代任务。
```

---

### 3.3 本协议不解决的问题

```text
1. 不替代正式 PRD。
2. 不替代工程迭代文档。
3. 不替代 DS / Codex 工作流。
4. 不要求日常轻量沟通都走协议。
5. 不要求产品侧设计代码、字段、测试命令或文件路径。
6. 不把产品侧交付直接升级为工程执行任务。
```

---

### 3.4 禁止变化

本协议执行时明确禁止：

```text
1. 不把一次性问题强行纳入协议。
2. 不让产品侧承担工程实现设计职责。
3. 不让产品侧直接定义 JSON 字段、Python 模块、测试文件或 whitebox artifact。
4. 不允许 AI 在复杂任务中一次性全量脑补最终交付。
5. 不允许交付方越过任务阶段，直接进入正文、实现或最终方案。
6. 不允许把产品侧建议自动升级为工程版本范围。
7. 不允许产品侧 AI 伪装成 DS Team / 多 reviewer 协作。
```

## 4. Role Boundary

### 4.1 Owner / 技术产品经理负责

```text
1. 提出任务目标。
2. 判断任务是否启用协议。
3. 判断任务等级：M-Level / L-Level。
4. 指定任务类型与预期交付模板。
5. 保留最终业务方向与工程转译权。
6. 将有效交付物转译为 report contract / prompt / prefill / whitebox / 迭代文档。
7. 判断交付物是否通过、退回或进入下一轮修订。
```

### 4.2 产品侧负责

```text
1. 明确目标读者。
2. 明确业务场景。
3. 提供产品判断。
4. 设计信息架构。
5. 拆分章节 / 模块职责。
6. 说明读者应形成的判断。
7. 提供正例 / 反例。
8. 提取案例结构与表达风格。
9. 归纳规则、范式和验收口径。
10. 判断交付物是否像业务研判报告，而不是技术测试报告。
```

### 4.3 产品侧不负责

```text
1. 不设计 JSON 字段结构。
2. 不设计 Python 模块拆分。
3. 不设计 tick_logs / whitebox / final_report.json 的读取方式。
4. 不决定拐点、风险等级、极化指数由哪段代码计算。
5. 不设计 prompt 文件路径。
6. 不设计 DS / Codex 执行边界。
7. 不写工程迭代文档。
8. 不替技术侧判断最终实现方案。
```

### 4.4 职责边界句

```text
产品侧负责定义“业务阅读目标与结构判断”；
技术侧负责定义“这些判断如何被稳定生成”。
```

## 5. Trigger Rule & Task Level

### 5.1 不启用协议：S-Level

S-Level 任务直接沟通，不走本协议。

适用：

```text
1. 改一句标题。
2. 判断某段话是否顺。
3. 临时问一个想法。
4. 单点表达反馈。
5. 问完即结束的一次性问题。
```

处理方式：

```text
直接问，不建卡，不走模板，不要求 DS Team。
```

---

### 5.2 启用轻量协议：M-Level

M-Level 适用于需要结构化输出，但不一定影响长期工程路线的任务。

适用：

```text
1. 找 3-5 篇优秀舆情分析文章。
2. 提取一类报告表达风格。
3. 分析某个报告模块怎么写。
4. 对比几个案例。
5. 给单章报告提供结构建议。
6. 做一次产品侧评审。
```

执行方式：

```text
轻量需求卡 + 指定交付模板 + 可一次性交付。
```

M-Level AI 最小自检：

```text
任务类型：
交付阶段：
不会做的事：
交付格式：
```

---

### 5.3 启用完整协议：L-Level

L-Level 适用于会沉淀为产品规则、报告范式、验收标准或工程输入的任务。

适用：

```text
1. 整份报告结构设计。
2. 报告产品验收标准。
3. 政府 / 公安 / 监管不同读者模式。
4. 代表性发言选择规则。
5. 风险研判范式。
6. 对策建议边界。
7. 产品侧长期交付模板。
8. 影响后续 Phase 4 / report contract / prompt / whitebox 的产品输入。
```

执行方式：

```text
完整需求卡 + 渐进确认 + 分段交付 + 验收矩阵。
```

L-Level AI 必须先确认：

```text
1. 任务类型。
2. 交付阶段。
3. 交付颗粒度。
4. 禁止事项。
5. 是否需要产品侧 DS Team / 多 reviewer 协作。
```

## 6. Task Type Matrix

### 6.1 任务类型总览

| 类型 | 名称 | 典型任务 | 交付重点 | 不看重 |
|---|---|---|---|---|
| A | 结构型任务 | 报告结构、页面信息架构、模块拆解 | 层级、模块、职责、读者判断 | 文采、字段、代码 |
| B | 内容型任务 | 正文样例、政府化表达、指标解释 | 表达准确、口径稳定、业务可读 | 重新设计结构 |
| C | 案例研究型任务 | 优秀舆情文章、政府报告案例 | 为什么值得参考、可复用元素 | 链接堆砌 |
| D | 风格提取型任务 | 风险命名、摘要风格、建议风格 | 原文表现 → 抽象规则 → 可复用句式 | 泛泛说“专业” |
| E | 规则归纳型任务 | 代表性发言、风险研判、验收规则 | 判断标准、正例、反例、退回条件 | 直接写代码 |
| F | 竞品分析型任务 | 舆情系统、智能分析平台 | 信息组织、阅读问题、可借鉴点 | 产品介绍流水账 |
| G | 验收评审型任务 | 报告评审、交付感评审 | 问题定位、严重程度、修改方向 | 只给主观感受 |
| H | 探索型任务 | 方向未定、问题未收敛 | 观察、假设、方向、风险 | 直接生成最终方案 |

---

### 6.2 一次任务的类型选择

```text
1. 每次任务必须选择 1 个主类型。
2. 允许选择 1 个副类型。
3. 不允许一个任务同时承载 3 个以上类型。
4. 若任务类型超过 2 个，应拆分为多个任务。
```

## 7. Delivery Stage

### 7.1 阶段定义

| 阶段 | 名称 | 回答的问题 | 禁止事项 |
|---|---|---|---|
| Stage 1 | 探索观察 | 现象是什么、问题可能在哪里 | 不直接给最终方案 |
| Stage 2 | 结构归纳 | 结构、模块、层级、读者判断是什么 | 不进入代码和字段实现 |
| Stage 3 | 规则抽象 | 可复用规则、正例、反例是什么 | 不写成泛泛感受 |
| Stage 4 | 样例沉淀 | 好样例、坏样例、可复用句式是什么 | 不自行新增结构 |
| Stage 5 | 验收评审 | 什么通过、什么退回、什么 known issue | 不替技术侧做最终 Gate |

---

### 7.2 阶段边界

```text
Stage 1 / Stage 2 主要用于产品结构输入。
Stage 3 / Stage 4 主要用于规则和风格沉淀。
Stage 5 主要用于产品侧验收与交付评审。
```

## 8. Collaboration Flow

### 8.1 M-Level 轻量交付流程

```text
Owner 发送轻量需求卡
  ↓
产品侧 AI 做 4 行自检
  ↓
产品侧按指定模板一次性交付
  ↓
Owner 按验收矩阵判断：采用 / 修订 / 退回
```

M-Level 不强制渐进确认。

但出现以下情况，应升级为 L-Level：

```text
1. 交付内容明显影响长期模板或工程路线。
2. 任务开始扩展到多个模块。
3. 双方对任务类型或阶段理解不一致。
4. AI 自检发现存在高歧义。
```

---

### 8.2 L-Level 渐进确认流程

```text
Owner 发送完整需求卡
  ↓
产品侧 AI / DS 先判断任务类型、阶段、颗粒度、禁止事项
  ↓
Owner 确认或修正
  ↓
产品侧生成第一段结构 / 样本 / 分析维度
  ↓
Owner 确认或修正
  ↓
产品侧继续展开正式交付
  ↓
产品侧自检
  ↓
Owner 验收：采用 / 修订 / 退回 / 转译
```

确认点不写死，按复杂度弹性设置。

原则：

```text
1. 简单任务可以少确认。
2. 复杂任务必须先确认方向。
3. 任一方发现跑偏，可以随时暂停并重新确认。
4. AI 不确定时必须自停，不得继续脑补。
```

## 9. Product-side AI / DS Team Rule

### 9.1 什么时候建议开 Team

以下任务建议产品侧使用 DS Team / 多 reviewer 协作，而不是单 agent 一次性生成：

```text
1. 找优秀舆情分析文章。
2. 提取政府报告风格。
3. 归纳风险研判表达范式。
4. 设计报告验收标准。
5. 评审报告是否像技术测试报告。
6. 制定代表性发言选择规则。
7. 做竞品 / 案例对比。
8. 任何 L-Level 可复用交付任务。
```

### 9.2 不建议开 Team 的任务

```text
1. 单段改写。
2. 单个标题建议。
3. 单一案例摘要。
4. 简单主观反馈。
```

### 9.3 推荐 Reviewer 角色

```text
Reviewer A：结构审查
- 关注信息架构、章节层级、模块职责。

Reviewer B：业务读者审查
- 关注政府 / 公安 / 监管部门是否读得懂、是否有决策价值。

Reviewer C：表达风格审查
- 关注是否像业务研判报告，是否像技术测试报告。

Reviewer D：规则与验收审查
- 关注正例、反例、hard fail、known issue。

Reviewer E：可转译性审查
- 关注交付物能否被 Owner 转译为 report contract / prompt / prefill / whitebox。
```

### 9.4 Team Mode 硬规则

```text
1. 若任务声明需要 Team Mode，产品侧 AI 必须明确 team_mode_used=true / false。
2. 若无法开启 Team Mode，必须停止并说明，不得伪装为多 reviewer 审查。
3. 主控只做汇总、冲突消解和最终整合，不替代各 reviewer 独立审查。
```

## 12. Acceptance Matrix

| 维度 | 合格 | 不合格 |
|---|---|---|
| 类型对齐 | 明确属于声明的任务类型 | 结构、正文、实现混在一起 |
| 阶段对齐 | 只回答当前阶段问题 | 跳到实现、字段、代码、测试 |
| 颗粒度 | 到模块职责、读者判断、规则或样例 | 只给泛泛目录或泛泛感受 |
| 读者意识 | 说明给谁看、看完判断什么 | 只写“内容应该包括什么” |
| 前后台边界 | 区分正文展示与后台支撑 | 把技术指标全部塞正文 |
| R0 边界 | 区分必需与可占位 | 什么都想一次做完 |
| 反例意识 | 写明不应包含什么 | 只有正向描述 |
| 可转译性 | Owner 能转成 contract / prompt / prefill / whitebox | Owner 看完仍无法推进 |
| AI 边界 | 有自检、有自停、有 team_mode 声明 | 一次性脑补、伪装 team review |

---

## 13. Fail / Return Rules

出现以下任一情况，Owner 可直接退回：

```text
1. 结构型任务交付成完整正文。
2. Stage 1 / Stage 2 任务交付成字段 schema 或代码实现。
3. 只给章节标题，没有模块职责和读者判断。
4. 没有说明目标读者。
5. 没有说明读者应形成什么判断。
6. 没有区分前台展示和后台支撑。
7. 越界设计 JSON / 代码 / prompt / whitebox。
8. 把模拟结果写成现实舆情事实。
9. 用“感觉更专业”替代具体判断。
10. 需要 Team Mode 但没有启动，也没有自停说明。
11. 没有正例 / 反例 / 验收标准，导致 Owner 无法转译。
```

修订规则：

```text
1. 只修当前阶段问题。
2. 不顺手扩大任务范围。
3. 不把产品侧建议自动升级为工程任务。
4. 若需要升级任务等级，必须由 Owner 确认。
```
