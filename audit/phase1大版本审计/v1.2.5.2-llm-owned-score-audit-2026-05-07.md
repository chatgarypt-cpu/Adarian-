## 4. Phase-by-Phase Findings

### 4.1 Phase 1 — Clean, No Issues

Phase 1 has a well-defined boundary between LLM-generated initial scores and code-derived schema properties:

- **LLM_OWNED_INITIAL (10 fields)**: event_scale, event_controversy, event_type, I, P, susceptibility, estimated_percentage, persona fields (5)
- **SCHEMA_PROPERTY_OWNED (3 fields)**: C, stance_score, confirmation_bias_level — all derived from I/P via `@property`
- **CODE_OWNED (2 fields)**: can_speak, original_statement — post-processed by `_post_process_entities()`

The GENERATOR prompt explicitly states "C = P × (I/10) — 你不需要生成 C，系统会自动推导", which is correct and prevents LLM from generating its own C.

**No migration needed.**

### 4.2 Phase 2 — Clean, No Issues

Phase 2 is entirely CODE_OWNED. All scores are either:
- Hardcoded constants (event entity stance=5.0, susceptibility=0.0)
- Copied from Phase 1 schema properties (spreader stance_score, confirmation_bias_level)
- Randomly perturbed via code (`random.uniform()`)

Zero LLM involvement. **No migration needed.**

### 4.3 Phase 3 — HYBRID Pattern, Correctly Implemented

Phase 3 has the most interesting ownership pattern — a tight LLM+code collaboration:

1. **LLM proposes** `new_stance` via `AGENT_POST_SYSTEM_PROMPT` (LLM_OWNED_RUNTIME)
2. **Code constrains** via `apply_stance_constraint()`:
   - `base_delta_map`: strong→±0.3, weak→±1.0, none→±2.0
   - `susceptibility_modulation`: `1 + 0.5*(susceptibility - 0.5)`
   - `effective_delta = base_delta * modulation`
   - Clip: `abs(delta) > effective_delta` → bounded
3. **Code computes** `GlobalMetrics` from agent_stances (pure statistics)

The HYBRID classification is not a problem — it's the correct design. The LLM provides the "intelligence" (semantic understanding of how the agent should react), and the code provides the "guardrails" (hard constraints on stance change magnitude). The result is deterministic within bounds but influenced by LLM judgment.

**Key detail**: `_parse_agent_response()` at `tick_simulation.py:731-734` does `new_stance = max(1.0, min(10.0, new_stance))` as a safety clamp, then `apply_stance_constraint()` does the real clipping.

**No migration needed. Documentation note**: The `change_reason` field (`within_effective_delta` vs `bounded_by_susceptibility`) is a useful observability hook that shows whether the LLM's proposal was accepted or overridden.

### 4.4 Phase 4 — ⚠️ Finding #1: Dual-Path Markdown Risk

This is the only finding requiring attention.

**The JSON path (safe)**:
`generate_report_with_llm()` → `parse_llm_report_response()` constructs `Phase4Output` entirely from code-owned data:
- `emotion_trajectory` ← `tick_logs[].global_metrics`
- `inflection_points` ← `identify_inflection_points()` (pol_delta > 0.1)
- `risk_level` ← `assess_risk()` (final_x thresholds)
- `x_t_sequence` ← `get_x_t_sequence()`

This is correct. The `final_report.json` is fully CODE_OWNED.

**The Markdown path (risk)**:
`save_markdown_report()` at `report_agent.py:586-612` has two branches:
```python
if self._llm_generated_markdown:
    # Branch A: Use LLM-written markdown directly
    with open(output_path, "w") as f:
        f.write(self._llm_generated_markdown)
else:
    # Branch B: Generate from code-owned Phase4Output
    markdown = generate_markdown_report(phase4_output, extraction_output)
```

**Branch A** uses `_llm_generated_markdown` — the raw LLM response from `REPORT_SYSTEM_PROMPT`. This prompt asks the LLM to:
- Independently identify inflection points (threshold: pol change > 0.05)
- Independently assess polarization (< 0.3 / 0.3-0.5 / > 0.5)
- Independently assess risk level
- Select trend symbols (↑↓→)

These are **different thresholds** from the code:
- Code inflection point: `pol_delta > 0.1` vs LLM prompt: `> 0.05`
- Code risk: `final_x > 7.5/6.5/5.0` vs LLM: free-form judgment

**Risk**: The LLM-generated Markdown may contain inflection points, risk assessments, and polarization judgments that **differ from** the authoritative `final_report.json`. A downstream consumer reading the Markdown would get different conclusions than one reading the JSON.

**Severity**: LOW — because:
1. The authoritative data is in `final_report.json` (code-owned)
2. The Markdown is a human-readable rendering
3. The fallback path (Branch B) is always correct

**Recommendation**: In v1.2.6, consider either:
- (A) Force Branch B always (remove LLM markdown generation) — safest but loses LLM's narrative quality
- (B) Pass code-computed inflection_points + risk_level into the LLM prompt so the LLM narrates FROM code-owned data rather than re-deriving
- (C) Add a diff-check in `save_markdown_report()` that warns if LLM markdown metrics diverge from Phase4Output

## 6. ⚠️ Finding #2: Susceptibility Jitter Creates Non-Deterministic Drift

**Location**: `topology_builder.py:34-80` (apply_individual_jitter)

Phase 2 applies random jitter (±5% Core, ±15% Periphery) to both `stance_score` and `susceptibility`. This means:
- The same Phase 1 output produces **different** Phase 2 initial conditions on each run
- `susceptibility` after jitter is used in Phase 3's `apply_stance_constraint()` as `effective_delta = base_delta * (1 + 0.5*(susceptibility - 0.5))`
- This creates **non-reproducible** simulation trajectories

**Is this a problem?** No — it's by design (v1.1.3). The jitter adds realistic variance. But it means that for **audit/reproducibility** purposes, two runs with the same seed text can produce different x(t) sequences. The only way to get exact reproducibility is to seed `random`.

**Recommendation**: If reproducibility matters for testing, add `random.seed(config.RANDOM_SEED)` at simulation start. Otherwise, no action.
