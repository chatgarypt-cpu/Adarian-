## 3. Phase Package Migration Assessment

### Phase 1

- **当前入口**: `src/phase1_entity_extraction.py`
- **目标入口**: `src/phase1/extraction.py`
- **可否迁移**: 可迁移
- **暴露的公开 API**: `extract_entities_from_file`, `save_entities_output`, `extract_entities_with_validation`, `extract_entities`, `ANALYZER_SYSTEM_PROMPT`, `ANALYZER_USER_PROMPT`, `GENERATOR_SYSTEM_PROMPT`, `GENERATOR_USER_PROMPT`, `VALIDATOR_SYSTEM_PROMPT`, `VALIDATOR_USER_PROMPT`, `_normalize_inner_cjk_quotes`, `_parse_json_candidate`, `analyzer_set_parameters`, `generator_create_entities`, `validator_check_format`

- **建议动作**: 迁移核心函数到 `src/phase1/extraction.py`，prompt 常量到 `src/phase1/prompts.py`。旧文件改为 shim，re-export 所有公开 API。`src/phase1/__init__.py` 做便捷导出。

### Whitebox 逻辑来源结论

当前 whitebox 逻辑分布：

1. **已在 whitebox 内**: `check_report_completeness` — 纯观察/检查函数，完美符合 whitebox 边界。
2. **在 main.py 编排层**: `write_report_completeness_summary` — 调 whitebox 函数 + 写文件 + 写 run.log。这个编排函数从概念上属于 "report observer" 的入口，可以考虑迁入 `src/whitebox/report_observer.py` 作为一个更高级的 API。
3. **在 schema 中**: `speaker_status`、`speaker_reason` 等白盒观测字段 — 这些是数据结构定义，不属于 whitebox 包，应在 schema 中保留。
4. **在 Phase 3 中**: `_selection_observability`、`_event_entity_observability` — 这些是运行时数据填充逻辑，属于 Phase 3 模拟过程，不应迁入 whitebox。
5. **在 RuntimeLogger 中**: `log_speaker_selection`、`log_tick_end` 等 — 这些是日志写入基础设施，不应迁入 whitebox。

## 5. Whitebox Boundary Judgment

### 哪些可迁移

- `write_report_completeness_summary` (main.py:263-288) → `src/whitebox/report_observer.py`。理由：纯编排 whitebox 检查，不参与生成。
- `build_run_paths` 中 `whitebox_summary` 的输出路径定义可保留在 main.py（路径编排属于 main.py 职责），但 whitebox_summary 的写入逻辑可封装到 whitebox。

### 哪些不可迁移

- `speaker_status` / `speaker_reason` / `decision_source` / `selector_score` 等字段定义 → 在 `src/schemas.py` 中，是结构化数据定义，不是 whitebox 逻辑。
- `_selection_observability` / `_event_entity_observability` → 在 Phase 3 中，是运行时模拟数据填充，不是事后检查。
- `save_report` / `save_markdown_report` → 是 Phase 4 报告生成逻辑，不是 whitebox。
- `load_extraction_output` / `load_phase2_output` → 是数据加载工具函数，不是 whitebox。

### 哪些必须留在 RuntimeLogger

- `log_run_start` / `log_run_end` / `log_phase_start` / `log_phase_end` / `log_tick_start` / `log_tick_end` — 这些是运行时观测基础设施，在模拟进行中实时写入。
- `log_llm_start` / `log_llm_end` — LLM 调用计数基础设施。
- `log_speaker_selection` — speaker selection 的实时日志记录，在 Phase 3 tick 执行过程中调用。如果迁入 whitebox，会形成 whitebox → Phase 3 的反向依赖或需要回调，违反 whitebox 仅观察的定位。
- `log_error` — 错误日志基础设施。

### 哪些必须留在 Phase 4

- `generate_report_with_llm` — LLM 报告生成入口。
- `build_full_report_context` — 为 LLM 构造报告上下文数据。
- `assess_risk` — 风险评估是报告生成的一部分，影响 Phase4Output.risk_level。
- `identify_inflection_points` — 拐点识别是报告生成的一部分。
- `generate_markdown_report` — 自动 fallback Markdown 生成。
- `save_report` / `save_markdown_report` — 报告保存。

### 是否会形成第二状态源

**不会。** 当前 `check_report_completeness` 仅在 Phase 4 完成后、main.py 的 `write_report_completeness_summary` 中调用，读取的是已写入的 `final_report.md`。它不参与模拟循环，不修改 agent 状态，不影响选 speaker 策略。whitebox 仅做"运行后质量检查"，完全符合"只能观察、检查、汇总、验证"的边界。

`write_report_completeness_summary` 迁入 whitebox 后，调用时机不变（仍在 `run_phase4` 完成后），不会形成第二状态源。

## 6. Blockers

### 无硬阻塞 (No hard blockers)

但存在以下需要 Codex 执行前决策的软问题：

1. **prompt 常量迁移策略 (SOFT)**: `profiling/prompts.py` 和 `scripts/probes/` 直接 import Phase 1 的 prompt 常量。迁移后需确保 shim 仍能 re-export 这些常量，或将常量单独抽到 `src/phase1/prompts.py`。如果只迁移函数不迁移 prompt 常量，profiling/probes 不会受影响。**建议**: prompt 常量留在旧文件或单独文件，旧入口 shim 保持 re-export。

2. **Phase 3 → Phase 4 依赖链 (SOFT)**: Phase 4 依赖 `src.phase3_tick_simulation` 的 `load_extraction_output` 和 `load_phase2_output`。迁移顺序需先 Phase 3 后 Phase 4，且 Phase 4 的新 import 路径需同步更新。不构成循环，但需 Codex 注意执行顺序。

3. **测试文件 import 路径 (SOFT)**: `tests/` 下 3 个文件直接 import `src.phase1_entity_extraction`。本轮可以不更新（测试不在主链），但需在 TASK_LOG 中记录为已知 debt。
