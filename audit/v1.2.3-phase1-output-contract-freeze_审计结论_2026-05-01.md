## 三、关键发现（按严重程度排序）

### 🔴 CRITICAL：TASK_LOG.md / CHANGELOG.md 包含虚假历史记录

**证据**：以下文件在多处以 ✅ 标记声称 `src/phase1/orchestrator.py`、`src/phase1/rules_engine.py`、`src/phase1/__init__.py` 已被创建/修改：

| 文件 | 受影响行 |
|------|---------|
| `docs/iterations/TASK_LOG.md` | 581-582, 652-655, 697, 700 |
| `docs/iterations/CHANGELOG.md` | 478-479, 491, 496, 512 |

但这些文件在磁盘上**不存在**。这意味着：
- R1 实施者阅读 TASK_LOG 会合理推断这些文件存在
- 这是**精确的合约警告场景**：文档声称的架构与实际代码不符
- 影响：如果 R1 基于 TASK_LOG 设计接入点，会造成结构性漂移

**建议**：R1 准入前审计并更正这些记录，或标注为 `[已回退/未实施]`。

---

### 🟠 HIGH #1：stance_score / confirmation_bias_level 双路径冲突

**问题**：合约将所有 stance_score/confirmation_bias_level 统一标记为"派生属性"，但这仅对 `EntityExtractionOutput → OpinionSpreader` 路径成立。

存在第二条路径 `phase1_persona_engine.py → Archetype`：

- `schemas.py:371` — Archetype.stance_score 是 **LLM 必填字段**
- `schemas.py:373` — Archetype.confirmation_bias_level 是 **LLM 必填字段**
- `phase1_persona_engine.py:77,79,91` — LLM prompt 要求输出这两个字段

**风险**：如果有人将合约字面理解为"所有 stance_score 都是派生的"，从 Archetype prompt 中删除这两个字段 → `phase1_persona_engine.py` 直接崩溃。

**合约现状**：合约全文未提及 `phase1_persona_engine.py` 或 `Archetype` 类型。

**建议**：合约增加一节说明双路径差异，或在 forbidden_to_change 中明确保护 Archetype 的 LLM 输出要求。

---

### 🟠 HIGH #2：main.py 缺少类型约束

**问题**：合约声称 `EntityExtractionOutput` 是 canonical object，但 main.py 的编排函数**没有类型标注**：

```python
# main.py:89
def run_phase2(extraction_output, output_path: Path = None):  # 无类型
# main.py:129
def run_phase3(extraction_output, phase2_output, seed_text, output_path: Path = None):  # 无类型
# main.py:159
def run_phase4(extraction_output, phase2_output, tick_logs, x_t_sequence, ...):  # 无类型
```

相比之下，内层函数都有标注（`phase2_topology_builder.py:193`、`phase3_tick_simulation.py:198`、`phase4_report_agent.py:82`）。

**风险**：main.py 是编排层。如果运行时的返回值类型改变，Python 不会在编排层捕获，错误会传播到内层才暴露。

**建议**：R1 准入前给 main.py 的编排函数添加类型标注。

---

### 🟠 HIGH #3：@property 方法未被 forbid 保护

**问题**：Phase 2 和 Phase 4 直接访问 `spreader.stance_score` 和 `spreader.confirmation_bias_level`（它们是 @property）。但合约的 `forbidden_to_change` 只保护了字段层面的 I/P 取值语义，**未保护 @property 方法本身**。

如果 R1 删除或重命名这些 @property → Phase 2 `phase2_topology_builder.py:134,136` 抛出 AttributeError。

**建议**：forbidden_to_change 增加：`OpinionSpreader.stance_score`、`.confirmation_bias_level`、`.C` @property 方法签名。

---

### 🟡 MEDIUM #1：group_distribution_strategy 是"幽灵字段"

- `phase3_tick_simulation.py:209`：`getattr(extraction_output, 'group_distribution_strategy', 'normal')`
- 此字段**不在 EntityExtractionOutput 的 schema 定义中**
- 合约仅在 legacy_fields (5.3) 提及，但未在 Phase 3 依赖 (4.2) 列出
- 如果 R1 清理 EntityExtractionOutput 时未注意 → 静默退化为 "normal"，改变模拟行为

**建议**：在 Phase 3 依赖表中显式列出该字段，说明其 ghost field 性质。

---

### 🟡 MEDIUM #2：simulation_card.py 使用防御性 getattr

`src/phase3/simulation_card.py:17-30` 对所有 persona 字段使用 `getattr(node, field, default)` 模式。这意味着这些字段**可以缺失而不崩溃**。

合约未记录这种优雅降级行为 → R1 可能不知道 Phase 3 有容错能力，错误地认为所有字段都是硬依赖。

**建议**：合约增加一节说明 Phase 3 的容错边界。

---

### 🟡 MEDIUM #3：C 属性是死代码

`schemas.py:168-171` 定义了 `C` @property，LLM prompt 也要求不输出 C，但全仓库**无任何代码读取 `.C`**。

**影响**：低。但合约将 C 列为需要保护的派生属性 → 在保护一个不被使用的属性。

**建议**：合约标注 C 为"已定义但当前无下游消费"，降低其保护优先级。
