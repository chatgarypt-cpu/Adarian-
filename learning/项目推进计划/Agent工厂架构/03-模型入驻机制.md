# 03 — 主模型入驻机制

---

## 核心问题

> 一个超大规模主模型，怎么「进入」GenFlow 并真正控制它？

答案：不是通过 API 调用，不是通过聊天界面。是通过**改写 GenFlow 的配置层和代码层**——主模型的触手伸到 Skills、Planner、Models、质量门的每一处。

---

## GenFlow 暴露给主模型的操作面

### 操作面 1：Skills Registry — 替换整个技能体系

```
操作对象: genflow-common/skills_registry.yaml
操作方式: 主模型生成新的 YAML → Factory 写入 → GenFlow 热加载
变更范围: 全部 Skill 定义、依赖关系、阶段分组、产物契约
```

主模型不需要「一个一个改 Skill」。它一次性设计整个 Skill 地图，生成完整的 skills.yaml，然后 Atomic 替换。

### 操作面 2：SKILL.md — 为每个 Skill 写执行指令

```
操作对象: packages/<domain>/skills/*/SKILL.md
操作方式: 主模型设计 Skill 合同 → Subagent 池并行写 → 质量门校验
变更范围: 每个 Skill 的 Purpose/Inputs/Outputs/Procedure/Examples/Failure modes
```

主模型不亲自写 Markdown。它为每个 Skill 生成一份合同（contract），然后派发 Subagent 去填。

### 操作面 3：Planner — 改写追问和 DAG 生成逻辑

```
操作对象: packages/<domain>/planner/*.py
操作方式: 主模型设计 Planner 契约 → Subagent 写代码 → AST 校验 + dry-run
变更范围: 追问策略函数、DAG 生成器、节点编排逻辑
```

### 操作面 4：Models — 定义领域知识体系

```
操作对象: packages/<domain>/models/*.py
操作方式: 主模型设计领域本体 → Subagent 写 Pydantic/dataclass → import 校验
变更范围: 实体定义、证据结构、输入输出 schema、枚举值
```

### 操作面 5：质量门 — 进化校验规则

```
操作对象: genflow-core/quality_gate/*.py
操作方式: 主模型从失败模式库中抽象新规则 → 生成 Python 校验函数
变更范围: 新的质量检查项、领域锚点词表、泛化废话黑名单
```

### 操作面 6：基座配置 — 优化运行时参数

```
操作对象: genflow-core/settings.py 的运行时值
操作方式: 主模型分析历史运行指标 → 建议新的超时/并发/模型路由参数
变更范围: 容器资源、LLM 模型选择、重试策略
```

## 入驻流程

### Phase 5.1：主模型首次连接

```
1. 主模型拿到 GenFlow 的完整接口面文档（操作面 1-6 的 schema）
2. 主模型拿到已有成功领域包（领域A + 领域B）的元模式摘要
3. 主模型拿到 Factory 的工具清单和能力边界
```

此时主模型不生成任何东西。它只**理解**——理解 GenFlow 能做什么、怎么做、边界在哪。

### Phase 5.2：第三领域孵化（首次自动化）

```
用户: "我要一个金融多Agent系统"

主模型:
  1. 分析新领域的深层结构
     - 与已有领域的共性：数据采集→实体标准化→证据推理→报告输出
     - 领域特化部分：实时数据、量化模型、合规审查、多资产类别

  2. 设计金融 Agent 社会的宪法
     - 技能地图：Entry(2) + Evidence(4) + Synthesis(3) + Output(2) + Review(2) = 13个Skill
     - 质量契约：风险评估必须量化到置信区间，投资建议必须有免责声明
     - 数据模型：StockQuote, FinancialStatement, RiskAssessment, PortfolioAnalysis

  3. 孵化领域架构师 Subagent
     - 生成金融领域架构师的任务单
     - 包含：13个 Skill 的 contract、模型蓝图、Planner 契约

  4. 领域架构师派发 Subagent 池
     - Skill 编写组 ×3 → 并行写 13 个 SKILL.md
     - Planner 编写组 ×1 → 写追问模块
     - Model 编写组 ×1 → 写数据模型

  5. 质量门校验
     - 全过 → 金融领域包交付
     - 有错 → 主模型收到失败清单 → 修复指令 → 子任务重做 → 最多 3 轮
```

### Phase 5.3：持续入驻（常态运行）

主模型不是「来一下就走」。它持续入驻：

```
每次新领域包完成:
  → 主模型收到完整的 factory_run.jsonl
  → 从中抽象新的元模式
  → 决定是否反哺到基座

每次质量门失败:
  → 主模型分析失败模式
  → 如果是新类型失败，加入失败模式库
  → 如果是已知类型，检查修复是否有效

每次用户反馈:
  → 人工审查标记某个 SKILL.md "语义不对"
  → 主模型收到标记 → 分析原因 → 更新 contract 设计策略
```

## 主模型的上下文管理策略

### 不入驻时

主模型不运行。不消耗 token。没有后台进程。

### 入驻时（每次孵化新领域）

主模型只携带三类上下文：

| 类别 | 内容 | Token 估算 |
|---|---|---|
| **接口面** | GenFlow 6 个操作面的 schema 定义 | ~5K |
| **参考摘要** | 已有成功领域包的元模式摘要 | ~8K |
| **当前任务** | 新领域的用户需求 + 主模型自己产出的蓝图 | ~10K |

总计约 23K，远在强模型的可靠推理窗口内。

### 修复轮

主模型不重读全文。只携带：

| 类别 | 内容 | Token 估算 |
|---|---|---|
| **蓝图** | 本轮领域的契约冻结版本 | ~8K |
| **失败清单** | 结构化 JSON：rule_id / file / line / expected / actual | ~2K |
| **相关片段** | 失败文件的具体出错段落 | ~3K |

总计约 13K。修复轮比初始轮更轻量。

## 主模型的能力边界

### 它能做的

- 设计一个领域的 Agent 社会拓扑（哪些 Skill、什么依赖关系）
- 生成 Skill 合同（每个 Skill 的输入/输出/禁止项）
- 决定质量门是否通过
- 从多个领域包中抽象元模式
- 建议基座配置变更

### 它不能做的

- 保证生成的 Skill 语义完全正确（需要人工验收）
- 处理需要实时反馈循环的系统（DAG 拓扑天然无环）
- 自己验证自己产出的 Python 代码逻辑是否正确（只能靠质量门的确定性规则）

### 它应该被拒绝的场景

- 用户需求包含实时/低延迟要求（毫秒级反馈）
- 用户需求需要循环推理（A → B → C → A）
- 用户需求涉及高度监管领域且无人工审核通道
