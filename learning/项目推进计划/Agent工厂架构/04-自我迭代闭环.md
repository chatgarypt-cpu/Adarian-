# 04 — 自我迭代闭环

---

## 核心命题

> 系统怎么越做越聪明？不是靠模型权重更新。是靠平台本身的模板、规则、策略、契约在每次领域孵化后变得更精准。

## 元模式提炼：主模型在学什么

### 从领域 A 学到（以政策分析为例）

```
领域 A 的深层结构:
  组织层级: 机构A → 分支B → 执行单元C
  时间维度: 周期 → 阶段 → 里程碑
  核心实体: 参与者、分类、范围、量化指标
  质量规则: 数值非负、总量一致、归属合法
  来源类型: 官方公告、结构化文件、PDF、人工修订

可迁移结构:
  · 实体标准化（参与方 → 任何需要ID对齐的实体）
  · 层级聚合（子单元 → 机构 → 跨域比较）
  · 来源可信度评分
  · 数值一致性校验（分量之和 = 总量）
```

### 从领域 B 学到（以合规审查为例）

```
领域 B 的深层结构:
  权限层级: 发布方 → 审核方 → 执行层
  权威层级: 上位规则 → 实施条例 → 操作指引 → 先例
  引用体系: 编号/条款/段落/历史
  论证结构: 主张 → 证据 → 依据 → 结论
  时效管理: 生效日、修订日、废止日

可迁移结构:
  · 证据链追溯（谁说的、依据什么、是否被推翻）
  · 权威层级判断
  · 冲突检测（两套规则矛盾时如何处理）
  · 引用完整性校验
```

### 多个领域交叉抽象出元骨架

```
┌─────────────────────────────────────────────┐
│           跨领域元骨架 (Meta-Skeleton)        │
│                                               │
│  Entry      → 定义问题范围、识别数据源          │
│  Ingestion  → 读取原始数据、提取结构化字段       │
│  Normalize  → 实体标准化、ID 对齐              │
│  Validate   → 数值/逻辑/来源校验               │
│  Evidence   → 多源证据聚合、可信度加权          │
│  Reasoning  → 领域推理（特化部分）              │
│  Report     → 结构化输出、可追溯引用             │
│  Audit      → 质量检查、合规审查（特化部分）      │
│                                               │
│  共 8 个阶段。其中的 Ingestion/Normalize/      │
│  Validate/Evidence/Report 是跨领域通用的。     │
│  Reasoning 和 Audit 需要领域特化。             │
└─────────────────────────────────────────────┘
```

## 反哺基座：元模式怎么变成平台能力

### 反哺 1：Skill 模板进化

```
第一版（仅一个领域）:
  SKILL.md 模板 = 自由格式 Markdown

第二版（第二个领域加入后）:
  发现：两个领域的 SKILL.md 都有 Purpose/Inputs/Outputs/Procedure/
        Examples/Failure modes 这些章节
  → 模板强制要求这 6 个章节，缺少任何一个质量门直接阻断

第三版（第三个领域加入后）:
  发现：负例（when NOT to use this skill）同样重要
  → 模板新增 When not to use 章节
```

### 反哺 2：质量门规则追加

```
第一版规则:
  · YAML schema 校验
  · 文件完整性校验

第二版追加:
  · domain_anchor 检测（领域锚点命中率 < 8 → 不通过）
  · 泛化废话黑名单（"do your best" "根据情况处理" → 不通过）

第三版追加:
  · SKILL.md 间相似度检测（两个 Skill 过于相似 → 警告）
  · cross-reference 完整性（引用的上游产物必须存在）
```

### 反哺 3：DAG 拓扑模板扩展

```
第一版模板:
  · layered_diamond（适用于报告生成型工作流）
  · two_stage_fanout（适用于先广后深型工作流）

第二版追加（来自第二个领域的需求）:
  · evidence_first（先收集所有证据，再分阶段推理）
  · multi_level_review（多层级审查）

第三版追加（来自第三个领域的需求）:
  · parallel_streams（多资产并行分析流，最后汇聚）
```

### 反哺 4：失败模式库

主模型维护一个跨领域的失败模式库。每次新领域孵化，先检查历史失败模式：

```yaml
failure_patterns:
  - id: unknown_skill_id
    cause: "Planner 引用了一个不在 skills.yaml 中的 skill_id"
    prevention: "向 Planner Subagent 注入 canonical skill ID enum"
    occurrence_count: 7  # 在3个领域包中反复出现了7次
    
  - id: skill_overlap
    cause: "多个 Skill 的职责边界模糊，都声称做'分析'"
    prevention: "主架构师在 blueprint 中明确定义每个 Skill 的 forbidden_overlap"
    occurrence_count: 4
    
  - id: semantic_drift
    cause: "SKILL.md 的标题和正文不在说同一件事"
    prevention: "domain_anchor gate 强制 ≥8 个领域锚点命中"
    occurrence_count: 3
```

每次修复成功的记录，都变成下一个领域的预防规则。

## 正反馈循环

```
第一个领域（人工，6个月）
  → 质量门规则: 6 条
  → Skill 模板: 自由格式
  → 失败模式库: 空
  → 拓扑模板: 2 个

第二个领域（半自动，2个月）
  → 质量门规则: 14 条（追加了 domain_anchor、废话检测等）
  → Skill 模板: 强制 6 章节
  → 失败模式库: 11 条
  → 拓扑模板: 4 个

第三个领域（全自动，1天）
  → 质量门规则: 22 条
  → Skill 模板: 强制 8 章节 + 负例
  → 失败模式库: 23 条
  → 拓扑模板: 6 个

...

第 N 个领域（全自动，15分钟）
  → 系统已经足够聪明，能自动预防绝大多数已知失败模式
  → 人工介入仅用于审查「领域语义正确性」
```

**不是模型变聪明了。是基座变聪明了。** 基座的模板、规则、模式库、拓扑策略都在进化。每一个新领域都在让基座更强。

---

## 人类在循环中的位置

在正反馈循环中，人类不退场。但角色变了：

| 阶段 | 人类角色 |
|---|---|
| 第 1-2 个领域 | 执行者——亲自写 SKILL.md、Planner、Models |
| 第 3-5 个领域 | 审查者——Factory 生成，人类抽查语义正确性 |
| 第 6+ 个领域 | 裁决者——只在主模型遇到全新失败模式时介入 |
| 长期 | 方向制定者——决定哪些新领域值得接入、系统演进的战略方向 |
