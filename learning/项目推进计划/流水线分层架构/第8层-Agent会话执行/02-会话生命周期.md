# 02 - 会话生命周期

## 概览

Agent 会话生命周期覆盖从容器启动到产物写回的全过程。当前架构存在两条路径：**Native Terminal Runner**（主力）和 **旧版 SDK 路径**（仅确定性导出节点复用）。本章以 Native Terminal Runner 为主线，并在关键差异处标注 SDK 路径的行为。

会话生命周期阶段：
```
[容器启动] → [配置加载] → [CLI/SDK 初始化] → [推理循环] → [收尾校验] → [产物输出] → [容器退出]
```

---

## 2.1 入口与配置加载

### `agent/native_terminal_runner.py` 入口

`main_async()` 是容器的实际入口函数。执行步骤如下：

1. **解析命令行参数** (`_parse_args()`)：接受 `--node-id` 参数，设置环境变量 `CLAUDE_NODE_ID`
2. **定位工作区** (`runtime._workspace_dir()`)：从环境变量 `CLAUDE_WORKSPACE` 读取；未设则回退到当前目录
3. **确保协议目录** (`runtime.ensure_protocol_dirs(ws)`)：创建 `output/` 子目录结构
4. **加载 task prompt** (`runtime._load_task_prompt(ws)`)：从 `meta/task_prompt.md` 读取；若文件不存在或内容为空则抛出 `RuntimeError`
5. **确定性节点快速通道**：调用 `runtime._is_deterministic_export_node(ws)` 或 `runtime._is_deterministic_appendix_node(ws)`，若是则直接委托给 `runtime.main_async()`
6. **验证模型配置**：环境变量 `CLAUDE_MODEL` 必须非空，否则抛出 RuntimeError

### `agent/election_agent.py` 入口（旧版 SDK 路径参考）

`main_async()` 函数 (line 1087) 的初始阶段：

- `_load_task_prompt(ws)`：加载 task prompt
- `_load_node_execution_config(ws)`：加载 NodeExecutionConfig，校验 `node_id` 和 `skill_id`
- `_detect_skill_id(ws)`：三级优先级解析 skill id —— 环境变量 `CLAUDE_SKILL_ID` > `run_manifest.json` > `node_context.json`

## 2.2 CLI 子进程初始化（Native Terminal 路径）

`native_terminal_runner.py` 的 `_run_cli()` 函数 (line 282) 负责启动 Claude Code CLI 子进程。

### CLI 命令构建 (`_build_cli_command`)

```text
claude --print
  --input-format text
  --output-format stream-json
  --verbose
  --include-partial-messages
  --include-hook-events
  --model <CLAUDE_MODEL>
  --permission-mode <CLAUDE_PERMISSION_MODE → "acceptEdits">
  --settings <workspace>/.claude/settings.json
  --append-system-prompt <系统提示词>
  [--mcp-config <workspace>/.mcp.json]
  [--add-dir <workspace>]
  [--add-dir /public]
  [--add-dir /workspace/upstream]
```

关键 CLI 参数：
- `--print`：非交互模式，输出到 stdout
- `--output-format stream-json`：逐行输出 JSON 事件流
- `--include-partial-messages`：包含未完成的 stream delta
- `--include-hook-events`：输出 hook 事件
- `--append-system-prompt`：追加系统提示词（由 `build_time_system_prompt` + `build_runtime_control_system_prompt` 拼接）
- `--add-dir`：挂载外部只读目录

### CLI 环境变量 (`_cli_env`)

子进程继承环境并通过以下调整：
- `PATH` 前缀追加 `/opt/venv/bin:/opt/claude-code/bin:/opt/node/bin`
- `ANTHROPIC_API_KEY` 设为 `llm-gateway`（所有请求走内部 LLM Gateway）
- `CLAUDE_CONFIG_DIR` 指向工作区 `.claude/`
- `HOME` 指向工作区

### CLI 配置初始化 (`_seed_cli_config`)

在启动 CLI 前，`_seed_cli_config(ws)` 会写入工作区下的 `.claude/.claude.json`，完成：
- `hasCompletedOnboarding = true`
- `customApiKeyResponses.approved` 中追加 `llm-gateway` API key
- 对应工作区的 `hasTrustDialogAccepted = true`

## 2.3 运行时会话状态记录

`native_terminal_runner.py` 使用 `_write_runtime_session()` 写 `meta/runtime_session.json`，会话状态经历以下阶段：

| state | 触发时机 |
|-------|---------|
| `starting` | CLI 启动前 (line 431) |
| `running` | 每收到一行 CLI 输出即更新 (line 229) |
| `exited` | CLI exit_code == 0 (line 305) |
| `failed` | CLI exit_code != 0 或收尾失败 (line 305/442) |
| `completed` | 最终产物写入成功 (line 442) |

`runtime_session.json` 的 JSON schema (version 1) 包含：
- `run_id`, `root_run_id`, `node_id`
- `conversation: {session_id, source: "claude_code_cli", model}`
- `terminal: {backend, runtime_terminal_id, pid}`
- `environment: {cwd, home_dir, claude_config_dir}`

对于 tmux 后端（`CLAUDE_NATIVE_TERMINAL_BACKEND=tmux`），terminal payload 额外包含 `container_id`、`container_name`、`socket_name`、`session_name`、`pane_id`。

## 2.4 推理循环与消息流

### Native Terminal 路径的 stdout 流处理

`_run_cli()` 通过 `asyncio.create_subprocess_exec` 启动子进程后：
1. 将 `prompt`（即 task prompt 全文）写入 `process.stdin`，随后关闭 stdin
2. 并发执行 `_read_stream(process.stdout, ...)` 和 `process.stderr.read()`
3. `_read_stream` 从 stdout 逐行读取 JSON 事件 (`_iter_stream_lines`)：每个事件通过 `_record_cli_line()` compact 后追加到 `sdk_messages.jsonl`

### 消息流形态

一条完整的 LLM 交互消息流如下：

```
[CLI 输出行]
  ├─ {"type":"system","subtype":"init","session_id":"...","model":"...","tools":[...]}
  ├─ {"type":"stream_event","event":{"type":"message_start","message":{"id":"...","model":"..."}}}
  ├─ {"type":"stream_event","event":{"type":"content_block_delta","delta":{"type":"text_delta","text":"..."}}}
  ├─ {"type":"assistant","content":[{"type":"text","text":"..."}]}
  ├─ {"type":"assistant","content":[{"type":"tool_use","name":"Read","id":"toolu_...","input":{...}}]}
  ├─ {"type":"user","content":[{"type":"tool_result","tool_use_id":"toolu_...","content":"..."}]}
  ├─ {"type":"assistant","content":[...]}
  ├─ ...（可能继续 tool_use / tool_result 来回）
  └─ {"type":"system","subtype":"success"}
```

### SDK 路径的消息流（参考）

旧版 SDK 路径 (`session_lifecycle.py:collect_sdk_messages`) 通过 `ClaudeSDKClient` 管理消息流：

1. `client = ClaudeSDKClient(options=options)`
2. `await client.__aenter__()` —— 进入 SDK 上下文
3. `await client.query(prompt)` —— 发送 prompt
4. `async for message in client.receive_response()` —— 逐条接收消息
5. 每条消息经 `normalize_sdk_message()` 规范化，再经 `compact_sdk_message()` 压缩记录

## 2.5 轮次限制与退出条件

### max_turns 限制

- Native Terminal 路径：由 `claude` CLI 自身管理，默认由 SDK 内部决定
- SDK 路径：通过环境变量 `CLAUDE_AGENT_MAX_TURNS` 配置，由 `session_lifecycle.py:prepare_sdk_runtime_context()` 读取 (line 209)。CLI 也尊重此环境变量，标准值为 `max_turns=300`

### 退出条件

退出条件分为以下几种：

1. **任务完成**：LLM 生成 `stop_reason: "end_turn"` 的 terminal success 消息。`_message_has_terminal_success()` 检测 `subtype == "success"` 且 `stop_reason in {"end_turn", ""}`
2. **轮次耗尽**：达到 max_turns 限制，模型自动停止
3. **错误退出**：CLI exit_code != 0（Native Terminal），或 SDK 抛出异常（SDK 路径）。`_cli_failure_detail()` (line 318) 提取 stderr 尾部 4000 字符 + stdout 错误信息
4. **Short-circuit 提前退出**（仅 SDK 路径）：当所有 required outputs 已在会话内被写入，且当前消息允许 short-circuit (terminal success 或 tool_result)，`_can_short_circuit_sdk_session()` 触发提前退出

## 2.6 产物输出与收尾

### 确定性导出阶段

无论哪条执行路径，在 LLM 推理完成后都会进入确定性导出阶段：

1. `generate_deterministic_export_node_outputs()`：生成确定性导出格式文件
2. `generate_report_exports()`：生成报告导出 (HTML/DOCX/PPTX)

### 产物收集

`election_agent._write_outputs()` (line 1017) 完成以下工作：

1. **写入调试产物**：`_write_debug_outputs()` → `debug_prompt.md` + `sdk_messages.jsonl`（debug 版）
2. **收集 artifacts**：`collect_output_artifacts(ws)` 扫描工作区输出文件
3. **提取摘要**：`_extract_summary()` 从消息中提取最终文本作为 summary
4. **结构输出映射**：`_structured_outputs_from_artifacts()` 按文件名后缀匹配结构化输出：

| 文件名后缀 | result key |
|-----------|-----------|
| `report.md` | `report_path` |
| `appendix.md` | `appendix_path` |
| `chart_manifest.json` | `chart_manifest_path` |
| `chart_bundle_manifest.json` | `chart_bundle_manifest_path` |
| `report.html` | `html_path` |
| `report.docx` | `docx_path` |
| `slides.pptx` | `pptx_path` |
| `pptx_outline.json` | `pptx_outline_path` |
| `report_workbook.xlsx` | `xlsx_path` |

5. **构建 result.json**：`build_result_payload()` 生成最终 result，包含：
   - `version`, `status`, `generated_at`
   - `workspace`, `run_id`, `node_id`
   - `summary`, `artifacts`, `structured`
   - `failure_type`, `reason_code`, `error`, `source_layer`
   - 数据源元数据：`data_source`, `external_data_available`, `knowledge_data_available` 等

6. **失败分类**：`_failure_metadata()` 根据错误文本分类：
   - `timeout` → `failed_timeout` / `launcher_timeout`
   - `cancelled` → `failed_canceled` / `run_canceled`
   - provider 级错误 (`api error: 400/401/403/404/429/500`) → `failed_provider`
   - SDK 级错误 (`claude_sdk_failed`) → `failed_provider`
   - 其他 → `failed_runtime` / `agent_failed`

### 必需输出校验

`_missing_required_outputs()` 在收尾时检查 `execution_contract.required_outputs` 是否全部产出。若缺失，最终 result 状态为 `failed`，错误消息为 `"agent_partial_output: missing required outputs (...)"`。

## 2.7 事件记录机制

`agent/event_recorder.py` 提供 SDK 消息事件的记录和压缩功能：

### `append_sdk_message(ws, entry, lock)`
异步追加一条消息到 `workspace/sdk_messages.jsonl`，使用 `asyncio.Lock` 保证线程安全。

### `compact_sdk_message(message)`
将原始 SDK 消息压缩为紧凑格式，针对不同 message type 做细化处理：

| 原始消息类型 | compact kind |
|------------|-------------|
| `subtype: "init"` | `kind: "subtype"`, 提取 `cwd`, `model`, `session_id`, `tools`, `agents`, `mcp_servers` |
| `subtype: "task_started"` | `kind: "task_started"`, 提取 `task_id`, `tool_use_id` |
| `subtype: "task_progress"` | `kind: "task_progress"`, 含 `progress_percent`, `total_tokens` 等 |
| `subtype: "task_notification"` | `kind: "task_notification"`, 含 `status`, `output_file` |
| `subtype: "success"/"error"/"failed"` | `kind: "subtype"`, 含 `is_error`, `stop_reason`, `duration_ms` |
| `event.type: "message_start"` | `kind: "message_start"`, 含 `input_tokens`, `output_tokens` |
| `event.type: "message_delta"` | `kind: "message_delta"`, 含 token 使用增量 |
| `content block: tool_use` | `kind: "tool_call"`, 含 `tool`, `tool_use_id`, `input_preview` |
| `content block: tool_result` | `kind: "tool_result"`, 含 `tool_use_id`, `is_error`, `content_preview` |
| `content block: text` | `kind: "text"`, 含 `text_preview` |

所有 text/content 预览均受 `agent/output_limits.py` 中定义的字符上限约束：

| 常量 | 值 |
|------|-----|
| `SDK_MESSAGE_TEXT_PREVIEW_MAX_CHARS` | 1600 |
| `SDK_MESSAGE_JSON_PREVIEW_MAX_CHARS` | 1200 |
| `SDK_MESSAGE_STATUS_TEXT_PREVIEW_MAX_CHARS` | 2000 |
| `SDK_MESSAGE_TOOL_INPUT_PREVIEW_MAX_CHARS` | 1600 |
| `SDK_MESSAGE_TOOL_RESULT_PREVIEW_MAX_CHARS` | 2000 |
| `SDK_MESSAGE_ASSISTANT_TEXT_PREVIEW_MAX_CHARS` | 3000 |
| `BASH_VIOLATION_SEGMENT_PREVIEW_MAX_CHARS` | 50 |
| `EXECUTION_SUMMARY_PREVIEW_MAX_CHARS` | 500 |

## 2.8 SDK 会话元数据（旧版 SDK 路径参考）

`agent/sdk_session.py` 管理 SDK 会话的持久化元数据：

- **`meta/sdk_session.json`**：当前会话的元数据快照，包含 `session_id`, `model`, `session_phase`, `started_at`, `parent_session_id` 等
- **`meta/sdk_sessions.jsonl`**：会话 lineage 日志，按时间顺序记录每次新建的会话
- **`SessionLineageTracker`**：管理会话 lineage 的写入，自动检测新 session_id 并记录 `session_order`

### SessionPhase 枚举 (`common/sdk_events.py`)

```python
class SessionPhase(StrEnum):
    ANALYSIS = "analysis"      # 分析阶段（默认）
    DISCOVERY = "discovery"    # 发现阶段
```

Native Terminal Runner 固定使用 `SESSION_PHASE = "execute"` 作为其 CLI 会话的阶段标签。
