# 01 - 概述

## Docker 容器启动在流水线中的位置

Docker 容器启动位于整个流水线分层架构的**第 7 层**，处于 **Workspace Sync（工作区同步）之后、Agent Session（Agent 会话）之前**。

在整个请求处理管线中，它的上下游关系如下：

```
Chat API 接入 (第4层)
  → Planning (第5层, 工作流计划生成)
    → DAG Construction (第6层, DAG 构建与验证)
      → **Docker 容器启动 (第7层, 本层)**
        → Agent Session (第8层, Agent SDK 执行)
          → Export (第9层, 结果导出)
```

也就是说，第 7 层负责将前序步骤生成的工作流计划（workflow DAG）和已经同步到位的 workspace skills/agents 资产"翻译"为实际的 Docker 容器运行环境，并将执行权移交给 Agent 运行时的 SDK 或 CLI。

## 核心入口：`execute_workflow()`

整个第 7 层的统一入口函数是 `orchestrator/chat/execute_api.py` 中的 `execute_workflow()`（约第 189 行）。它是一个异步函数，签名如下：

```python
async def execute_workflow(
    runtime: ExecuteRuntime,
    req,
    http_req,
    idempotency_key: str | None,
    *,
    get_deps_fn: Callable[[Any], Any],
    execute_with_dag_scheduler: Callable[..., Awaitable[dict[str, Any]]],
    execute_single_agent: Callable[..., Awaitable[dict[str, Any]]],
) -> dict[str, Any]:
```

其中 `get_deps_fn`、`execute_with_dag_scheduler`、`execute_single_agent` 通过依���注入传入，使得这一层与具体的 FastAPI 应用对象解耦。

## `ExecuteRuntime` dataclass

`ExecuteRuntime`（同文件约第 51 行）是一个 frozen dataclass，封装了执行阶段所需的基础设施引用：

```python
@dataclass(frozen=True)
class ExecuteRuntime:
    storage: Any                    # Chat 存储层（workflow/session 读写）
    orchestration_engine: Any       # 编排引擎引用
    logger: logging.Logger          # 日志记录器
    normalize_workflow_payload: Any # workflow 规范化的函数引用
```

## 两种执行模式

`execute_workflow()` 在入口处通过 `determine_execution_mode()` 函数（`orchestrator/chat/execution.py` 约第 244 行）判断当前 workflow 应走哪种执行路径：

### 判断逻辑

```python
def determine_execution_mode(workflow_data: dict, req) -> tuple[bool, list]:
    executable_nodes = [
        n for n in nodes
        if n.get("enabled", True) and n.get("kind", "agent") == "agent"
    ]
    edge_count = len(workflow_data.get("edges") or [])
    use_dag_scheduler = len(executable_nodes) > 1 and edge_count > 0
    if hasattr(req, 'useDagScheduler'):
        use_dag_scheduler = len(executable_nodes) > 1 and edge_count > 0 and req.useDagScheduler
    return use_dag_scheduler, executable_nodes
```

判断规则：
- 可执行的 agent 节点数 > 1 且边数 > 0：走 **DAG 调度模式**
- 否则：走 **单 Agent 模式**
- 前端请求可以通过 `useDagScheduler` 标志位显式控制

### 模式一：DAG 调度模式 (`execute_with_dag_scheduler`)

当 workflow 包含多个 agent 节点且存在数据依赖边时，系统使用 `execute_with_dag_scheduler()`（约第 448 行）启动多节点 DAG 并发调度。这条路径的特征是：
- 从 workflow 数据重建 `GeneratedDAG` 对象
- 创建 `DAGScheduler` 实例，由其管理同层并发与层级间的拓扑依赖
- 采用长生命周期容器 + `docker exec` 的复用策略（详见 03-容器生命周期）

### 模式二：单 Agent 模式 (`execute_single_agent`)

当 workflow 只有一个 agent 节点（或没有边关系）时，系统走 `execute_single_agent()`（约第 696 行）路径。这条路径的特征是：
- 直接构建 task_prompt 字符串
- 启动一次性容器（或复用已有的单 Agent 容器）
- 执行完毕后直接等待容器退出

## 执行分派：`_dispatch_execution()`

`execute_workflow()` 在完成一系列前置检查后（幂等性、LLM 配置验证、资源预检等），最终调用 `_dispatch_execution()`（约第 406 行）将执行分派到正确的模式：

```python
async def _dispatch_execution(...):
    if use_dag_scheduler:
        resp = await execute_with_dag_scheduler(...)
    else:
        resp = await execute_single_agent(...)
```

## 执行前检查清单

`execute_workflow()` 入口处按顺序执行以下检查：

| 步骤 | 函数 | 作用 |
|------|------|------|
| 1 | `validate_session_and_workflow()` | 验证 session 存在、workflow 有效 |
| 2 | `resolve_user_request_for_execution()` | 从 workflow 快照恢复原始用户意图 |
| 3 | `_resolve_execution_external_data()` | 解析外部数据开关 |
| 4 | `_resolve_execution_agent_team()` | 解析 Agent Team 开关 |
| 5 | `check_workflow_requires_llm()` | 检查是否至少有一个非 deterministic 节点 |
| 6 | `validate_llm_config()` | 确保 ANTHROPIC_API_KEY 已配置 |
| 7 | `build_idempotency_key()` | 构建幂等键 |
| 8 | `_handle_existing_idempotency()` | 检查已有运行，避免重复执行 |
| 9 | `_claim_reserved_run()` | 预留 run_id 并注册幂等记录 |
| 10 | `run_resource_precheck()` | 资源审计预检 |
