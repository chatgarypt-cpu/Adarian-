# 02 - 启动器分析

## `execute_workflow()` 完整流程

`orchestrator/chat/execute_api.py` 中的 `execute_workflow()`（约第 189 行）是整个容器启动管线的顶级协调函数。它的完整执行流程分为三个阶段：

### 阶段一：校验与幂等（同步）

1. **Session/Workflow 校验**：调用 `validate_session_and_workflow()`（`execution.py` 第 104 行），验证 session 存在且 workflow 数据有效。校验通过后，workflow 数据被规范化（normalize）并写回 storage。
2. **用户意图恢复**：调用 `resolve_user_request_for_execution()`（`execution.py` 第 231 行），优先从 workflow 快照中提取原始 userRequest，避免 `/execute` 等控制消息覆盖生成时的用户意图。
3. **外部数据 / Agent Team 解析**：`_resolve_execution_external_data()` 和 `_resolve_execution_agent_team()` 分别根据 admin config 解析外部搜索数据和 agent team 的启用状态。
4. **LLM 配置检查**：如果 workflow 中存在非 deterministic agent 节点（即需要 LLM 调用），则调用 `validate_llm_config()` 确保 `ANTHROPIC_API_KEY` 已配置。
5. **模式判断**：`determine_execution_mode()` 根据节点数和边数决定走 DAG 调度还是单 Agent 路径。
6. **幂等键构建**：`build_idempotency_key()` 基于 HTTP 头、workflowId、sessionId、配置标志位和 workflow 数据哈希生成幂等键。
7. **已有运行检查**：`_handle_existing_idempotency()` 查询 Redis，若幂等键命中已有运行，直接返回现有 run 的 status，避免重复执行。
8. **Run ID 预留**：`_claim_reserved_run()` 通过 Redis `SET NX` 原子地预留 run_id 并写入幂等记录。

### 阶段二：资源预检（同步）

`run_resource_precheck()`（`execution.py` 第 496 行）在执行前对所需资源进行审计，检查 knowledge MCP 运行时配置，生成 `resource_audit` 字典。

### 阶段三：执行分派（异步）

`_dispatch_execution()`（`execute_api.py` 第 406 行）将控制权移交给两种执行模式之一：

```python
if use_dag_scheduler:
    resp = await execute_with_dag_scheduler(...)
else:
    resp = await execute_single_agent(...)
```

执行完毕后，`execute_workflow()` 在返回前完成：
- 将 `resourceAudit` 附加到响应
- 调用 `_bind_workflow_to_run()` 绑定 workflow/session 到 run
- 调用 `update_idempotency_on_success()` 更新幂等性记录的最终状态

## DAG 调度模式：`execute_with_dag_scheduler()`

位于 `execute_api.py` 约第 448 行。这是多节点并发调度路径的核心函数。

### 1. `rebuild_dag_from_workflow()`

`execution.py` 第 554 行。将规范化后的 workflow 字典重建为 `GeneratedDAG` 对象：

```python
nodes = [
    DAGNode(
        id=n["id"],
        label=n.get("label", n["id"]),
        kind=n.get("kind", "agent"),
        agent_config=_build_runtime_agent_config(n),
        block_profile=_build_runtime_block_profile(n),
        enabled=n.get("enabled", True),
        critical=n.get("critical", True),
        layer=n.get("layer", 0),
        order=n.get("order", 0),
    )
    for n in workflow_data.get("nodes", [])
]
edges = [
    DAGEdge(from_node=e["from"], to_node=e["to"],
            edge_type=e.get("type", "data_dependency"),
            condition=e.get("condition", ""))
    for e in workflow_data.get("edges", [])
]
```

其中 `_build_runtime_agent_config()` 负责将前端的 agentConfig 转换为运行时可用格式，包括解析 skill_id（支持 SkillRegistry 回退和 GENERIC_AGENT_SKILL_ID 兜底）。

### 2. `prepare_dag_workspace()`

`execution.py` 第 628 行。这是 DAG 模式中专用于工作区准备的函数。它执行以下操作：

1. **布局初始化**：通过 `_prepare_workspace_layout()` 调用 `WorkspaceInitializer`（`workspace_initializer.py`），在 `/workspace/<run_id>/` 下创建标准目录结构（`data/`, `input/`, `output/`, `debug/`, `code/`, `.claude/`, `meta/`）。

2. **Workflow 快照**：调用 `snapshot_workflow_dag()` 将规范化后的 workflow JSON 写入 workspace。

3. **Skills 快照**：收集所有 agent 节点的 skill_id 列表，调用 `current_skills_snapshot_meta()` 获取当前 skills 的 revision 和 fingerprint，写入 `skills_used.json`。

4. **Node Runs 元数据**：为每个 enabled agent 节点通过 `build_node_run_id()` 生成独立的 node_run_id，写入 `meta/node_runs.json`。

5. **配置快照**：调用 `build_effective_config_snapshot()` 收集所有配置存储（runtime、llm、admin）的当前状态，写入 `run_manifest.json`（通过 `snapshot_run_manifest()`）。

### 3. `write_dag_run_metadata()`

`execution.py` 第 713 行。将 DAG 运行的元数据写入 Redis：

```python
def write_dag_run_metadata(deps, run_id, ...):
    _reset_dag_runtime_state(deps=deps, run_id=run_id, ...)
    _run_state_store(deps).set_run_meta(run_id, _dag_run_meta(...))
    deps.redis_client.zadd(deps.run_index_key, {run_id: timestamp})
    _apply_dag_run_ttl(deps, run_id)
    _start_dag_run_audit_record(deps=deps, run_id=run_id, task_prompt=task_prompt)
```

写入内容包括：
- `status`: "starting"
- `mode`: "dag_scheduler"
- `total_nodes`: enabled agent 节点总数
- `workspace`: workspace 路径
- `created_at`: ISO 时间戳
- `progress`: "0"

同时将 run_id 加入 Redis sorted set 索引（`run_index_key`），并设置 TTL 过期时间。

### 4. 执行队列（`execution_job_store`）

`execute_with_dag_scheduler()` 在执行路径上首先尝试入队：

```python
if not _queue_dag_execution_job(deps=deps, ...):
    asyncio.create_task(_run_dag_task(...))
```

`_queue_dag_execution_job()`（`execute_api.py` 第 775 行）检查 `deps.execution_job_store` 是否存在：
- **如果存在**（RuntimeWorker 模式）：将 DAG 执行任务入队列，立即返回 HTTP 响应。后台 worker（`runtime_worker.py`）会消费该任务并调用 `_run_dag_task()` 异步执行。
- **如果不存在**（内联模式）：通过 `asyncio.create_task()` 直接在事件循环中启动 `_run_dag_task()`。

`_run_dag_task()`（第 896 行）是 DAG 执行的真正引擎。它创建 `DAGScheduler` 实例（通过 `_build_dag_scheduler()`），然后迭代 `scheduler.execute()` 返回的 async generator，逐事件处理：

```python
async for event in scheduler.execute(dag, run_id, context, skip_completed=skip_completed):
    final_status = await _handle_dag_event(...) or final_status
```

事件类型包括 `workflow.start`、`node.start`、`node.complete`、`node.error`、`workflow.complete`、`workflow.error`。每个事件通过 Redis pub/sub 对外发布，SSE 推送实况进度。

## 单 Agent 模式：`execute_single_agent()`

位于 `execute_api.py` 约第 696 行。这是单节点执行路径的核心函数。

### 1. `build_single_agent_task_prompt()`

`execution.py` 第 797 行。将 workflow 中的节点信息转换为自然语言中文 prompt：

```python
def build_single_agent_task_prompt(workflow_data, user_req, req) -> str:
    task_parts = ["请执行以下选举推演/分析任务："]
    task_parts.append(f"任务名: {wf_name}")
    ...
    for node in nodes:
        step_no += 1
        task_parts.append(f"{step_no}. {label}")
    ...
    task_parts.append("- 仅使用 /public 下的数据源完成分析（只读）。")
    task_parts.append("- 将关键产物写入 output/ 目录")
```

生成的 prompt 包含任务名、用户需求、步骤列表、数据约束和输出要求。

### 2. `launch_single_agent_run()`

`execute_api.py` 第 610 行（内部函数 `_launch_single_agent_run`）。调用 `deps.launcher.launch()` 启动容器：

```python
result = await asyncio.to_thread(
    deps.launcher.launch,
    task_prompt=task_prompt,
    run_id=run_id,
    enable_external_data=enable_external_data,
    model_override=model_override,
)
```

容器启动成功后：
1. 调用 `write_single_agent_run_metadata()` 写入 Redis 元数据。
2. 调用 `schedule_monitor_task()` 创建后台监控任务（`RunContainerMonitor`）。
3. 调用 `snapshot_single_agent_run()` 对 workflow DAG 和 skills 做快照。

### 3. 执行队列路径

与 DAG 模式类似，单 Agent 模式也可通过 `_queue_single_agent_execution_job()` 入队列。如果 `execution_job_store` 存在，任务被入队后立即返回 `queued` 状态；否则直接启动容器。

队列模式下，`execute_single_agent()` 返回 status 为 `"queued"` 的响应，后台 worker 的 `execute_single_agent_job()` 在消费到任务后执行真正的容器启动。

## 幂等性机制

幂等性机制确保同一请求在短时间内重复提交时不会创建重复运行。核心实现在 `orchestrator/chat/execution.py` 中。

### `build_idempotency_key()`

`execution.py` 第 367 行。构建三步：

1. **规范化**：`normalize_idempotency_key()` 将客户端传入的 `Idempotency-Key` HTTP 头规范化为 `{prefix}/{uuid}` 格式。
2. **作用域**：`build_scope("POST", "/api/chat/execute", headers)` 生成 Redis key 前缀。
3. **请求哈希**：`request_hash()` 对 `{workflowId, sessionId, enable_external_data, enableAgentTeam, workflow}` 做确定性哈希。

返回三元组 `(idem_key, idem_rkey, idem_req_hash)`。

### Redis 锁：`reserve_and_claim_idempotency()`

`execution.py` 第 408 行。原子性地预留 run_id：

```python
claimed = deps.redis_client.set(
    idem_rkey,
    json.dumps({"run_id": reserved_run_id, "req_hash": idem_req_hash, ...}),
    nx=True,     # 仅当 key 不存在时设置
    ex=inflight_ttl_seconds(),  # 设置过期时间
)
```

`SET NX` 保证原子性。如果 key 已存在，返回 None，上层进入"重用已有运行"路径。

### 已有运行重用

`_handle_existing_idempotency()`（`execute_api.py` 第 324 行）读取 Redis 中已有的幂等记录：

- 如果 `req_hash` 不匹配 → HTTP 409 Conflict（"Idempotency-Key 与请求内容不一致"）
- 如果匹配 → 通过 `handle_idempotency_existing_run()` 返回现有 run 的信息（含 `reused: true`）

### `_claim_reserved_run()`

`execute_api.py` 第 364 行。处理"预留失败但已有记录"的竞态场景：

- 如果 `reserve_and_claim_idempotency()` 返回 None 但 Redis 中已有记录 → 查找已有 run 的 meta，返回 `reused: true` 响应
- 如果连已有记录都不存在 → HTTP 202（"workflow 正在执行中"）

## RuntimeWorker 与执行队列

`orchestrator/runtime_worker.py` 中的 `RuntimeWorkerApp` 是可选的后台 worker，通过环境变量 `RUNTIME_WORKER_ENABLED` 控制开关（默认关闭）。

### 架构

```
FastAPI 主进程                     RuntimeWorker (可选)
     │                                     │
     │ execute_workflow()                   │
     │   → enqueue to execution_job_store   │
     │   → return {status: "queued"}        │
     │                                     │ poll execution_job_store
     │                                     │ claim job (lease)
     │                                     │ execute job
     │                                     │   → _execute_runtime()
     │                                     │ mark job complete
```

### Job 类型

`execution_job_store.enqueue()` 支持两种 job 类型：
- `"dag_execution"`：DAG 调度模式的任务
- `"single_agent_execute"`：单 Agent 模式的任务

每个 job 通过 lease 机制实现分布式协调：worker 取 job 时获取租约，执行期间周期续约，执行完毕后标记完成。若 worker 宕机，租约到期后其他 worker 可以接管。
