# 03 - 容器生命周期

## 容器完整生命周期

系统中 Docker 容器的生命周期经历四个阶段：**启动 → 执行 → 退出 → 清理**。不同执行模式下的容器管理策略有显著差异。

### 生命周期总览

```
┌──────────────────────────────────────────────────────────────────┐
│                    容器生命周期总览                              │
│                                                                  │
│  [启动]           [执行]            [退出]           [清理]     │
│   │                │                 │                │         │
│   ├─ 镜像拉取      ├─ docker exec    ├─ 正常退出(0)   ├─ 停止容器│
│   ├─ 挂载构建      ├─ SDK messages   ├─ 异常退出(≠0)  ├─ 强制移除│
│   ├─ 网络接入      ├─ audit.jsonl    ├─ 超时 kill     ├─ GC 回收 │
│   ├─ 环境变量      ├─ 心跳更新       ├─ 取消信号      ├─ 归档保留│
│   ├─ 资源限制      └─ 结果写入       └─ orphan reap   └─ 审计关闭│
│   └─ 健康检查                                                  │
└──────────────────────────────────────────────────────────────────┘
```

## 长生命周期容器策略（DAG 模式专用）

DAG 调度模式采用**长生命周期容器 + `docker exec` 复用**策略，这是整个系统最核心的容器设计决策之一。

### 设计原理

`orchestrator/agent/launcher.py` 中 `RunContainerManager._start_container()`（约第 879 行）负责创建持久化容器：

```python
def _run_kwargs(self, *, docker_client: Any) -> dict[str, Any]:
    return {
        "image": self.launcher.agent_image,
        "command": ["sleep", "infinity"],  # 关键：无操作挂起
        "detach": True,
        "environment": self._container_env(),
        "network": self.launcher.agent_network,
        "init": True,
        "user": "1000:1000",
        "name": self.container_name,       # agent-{run_id}
        "auto_remove": False,
        "labels": {
            "orchestrator.managed": "true",
            "orchestrator.run_id": self.run_id,
            "orchestrator.kind": "agent",
        },
        "mounts": self.launcher._build_isolated_mounts(...),
        "healthcheck": self._healthcheck(),
        "extra_hosts": {"host.docker.internal": "host-gateway"},
    }
```

容器以 `sleep infinity` 命令启动并 detach，等待后续通过 `docker exec` 注入实际运行命令。

### 容器命名与复用

容器命名为 `agent-{run_id}`，使得同一 DAG run 的所有节点共享同一个容器运行时。在 `RunContainerManager.start()`（约第 636 行）中：

1. 首先调用 `_reusable_container()` 检查是否已有同名容器。
2. **如果容器已存在**：跳过启动，直接复用（处理 orchestrator 重启后恢复场景）。
3. **如果容器不存在**：检查容量 `wait_for_agent_capacity_async()`，然后通过 `docker_client.containers.run(**self._run_kwargs())` 创建新容器。

`_start_container()` 的复用逻辑覆盖三种状态：
- **running**：直接返回现有容器引用，记录日志 `run_container_reuse_running`。
- **created**（未启动）：调用 `existing.start()` 启动后返回。
- **exited/dead**：先 `remove(force=True)` 移除旧容器，再重新创建。

### `docker exec` 复用机制

`RunContainerManager.exec_node()`（约第 683 行）通过 `docker exec` 在已运行的容器中执行节点命令：

```python
exec_id = await run_docker_call(
    docker_client.api.exec_create,
    self.container_id,
    exec_cmd,              # /app/agent/run_native_terminal_node.sh --node-id=xxx
    environment=self._node_env(...),
    workdir=node_workspace,  # /workspace/{run_id}/output/{node_id}
    user="1000:1000",
)
```

执行前的重要步骤：
1. `_materialize_node_runtime()`：为当前节点同步 skills 到节点 workspace 的 `.claude/skills/`，并生成 settings.json。
2. `_cleanup_reused_node_processes()`：如果是复用容器，通过 Python 脚本扫描 `/proc` 清理上一次执行残留的进程（SIGTERM → SIGKILL 两步）。
3. `_emit_node_started()`：触发 `on_container_started` 回调，通知调度器节点已启动。
4. `_run_exec()`：实际执行 docker exec，包括启动 audit/sdk JSONL tail task，等待执行完毕，解析 exit code。

### 长生命周期容器的优势与代价

**优势**：
- 避免每个节点启动/停止容器的开销（镜像层缓存已热）
- 节点间可共享 /workspace 下的文件系统状态
- skills sync 只需在容器启动时做一次（后续 exec_node 只做增量同步）

**代价**：
- 容器健康需要额外的 healthcheck 保障
- orchestrator 重启后需要恢复逻辑（通过容器名查找已有容器）
- 残留进程需要 `_cleanup_reused_node_processes` 主动清理
- 孤儿运行（orphan run）的回收逻辑更复杂

## RunContainerMonitor 容器监控

`orchestrator/container_monitor.py` 中的 `RunContainerMonitor`（第 16 行）负责监控单 Agent 模式下的容器运行状态。它实现 `__call__` 使其可被 `asyncio.create_task` 调度。

### 监控流程

```python
async def __call__(self, run_id: str, container_id: str, workspace: str) -> None:
    stop = asyncio.Event()
    tail_tasks = self._start_tail_tasks(run_id, workspace, stop)
    try:
        status, exit_code, error = await self._wait_terminal_status(run_id, container_id)
        finished_at = datetime.now(timezone.utc).isoformat()
        await self._persist_terminal_status(run_id, status, exit_code, finished_at, error)
        self._end_audit_run(run_id, status)
    finally:
        stop.set()
        await self._stop_tail_tasks(tail_tasks)
        await self._remove_container(container_id, run_id)
```

监控任务完成三件事：

1. **启动 JSONL Tail**：`_start_tail_tasks()` 创建两个 asyncio task 分别尾随容器的 `audit.jsonl` 和 `sdk_messages.jsonl`，将增量内容推送到 Redis pub/sub（SSE 事件流）。

2. **等待容器退出**：`_wait_terminal_status()` 通过 `docker.from_env().api.wait(container_id)` 阻塞等待容器结束，获取 exit code。

3. **持久化与清理**：
   - 状态解析：`exit_code == 0` → `"completed"`，否则 → `"error"`。但如果 run 的当前状态已是 `canceled`/`canceling`，则最终状态为 `"canceled"`。
   - `_persist_terminal_status()`：将 status、exit_code、finished_at 写入 `run_state_store` 并通过 `publish_run_event_async()` 发布 `run_status` 事件。
   - `_end_audit_run()`：通知 audit logger 关闭当前 run 的审计记录。
   - `_remove_container()`：默认移除已退出的容器，除非 `KEEP_AGENT_CONTAINERS=true`。

### `schedule_monitor_task()`

`orchestrator/chat/execution.py` 第 901 行。从 `app.state` 中获取 `run_monitor_container` 回调，将其包装为 `asyncio.create_task()`。这使得监控任务在后台运行，不阻塞 HTTP 响应。

`orchestrator/runs/lifecycle.py` 第 102 行。此函数定期更新 run 的进度和输入 token 基线，供 stall guard（卡死检测）使用：

```python
def mark_run_progress_heartbeat(deps, run_id, *, progress=None, timestamp=None):

        "stall_input_tokens_baseline": str(max(0, current_llm_input_tokens)),

    if progress is not None:
        mapping["last_progress_value"] = str(p)
        mapping["progress"] = str(p)
```

心跳更新时机：
- DAG 模式：每个 `node.complete` 事件触发时（`_mark_dag_progress_if_needed` → `_mark_node_progress`）

- LLM usage 更新时（stall guard 内部使用）

## Run 状态机

整个 Run 的状态在 Redis 中通过 `run_state_store.set_run_meta()` 维护。状态转换如下：

```
      [用户提交执行]
            │
            ▼
        ┌───────┐
        │ queued│  ← 仅当 execution_job_store 存在时（RuntimeWorker 模式）
        └───┬───┘
            │ worker 消费 job
            ▼
       ┌──────────┐
       │ starting │  ← execute_workflow() 返回前写入
       └─────┬────┘
             │ 容器启动成功
             ▼
       ┌──────────┐
       │ running  │  ← workflow.start / node.start 事件触发
       └─────┬────┘
             │
      ┌──────┼──────────┐
      │      │          │
      ▼      ▼          ▼
 ┌─────────┐ ┌────────────────────┐ ┌───────┐
 │completed│ │completed_with_errors│ │ error │
 └─────────┘ └────────────────────┘ └───────┘
      │              │                    │
      │              │              ┌─────┴─────┐
      │              │              │  canceled │ ← 用户取消/卡死检测
      │              │              └───────────┘
      └──────────────┴──────────────────────┘
                       │
                 终端状态（TERMINAL）
```

### 关键状态常量

定义在 `execute_api.py` 第 65-71 行：

```python
_TERMINAL_RUN_STATUSES = frozenset({
    "completed", "completed_with_errors", "completed_with_issues", "error", "canceled"
})
_ACTIVE_NODE_STATUSES = frozenset({
    "pending", "running", "started", "starting", "queued", "in_progress", "canceling"
})
_TERMINAL_NODE_STATUSES = frozenset({"completed", "error", "skipped", "canceled"})
```

### 状态转换触发点

| 状态 | 触发点 | 源码位置 |
|------|--------|----------|
| `queued` | execution_job_store.enqueue() 成功后 | `execute_api.py:_queue_single_agent_execution()` |
| `starting` | write_dag_run_metadata() / execute_with_dag_scheduler() 返回前 | `execution.py:_dag_run_meta()` |
| `running` | workflow.start / node.start 事件 | `execute_api.py:_mark_running_run_status_if_needed()` |
| `completed` | workflow.complete 事件 / 容器 exit_code==0 | `execute_api.py:_set_completed_run_status()` |
| `completed_with_errors` | 节点状态回推（部分 error） | `execute_api.py:_infer_terminal_status_from_node_states()` |
| `error` | workflow.error 事件 / 容器 exit_code!=0 | `execute_api.py:_set_error_run_status()` |
| `canceled` | 用户取消/卡死检测 | `lifecycle.py:_stop_container_best_effort()` |

### `_ensure_terminal_run_status()`

`execute_api.py` 第 1133 行。这是状态机的**兜底机制**，在 `_run_dag_task()` 的 `finally` 块中调用，确保无论如何 Run 都会进入终端状态：

```python
async def _ensure_terminal_run_status(logger, deps, run_id):
    current = normalize_status(run field "status")
    if current in _TERMINAL_RUN_STATUSES:
        return  # 已经在终端状态，无需处理

    # 尝试从 node_states 推断
    inferred = _infer_terminal_status_from_node_states(deps, run_id)
    if inferred:
        # 写入终端状态 + finished_at + 发布 run_status 事件
        ...

    # 兜底：标记为 error
    await store.set_run_meta_async(run_id, {
        "status": "error",
        "finished_at": finished_at,
        "error": "missing_terminal_workflow_event",
    })
```

## 容器网络

系统定义了两个 Docker bridge 网络，在 `docker/docker-compose.yml` 第 296-303 行声明：

### `election-network`
- **网络名**：`election-network`
- **驱动**：bridge
- **用途**：系统核心组件间通信。orchestrator、Redis、frontend-proxy 等服务均接入此网络。

### `agent-network`（`election-agent-network`）
- **网络名**：`election-agent-network`（通过 `AGENT_NETWORK` 环境变量可覆盖）
- **驱动**：bridge
- **用途**：Agent 容器接入。Agent 容器只能通过此网络访问 orchestrator 的 LLM Gateway 端口，与其他内部服务（如 Redis）隔离。

### 网络隔离设计

orchestrator 容器同时接入两个网络（`docker-compose.yml` 第 207-208 行），充当 agent 网络与内部网络的**网关**。Agent 容器只接入 `agent-network`（通过 `AgentLauncher.__init__` 的 `agent_network` 参数传入，默认 `"election-agent-network"`）。

Agent 容器通过 `host.docker.internal:host-gateway` extra_host 可以访问宿主机（用于部分 MCP server），通过 orchestrator 容器名访问 LLM Gateway：

```python
"ANTHROPIC_BASE_URL": f"http://{orchestrator_container_name}:{port}/llm-gateway/run/{run_id}/node/{node_id}"
```

## 容器健康检查

`RunContainerManager._healthcheck()`（launcher.py 约第 992 行）为长生命周期容器配置 Docker healthcheck：

```python
{
    "test": ["CMD-SHELL", "test -d /workspace/{run_id} && test -d /public && test -r /public"],
    "interval": 1_000_000_000,    # 1 秒
    "timeout": 3_000_000_000,     # 3 秒
    "start_period": 1_000_000_000, # 1 秒
    "retries": 15,
}
```

检查逻辑：确认 `/workspace/{run_id}` 目录存在、`/public` 目录存在且可读。这验证了 volume 挂载正确完成。

容器启动后，`_wait_until_healthy()` 最多等待 30 秒（`RUN_CONTAINER_HEALTHCHECK_WAIT_SECONDS`）直到健康检查通过，否则抛出 `RuntimeError`。

## 孤儿运行回收（Orphan Run Reaper）

`orchestrator/runs/lifecycle.py` 中的 `reap_orphan_runs_once()`（第 1102 行）是一个周期性后台任务，用于回收因 monitor task 丢失而卡在 active 状态的运行。

回收逻辑（`maybe_reap_orphan_run()` 约第 948 行）：
1. 从 Redis events 推断终端状态（`infer_terminal_status_from_events()`）。
2. 检查容器实际状态（`inspect_container_state()`）：
   - 如果容器不在运行且非 DAG shell → 立即 finalize。
   - 如果容器在运行但是 DAG shell → 检查活跃节点是否已完成（`_check_active_node_completed_on_disk()`），通过 result.json 或 progress CSV 判断。
3. 超时检查：运行超过 `orphan_run_stale_seconds()`（默认 900 秒）且无活动 → 标记为 `error`。
4. 对于 queued 但无执行任务的运行，使用更短的 `orphan_run_queued_stale_seconds()`（默认 300 秒）。

回收后执行：
- `finalize_orphan_run()`：写入终端状态和 `orphan_reaped_at` 时间戳
- `_stop_and_remove_leaked_container()`：停止并移除残留的容器

## 容器 GC（Garbage Collection）

`orchestrator/utils/container_gc.py` 提供退出容器的后台 GC。`gc_exited_agent_containers_once()`（第 55 行）周期性（默认 120 秒间隔）列出所有 `status=exited` 且 `orchestrator.managed=true` 的容器，对超过 `container_gc_min_age_seconds()`（默认 120 秒）的容器执行 `force=True` 移除。

可通过 `KEEP_AGENT_CONTAINERS=true` 完全禁用 GC（用于调试），通过 `CONTAINER_GC_ENABLED=false` 单独关闭 GC。

## 卡死检测（Stall Guard）

`detect_and_mitigate_stall_on_llm_usage()`（`lifecycle.py` 第 602 行）在 LLM usage 写入时触发检测：

- **空闲阈值**：`run_stall_idle_seconds()`（默认 600 秒）内无进度心跳
- **输入增长阈值**：`run_stall_min_input_growth()`（默认 1 token）以上的 input token 增长
- **处置**：发布 `run_stall_detected` 事件，标记状态为 `canceled`，停止关联容器
