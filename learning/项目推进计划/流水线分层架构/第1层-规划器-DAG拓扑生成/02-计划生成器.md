# 02 - 计划生成器

## plan_generator.py 的核心流程

`orchestrator/dag/plan_generator.py` 是 Planner 的执行中枢。它不直接触碰 LLM 或 Agent SDK，而是通过 **策略模式** + **传输层** 将生成请求委托出去。核心类是 `WorkflowPlanGenerator`，其配置由 `WorkflowPlanGeneratorConfig` dataclass 冻结提供。

### WorkflowPlanGeneratorConfig 配置项

```python
@dataclass(frozen=True)
class WorkflowPlanGeneratorConfig:
    llm_gateway_url: str          # LLM Gateway 地址
    model: str                    # 工作流生成模型名
    timeout_s: float              # 超时秒数 (workflow_gen_timeout_s)
    max_attempts: int             # 最大修复尝试次数
    anthropic_version: str        # anthropic-version 请求头
    structured_outputs_beta: str  # anthropic-beta 请求头（如 "output-json-schema-2025-06-15"）
    auth_headers: dict[str, str]  # 认证头
    allowed_mode: str             # 节点模式 (open/skills_only/skills_plus_custom)
    custom_prefix: str            # 自定义节点前缀
```

参数来源均在 `engine.py` 的 `OrchestrationEngine` 中通过 `load_settings()` 读取。

### WorkflowPlanGenerator 的两个主方法

```python
class WorkflowPlanGenerator:
    config: WorkflowPlanGeneratorConfig
```

#### generate_planner_sdk() -- Claude Agent SDK 驱动

路径：`plan_generator.py` -> `generate_with_planner_sdk_request()` -> `plan_transport.py:query_planner_sdk()`

执行流程：

1. 构造 `WorkflowPlanningRequest`（含 prompt builder、repair prompt builder、normalizer、validator）
2. 进入 `WorkflowPlanningRepairLoop.generate()`（定义在 `plan_repair_loop.py`）
3. repair loop 调用 `transport` lambda，执行 `query_planner_sdk()`
4. `query_planner_sdk()` 在 `plan_transport.py` 中：
   - 创建临时目录 `workflow-planner-*`
   - 调用 `sync_workspace_skills()` 将 `claude-runtime/skills/` 下的 skill 文件同步到临时 workspace 的 `.claude/skills/`
   - 构造 `ClaudeAgentOptions`：仅允许 `Skill` 工具，禁止 Read/Write/Edit/Bash/WebSearch/Agent 等
   - `permission_mode` 设为 `"acceptEdits"`
   - `system_prompt` 为 `claude_code` preset
   - 通过 `ClaudeSDKClient` 发送 prompt 并收集 assistant 响应文本
5. 返回 `TransportResponse(text=..., thinking="")`

关键约束：SDK 通道的 planner Agent 只能使用 Skill 工具（即读取注入的 `dag-planner` Skill 内容），不能执行任何文件操作或外部调用。

#### generate_llm() -- 直接 LLM API 调用

路径：`plan_generator.py` -> `generate_with_llm_request()` -> `plan_transport.py:query_llm_transport()`

执行流程：

1. 获取 `WorkflowPlan.model_json_schema(by_alias=True)` 作为 structured output schema
2. 创建 `httpx.AsyncClient`（超时 = `config.timeout_s`）
3. 进入同样的 `WorkflowPlanningRepairLoop.generate()`
4. repair loop 调用 `transport` lambda，执行 `query_llm_transport()`
5. `query_llm_transport()` 在 `plan_transport.py` 中：
   - 构造请求体：`model`, `messages`, `output_format: {type: "json_schema", schema: <WorkflowPlan schema>}`
   - 根据 `workflow_gen_thinking_mode` 配置决定是否启用 `thinking: {type: "enabled"}`；不使用 thinking 时设 `temperature=0.2`
   - 设置 `anthropic-version` 和 `anthropic-beta` 请求头
   - 通过 `request_with_retries()` 发送 POST 到 `{llm_gateway_url}/v1/messages`
6. `extract_llm_text()` 从响应中分离 text content 和 thinking content
7. 返回 `TransportResponse(text=..., thinking=...)`

### 双通道选择与 fallback 机制

通道选择不在 `WorkflowPlanGenerator` 内部决定，而是在上层 `OrchestrationEngine` 中由 `workflow_planner_mode` 配置决定：

- `workflow_planner_mode` 为 planner 类值（如 `"planner"`）-- 走 SDK 通道（`_generate_dag_planner_sdk()`）
- 其他值 -- 走 LLM 通道（`_generate_dag_llm()`）

两通道共享同一个 `WorkflowPlanningRepairLoop`，其 `max_attempts` 由 `workflow_plan_repair_attempts` 设置控制。当 LLM/SDK 返回的 JSON 无法被解析或验证失败时，repair loop 自动构造 `build_repair_prompt` 并将 `validation_error` 和 `previous_output` 传回模型，请求重新生成。

### plan_generator_support.py 的辅助函数

`orchestrator/dag/plan_generator_support.py` 提供跨通道公用的文本处理工具：

#### extract_json_object()

```python
def extract_json_object(text: str) -> str
```

从 LLM/SDK 的原始文本输出中提取 JSON 对象。提取策略（按优先级）：

1. **直接解析**：尝试 `json.loads()` 整个文本，成功且结果为 `dict` 则直接返回
2. **括号扫描**：调用 `_scan_balanced_braces()`，从文本中逐字符扫描平衡的 `{...}` 对，找到最后一个合法的 JSON 对象
3. **Markdown 代码块回退**：如果前两步都失败，用正则 `` ```json ... ``` `` 或 `` ``` ... ``` `` 匹配代码块内容，在内层再次调用括号扫描

`_scan_balanced_braces()` 是关键算法：维护括号深度计数器，记录最后一个成功解析为合法 JSON 对象的 `{...}` 片段，确保即使文本前后有噪音也能提取到有效 JSON。

#### extract_assistant_text_from_sdk_message()

```python
def extract_assistant_text_from_sdk_message(message: object) -> str
```

处理 Claude Agent SDK 返回的 message 对象。支持 `str`/`bytes`/`bytearray`、Pydantic model（`model_dump()`）、dataclass（`asdict()`）、原生 `dict` 等多种格式。仅提取 `role == "assistant"` 的消息内容。

#### extract_llm_text()

```python
def extract_llm_text(payload: dict[str, Any], *, thinking_content: str) -> tuple[str, str]
```

从 LLM Gateway 返回的响应 body 中分离 text 和 thinking 块。遍历 `content` 数组，将 `type="text"` 的块提取为文本，将 `type="thinking"/"redacted_thinking"` 的块累积到 thinking_content 中。

#### 其他辅助函数

| 函数 | 用途 |
|------|------|
| `short_response_detail(response, limit=1000)` | 从 httpx Response 中提取错误详情字符串，截断到 limit 长度 |
| `with_degraded_model_hint(detail)` | 检测到上游模型 DEGRADED 错误时，追加中文提示建议切换模型 |

## 超时配置

两个超时参数均定义在 `engine.py` 中，通过 `load_settings()` 读取：

| 参数 | 读取方法 | 用途 |
|------|---------|------|
| `intent_parse_timeout_s` | `_intent_parse_timeout_s()` | 第 0 层意图解析的超时（本层不直接使用） |
| `workflow_gen_timeout_s` | `_workflow_gen_timeout_s()` | 传递给 `WorkflowPlanGeneratorConfig.timeout_s`，控制 httpx AsyncClient 的总超时 |

## Repair Loop 集成

`WorkflowPlanGenerator` 通过 `_repair_loop()` 工厂方法创建 `WorkflowPlanningRepairLoop`（定义在 `plan_repair_loop.py`），配合 `_compiler()` 创建 `WorkflowPlanCompiler`：

```
for attempt in 1..max_attempts:
    1. transport(prompt) -> raw_text
    2. compiler.compile(raw_text) -> CompiledWorkflowPlan
        2a. extract JSON via extract_json_object()
        2b. WorkflowPlan.model_validate()
        2c. _validate_explicit_skill_whitelist()
        2d. _validate_planner_size()
        2e. normalize_plan()
        2f. validate_plan() -> warnings
    3. if no errors: return GeneratedDAG (materialize)
    4. else: build repair_prompt with validation_error, retry
```

编译器 `WorkflowPlanCompiler` 位于 `plan_compiler.py`，负责将原始文本编译为 `WorkflowPlan` 并执行三层校验：JSON 解析、Pydantic 模型验证、Skill 白名单检查。

## 生成详情记录

每次生成的结果通过 `_generation_details()`（`plan_generator.py`）记录元数据：

```python
details = {
    "model": model,
    "attempts": attempt,         # 实际使用的尝试次数
    "max_attempts": max_attempts,
    "thinking": thinking,        # LLM 通道有值，SDK 通道为空
    "validationWarnings": warnings,
    "evidenceFrame": ...,        # 来自 resource_audit，可选
}
```

这些详情最终写入 `GeneratedDAG.generation_details` 字段，供 UI 监控面板和调试工具使用。
