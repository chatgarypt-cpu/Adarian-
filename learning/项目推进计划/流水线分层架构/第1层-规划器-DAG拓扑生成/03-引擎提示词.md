# 03 - 引擎提示词

## engine_prompts.py 概述

`orchestrator/dag/engine_prompts.py` 是本层最核心的 prompt 工程文件，负责将结构化的输入（意图、资源审计、Skill 注册表）组装为发送给 LLM 或 Agent SDK 的完整提示词。整个模块围绕 `build_workflow_plan_prompt()` 展开，该函数按七层结构逐段组装 prompt。

## prompt 组装的核心函数

模块对外暴露四个 prompt 构建函数，两两对应（正常 + 修复）：

| 函数 | 用途 | 调用方 |
|------|------|--------|
| `build_workflow_plan_prompt()` | LLM 通道的标准生成 prompt | `EnginePlanningMixin._build_workflow_plan_prompt()` |
| `build_workflow_plan_repair_prompt()` | LLM 通道的修复 prompt | `EnginePlanningMixin._build_workflow_plan_repair_prompt()` |
| `build_workflow_planner_prompt()` | SDK 通道的标准生成 prompt（基于 plan prompt + planner 补充说明） | `EnginePlanningMixin._build_workflow_planner_prompt()` |
| `build_workflow_planner_repair_prompt()` | SDK 通道的修复 prompt | `EnginePlanningMixin._build_workflow_planner_repair_prompt()` |

## 七层组装结构

`build_workflow_plan_prompt()` 按以下七层顺序拼装 prompt（源码中 `parts` 列表的顺序）：

### 第 1 层：角色与基石 Skill 层

```text
你是 ElectionSim-Lab 的 Layer 1 DAG planner；必须优先遵守下方 dag-planner Skill。
## Skill `dag-planner`
source: `claude-runtime/skills/planner/framework/dag-planner/SKILL.md`
<dag-planner SKILL.md 正文>
### Reference `rules-and-examples.md`
<rules-and-examples.md 正文>
```

通过 `planner_skill_assets.py` 的 `render_skill_prompt_block()` 函数，从 `claude-runtime/skills/` 目录读取 `dag-planner` 的 `SKILL.md` 及其引用文件 `references/rules-and-examples.md`（由常量 `DAG_PLANNER_REFERENCES = ("rules-and-examples.md",)` 指定）。

这是整个 prompt 的"宪法"——dag-planner 包含 DAG 规划方法论、拓扑 recipe 和校验失败范例。

### 第 2 层：动态规划上下文层（约束条件）

```text
【动态规划上下文】
要求：
- 节点 id 必须匹配正则 ^[a-z0-9][a-z0-9_-]{0,63}$（小写英数字/下划线/短横线）。
- <_node_id_rule() 动态规则>
- <_skill_binding_rule() 动态规则>
- DAG 必须无环；edges 的 from/to 必须引用已存在的 node.id。
- 当前 planningRichness=<值>；结构节奏建议：<topology_assembly_rule_text()>
- 当前档位拓扑门槛：<topology_target_text()>
- <topology_node_strategy_rule()>
- 模板摘要里的 layer 只表示常见流水线位置，不要求机械照抄...
- single-use skill 冲突由宿主确定性 binding 处理...
- 规划时必须先满足结构真值，再考虑节点命名...
- comprehensive / 深度模式下，不要用 3-4 节点全串行单链冒充高丰富度 DAG。
- open 模式下的 generic 节点 description 只写职责...
```

此层的三个关键函数在 `engine_prompts.py` 中定义：

- `_node_id_rule(allowed_mode, custom_prefix)`：根据 `allowed_mode`（open/skills_only/skills_plus_custom）返回不同的节点 ID 命名规则
- `_skill_binding_rule(allowed_mode)`：控制 skill_id 绑定策略（open 模式下不硬套固定 skill id）
- `blocking_predecessor_prompt_lines()`：注入阻塞型前驱真值规则（entry 可做根节点，其他节点必须有至少 1 条 `data_dependency` 或 `conditional` 上游边）

### 第 3 层：拓扑指导层

```text
- DAG 拓扑技能原则：<guide.principles[0]>
- DAG 拓扑技能原则补充：<guide.principles[1..]>
- <guide.preferred 推荐结构>
- <guide.acceptable 可接受结构>
- 常见误区：<guide.mistakes>
```

通过 `workflow_topology_guidance.py` 的 `topology_prompt_guidance_lines()` 生成，依据 `planning_richness` 选择对应的指导语：

| Richness | 推荐结构 | 节点范围 | 关键约束 |
|----------|---------|---------|---------|
| minimal | 问题界定 -> 1-2 执行节点 -> 输出 | 2-4 | 不要求并行层；不强求多级拓扑 |
| standard | 问题界定 -> 2-3 路轻并行取证 -> 综合 -> 输出 | 5-8 | 至少 1 次轻并行取证 + 1 个显式汇聚 |
| detailed | 问题界定/数据定位 -> 并行取证 -> 中间综合 -> 1-2 专题深化/交叉验证 -> 输出 | 10-16 | 必须至少 10 节点；至少 1 次汇聚 |
| comprehensive | 多级结构：首轮并行取证 -> 中间汇聚 -> 二次专题展开 -> 最终综合/交付 | 15-25 | 必须至少 15 节点；并行层>=2；汇聚节点>=2；优先宽-窄-宽 |

### 第 4 层：报告规划指导层

```text
<report_planning_guidance_lines() 输出>
```

来自 `orchestrator/export/report_planning.py`，根据用户需求中的报告格式要求，给出对应的 DAG 节点结构建议。

### 第 5 层：Skill 执行约束补充层

```text
【Skill 执行约束补充】
- 上方 dag-planner Skill 与 references/rules-and-examples.md 是规划方法论...
- 当内置技能与职责高度吻合时可直接复用；不吻合时创建新语义化节点。
- 自定义可执行节点若不绑定 skill，必须写清 description...
- label 使用中文短语，尽量以动词开头...
- 输出 JSON 必须包含字段 name, nodes, edges...
- 可选 rationale：用不超过 800 字说明规划思路...
- 请只输出一个 JSON 对象，不要输出 Markdown/解释/代码块。
```

### 第 6 层：资源审计与证据框架层

```text
资源盘点摘要（用于减少幻觉与误规划）：
{localDataStatus, externalData, dataGap, matchedPathsSample 的紧凑 JSON}

<evidence_frame_prompt_block() 输出>
```

条件注入：只有当 `resource_audit` 为非空 dict 时才添加。包含：
- `_resource_audit_summary()`：将资源审计数据压缩为 ≤1600 字符的 JSON，包含本地数据状态、外部数据开关、数据缺口和匹配路径采样
- `evidence_frame_prompt_block()`：来自 `orchestrator/chat/evidence_frame.py`，注入证据框架的结构化描述

### 第 7 层：节点积木库 + Skill 模板目录层

```text
以下是节点积木库（抽象结构语法）：
- entry_point: 入口节点（阶段=entry；下游=evidence；行为=root/singleton；...）
- evidence_collector: 证据收集节点（阶段=evidence；下游=synthesis；...）
- evidence_synthesizer: 证据综合节点（...）
... (来自 SkillRegistry.planning_block_catalog())
- 配方 recipe_a: ...（...；适用=...）

以下是系统内置的可复用技能模板摘要，你可以复用也可以直接创建语义化节点：
| skill_id | label | stage | archetype | predecessor_stages | successor_stages | trigger | summary |
| --- | --- | --- | --- | --- | --- | --- | --- |
| agenda_setter        | 议题设定   | entry     | ... | ... | ... | ... | ... |
| data_discovery       | 数据发现   | entry     | ... | ... | ... | ... | ... |
| ...                 | ...       | ...       | ... | ... | ... | ... | ... |
```

两层内容：
1. **节点积木库**：`_node_block_lines()` 调用 `SkillRegistry.planning_block_catalog()` 获取 archetypes 和 recipes，描述每种节点积木的阶段、下游、行为特征
2. **Skill 模板目录**：`_skill_lines()` 调用 `SkillRegistry.planning_snapshot()` 获取所有 Skill 的摘要表，经 `filter_skill_snapshot_for_report_scope()` 按用户需求过滤，以 8 列 Markdown 表格形式呈现

### Planner 模式额外补充

`build_workflow_planner_prompt()` 在七层基础上追加：

```text
补充说明（planner 模式）：
- DAG 规划方法论来自系统注入的 dag-planner Skill；仓库源文件位于 claude-runtime/skills/...
- <open 模式提示>
- 如需查看每个 skill 的更详细说明，使用系统已注入的 SkillRegistry/skill docs...

```

## planning_strategies.py 的策略模式

`orchestrator/dag/planning_strategies.py` 非常精简，仅定义策略协议和两个具体策略：

```python
class PlanningStrategy(Protocol):
    async def generate(self, request: WorkflowPlanningRequest) -> GeneratedDAG: ...
```

| 策略类 | 生成方法 | 底层调用 |
|--------|---------|---------|
| `WorkflowLLMPlanningStrategy` | `generator.generate_with_llm_request(request)` | LLM Gateway 直接 API |
| `WorkflowPlannerSDKStrategy` | `generator.generate_with_planner_sdk_request(request)` | Claude Agent SDK |

两个策略都是 `frozen=True` dataclass，持有同一个 `WorkflowPlanGenerator` 实例。区别仅在于调用 `WorkflowPlanGenerator` 的不同方法。

## planner_skill_assets.py 的 Skill 元数据注入

`orchestrator/dag/planner_skill_assets.py` 负责从文件系统读取 Skill 源文件并注入到 prompt 中：

### render_skill_prompt_block()

```python
def render_skill_prompt_block(skill_id: str, *, references: tuple[str, ...] = ()) -> str
```

执行流程：
1. 调用 `resolve_skill_dir_path()` 在 `claude-runtime/skills/` 下定位 skill 目录
2. 读取 `SKILL.md`，通过 `parse_frontmatter()` 解析 frontmatter，校验 `name` 字段与 `skill_id` 一致
3. 逐个读取 `references/` 下的引用文件
4. 拼装为 `## Skill \`id\`` + body + `### Reference \`name\`` 格式

关键校验点：frontmatter 中 `name` 必须与 `skill_id` 匹配，否则抛出 `ValueError`。引用文件名不允许含 `..` 或绝对路径，防止路径遍历。

### render_skill_reference_block()

```python
def render_skill_reference_block(skill_id: str, reference: str) -> str
```

单独渲染某个 skill 的单个 reference 文件，供其他模块按需引用。

### Skill 源目录解析

通过 `common.claude_runtime_assets.py` 的 `default_runtime_skills_dir()` 定位 skill 根目录，`resolve_skill_dir_path()` 支持多种目录命名习惯。源路径标签通过 `claude_runtime_source_label()` 生成为 `claude-runtime/skills/<relative-path>` 格式。

## Repair Prompt 的差异

修复类 prompt（`build_workflow_plan_repair_prompt()` / `build_workflow_planner_repair_prompt()`）在基础 prompt 上追加：

```text
你上一次输出未通过系统校验（将进行第 N 次修复尝试）。
校验错误：<validation_error>
上一次输出（请基于此做最小修改以通过校验）：
<previous_output[:2000]>
- 修复必须遵守上方 dag-planner Skill 的 references/rules-and-examples.md 校验规则与负面范例。
- <blocking_predecessor_repair_guidance_lines() 动态修复指导>
- <topology_repair_guidance_lines() 拓扑修复指导>
- <report_repair_guidance_lines() 报告修复指导>

请重新输出一个 JSON 对象，不要输出任何解释文字。
```

`blocking_predecessor_repair_guidance_lines()` 通过正则 `_MISSING_PREDECESSOR_RE` 从校验错误中提取缺失前驱的节点 ID 和期望的阶段，生成针对性修复建议。
