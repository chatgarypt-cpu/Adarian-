# 03 - 修复循环

## 概述

修复循环 (`WorkflowPlanningRepairLoop`) 是整个 Compile-Validate-Repair 流水线的编排器。它位于 `orchestrator/dag/plan_repair_loop.py`，负责在一次或多次尝试中完成"调用 LLM → 编译校验 → 失败则修复重试"的循环，直到成功产出 `GeneratedDAG` 或用尽重试次数。

同时，修复 prompt 的构建逻辑独立在 `orchestrator/chat/planning_repair.py` 中，通过 `build_planning_repair_prompt()` 将校验错误转化为 LLM 可理解和修复的指引。

## `WorkflowPlanningRepairLoop` 结构

```python
# orchestrator/dag/plan_repair_loop.py:22-26
@dataclass(frozen=True)
class WorkflowPlanningRepairLoop:
    max_attempts: int                       # 最大尝试次数（含初次 = workflow_plan_repair_attempts）
    compiler: WorkflowPlanCompiler          # 编译器实例（含 allowed_mode, custom_prefix）

    async def generate(
        self,
        *,
        request: WorkflowPlanningRequest,   # 含 prompt() 和 repair_prompt()
        transport: PlanTransport,           # async (prompt, thinking) → TransportResponse
        generation_source: str,             # "llm" 或 "planner_sdk"
        generation_details_builder: GenerationDetailsBuilder,
    ) -> GeneratedDAG: ...
```

`PlanTransport` 是一个 Protocol（`plan_repair_loop.py:15-16`），抽象了 LLM 调用方式：
- LLM 通道：通过 `query_llm_transport()` 发送带 JSON schema 约束的请求到 LLM Gateway。
- SDK 通道：通过 `query_planner_sdk()` 调用 Claude Agent SDK（本地 CLI 模式）。

## `generate()` 主循环详解

`generate()` 方法（`plan_repair_loop.py:27-65`）的核心逻辑如下：

```python
async def generate(self, *, request, transport, generation_source, generation_details_builder):
    prompt = request.prompt()                    # 构建初始 prompt
    thinking_content = ""                        # 累积 thinking 内容

    for attempt in range(1, self.max_attempts + 1):
        # ---- 第 1 步：调用 LLM/SDK ----
        response = await transport(prompt, thinking_content)

        # ---- 第 2 步：更新 thinking ----
        thinking_content = self._next_thinking(
            current=thinking_content,
            response=response
        )

        # ---- 第 3 步：尝试编译 ----
        try:
            compiled_plan = self.compiler.compile(
                raw_text=response.text,
                request=request
            )
        except (ValueError, json.JSONDecodeError, ValidationError) as exc:
            # ---- 第 4 步：编译失败 → 构建修复 prompt 或抛出 ----
            prompt = self._repair_prompt_or_raise(
                request=request,
                response=response,
                error=exc,
                attempt=attempt,
            )
            continue                                 # 重试下一轮

        # ---- 第 5 步：编译成功 → 物化 ----
        thinking_content = self._thinking_from_rationale(
            current=thinking_content,
            rationale=compiled_plan.plan.rationale,
        )
        generation_details = generation_details_builder(
            attempt, thinking_content, compiled_plan.validation_warnings,
        )
        return self.compiler.materialize(            # 产出 GeneratedDAG
            compiled_plan=compiled_plan,
            request=request,
            generation_source=generation_source,
            generation_details=generation_details,
        )

    raise RuntimeError("workflow plan generation failed without a terminal error")
```

### 关键设计要点

1. **Thinking 累积**：`_next_thinking()` (`plan_repair_loop.py:68-69`) 在每轮调用后更新 `thinking_content`，优先使用 response.thinking。失败时不更新 thinking（使用上一轮的），成功时从 `plan.rationale` 回填（仅当 thinking 为空时）。

2. **异常捕获范围**：`except (ValueError, json.JSONDecodeError, ValidationError)` 精确捕获编译阶段的三种异常类型。其他异常（如 network error）会直接穿透，不触发 repair 逻辑。

3. **最后一轮失败**：`_repair_prompt_or_raise()` 在 `attempt >= max_attempts` 时直接 `raise error`，不再构建 repair prompt。

4. **防御性 RuntimeError**：若循环正常退出（理论上不应发生），抛出 `RuntimeError`。

## Thinking 累积策略

```python
# plan_repair_loop.py:68-69
@staticmethod
def _next_thinking(*, current: str, response: TransportResponse) -> str:
    return response.thinking or current
```

- 优先使用当前响应的 `thinking` 字段。
- 若 response 中无 thinking，保留之前累积的内容。
- thinking 会随 repair prompt 一起传给下一轮 LLM 调用，帮助模型理解上下文。

```python
# plan_repair_loop.py:71-75
@staticmethod
def _thinking_from_rationale(*, current: str, rationale: object) -> str:
    if current or not rationale:
        return current
    return str(rationale).strip()[:2000]
```

- 成功编译后，若当前 thinking 为空且 plan 有 `rationale`，则用 rationale（截断到 2000 字符）作为 thinking 内容传递给 `generation_details_builder`。

## 错误类型分类和诊断

修复循环需要捕获并理解以下错误类别，以便构建有针对性的修复 prompt：

### 1. JSON 语法错误 (`json.JSONDecodeError`)

由 `_workflow_plan_from_json()` 中的 `json.loads()` 抛出。常见原因：
- LLM 在 JSON 前后输出了解释性文字
- JSON 被包裹在 Markdown 代码围栏中（本应由 `extract_json_object()` 处理，但极端情况下可能遗漏）
- JSON 中包含非法字符、未转义引号等

### 2. Pydantic Schema 校验错误 (`ValidationError`)

由 `WorkflowPlan.model_validate()` 抛出。常见错误模式：
- **字段缺失**：缺少必填字段如 `rationale`、`status`
- **类型不匹配**：如 `nodes` 不是数组、`enabled` 不是布尔值
- **字段格式错误**：`node.id` 包含非法字符（大写、中文、空格）
- **长度超限**：nodes/edges 超过 `PLANNER_WORKFLOW_MAX_NODES`/`MAX_EDGES`

错误信息在 `_workflow_validation_message()` (`plan_compiler.py:106-112`) 中格式化为：`"WorkflowPlan 字段校验失败：loc: msg；loc: msg"`。

### 3. 业务校验错误 (`ValueError`)

由 `_validate_explicit_skill_whitelist()`, `_validate_planner_size()`, `validate_plan_dag()`, `validate_generated_plan()` 等函数抛出。覆盖 DAG 语义违规的全部场景（唯一 ID、无环、边合法性、Skill 白名单、扇出限制等）。

## RepairPrompt 的构建策略

修复 prompt 的构建由 `planning_repair.py` 的 `build_planning_repair_prompt()` 函数负责（第 8-43 行）：

```python
def build_planning_repair_prompt(
    *,
    prompt: str,               # 原始 prompt
    validation_error: str,     # 校验错误文本
    previous_output: str,      # LLM 上一次输出
    user_input: str,           # 用户原始输入
    planning_richness: str | None = None,
) -> str:
```

### 构建流程

1. **收集修复指引**：
   - `topology_repair_guidance_lines(error_text)` -- 来自 `workflow_topology.py`，根据拓扑评估结果生成结构修复建议。
   - `report_repair_guidance_lines(user_input, error_text, planning_richness)` -- 来自 `export/report_planning.py`，针对报告意图的结构修复建议。
   - `planning_payload_repair_guidance_lines(error_text)` -- 本地函数，针对 payload 级别常见错误的修复指引。

2. **组装修复消息**：
   - 告知 LLM "上一次输出未通过系统校验"。
   - 注入 `dag-planner` Skill 的修复规则（通过 `render_skill_reference_block("dag-planner", "rules-and-examples.md")`）。
   - 附上校验错误文本（截断到 1200 字符）。
   - 附上额外修复要求（从 repair_lines 收集）。
   - 强制输出格式："回复首字符必须是 `{`，最后一个非空字符必须是 `}`"。
   - 附上上一次的原始输出（截断到 2500 字符）。

3. **最终输出**：`原始 prompt + "\n" + 修复部分`。

### `planning_payload_repair_guidance_lines()` 的四种错误检测

`planning_payload_repair_guidance_lines()` (`planning_repair.py:53-87`) 通过分析 `validation_error` 字符串识别特定错误模式，生成针对性修复指引：

| 检测函数 | 触发条件 | 修复指引 |
|----------|----------|----------|
| `_missing_status()` | `validation_error` 中包含 `"status"`, `"Field required"`, `"PlanningDecisionPayload"` | 补齐 `status` 字段，值只能是 `chat`/`ask`/`ready` 之一 |
| `_missing_rationale()` | 包含 `"rationale"` + `"PlanningDecisionPayload"` + `"Field required"` 或 `"rationale 不能为空"` | 补齐 `rationale` 字段，放顶层不能塞进 `assistantReply` 或 `dag` |
| `_non_json_output()` | 包含 `"not_json"` 或 `"not JSON"` | 禁止解释/前言/Markdown 围栏，首字符必须为 `{` |
| `_invalid_dag_node_id()` | 包含 `"dag.WorkflowPlan"` + `"String should match pattern"` | `dag.nodes[].id` 只能用小写英文/数字/下划线/短横线，禁止大写/中文/空格 |

## 重试策略

### 最大尝试次数

由 `max_attempts` 控制，值来自 `workflow_plan_repair_attempts` 配置（默认 2）：

```
max_attempts = 2 时的重试行为：
  attempt 1 → 失败 → 构建 repair_prompt → attempt 2
  attempt 2 → 失败 → _repair_prompt_or_raise() 发现 attempt >= max_attempts → raise error
```

### 两类生成策略中的调用

在 `orchestrator/dag/plan_generator.py` 中，两种生成策略共用同一个 `_repair_loop()` 实例：

- **LLM 通道** (`generate_with_llm_request()`, 第 104-133 行)：通过 `httpx.AsyncClient` 调用 LLM Gateway，传入 JSON schema 约束和 retry 配置。
- **SDK 通道** (`generate_with_planner_sdk_request()`, 第 86-102 行)：通过 `query_planner_sdk()` 调用本地 Claude Agent SDK。

两者的 `generation_details_builder` 不同：SDK 通道不传 `thinking`。

### Chat 模块中的多轮修复

在 `orchestrator/chat/planning_agent.py` 中，`_run_planning_attempts()` (`planning_agent.py:159-209`) 是 chat 场景下的修复循环。它读取 `max_attempts = router.engine._workflow_plan_repair_attempts()`，在每轮中运行完整的 SDK session，收集 messages，编译结果，失败时通过 `_build_workflow_plan_repair_prompt()` 构建新的 prompt 并重试。

`_build_workflow_plan_repair_prompt()` (`planning_agent.py` 中的定义) 封装了 `build_planning_repair_prompt()`，并将 repair prompt 注入到 session 的 messages 历史中。

## 修复失败的最终处理

修复失败有两种路径：

### 路径 1：修复循环内失败（PlanGenerator 场景）

在 `WorkflowPlanningRepairLoop._repair_prompt_or_raise()` 中，当 `attempt >= max_attempts` 时直接 `raise error`：

```python
# plan_repair_loop.py:77-91
def _repair_prompt_or_raise(self, *, request, response, error, attempt):
    if attempt >= self.max_attempts:
        raise error                                # 直接抛出原始异常
    return request.repair_prompt(                  # 否则构建修复 prompt
        previous_output=response.text,
        validation_error=str(error),
        attempt=attempt + 1,
    )
```

异常会传播到 `WorkflowPlanGenerator.generate_with_llm_request()` 或 `generate_with_planner_sdk_request()`，进而传播到 `OrchestrationEngine._generate_dag_llm()` (`engine_planning_mixin.py:191-203`)，最终转换为面向用户的错误响应。

### 路径 2：Chat 多轮场景失败

在 `_run_planning_attempts()` 中，最后一轮失败后，`_build_planning_agent_result()` 将错误信息封装在 `PlanningAgentResult` 中，通过 `kind="error"` 事件传递给前端。错误信息包含：
- `error` 字段：异常消息原文
- `debug_attempts`：所有尝试的详细记录（每个 attempt 的 messages、validation_error 等）

### 典型失败场景

- **模型持续输出非法 JSON**：若 LLM 多轮都无法输出合法 JSON，最终抛出 `ValueError("Workflow generation output is not JSON")` 或 `json.JSONDecodeError`。
- **DAG 结构持续违规**：LLM 的 DAG 设计有根本性缺陷（如始终包含未知 Skill），多轮修复无法纠正 → 最终抛出对应的业务 `ValueError`。
- **网络/网关错误**：不在 `(ValueError, json.JSONDecodeError, ValidationError)` 捕获范围内，会直接穿透修复循环。

## `planning_repair.py` (`chat` 模块) 的 `build_planning_repair_prompt()` 逻辑

`orchestrator/chat/planning_repair.py` 定义了两个公开函数：

- **`build_planning_repair_prompt()`** (`planning_repair.py:8-43`)：核心修复 prompt 构建函数。接收原始 prompt、校验错误、上一次输出、用户输入、richness，返回拼接了错误诊断和修复指引的完整 prompt。
- **`planning_payload_repair_guidance_lines()`** (`planning_repair.py:53-87`)：根据校验错误文本生成 payload 级别的修复指引行。

### 依赖的辅助模块

`build_planning_repair_prompt()` 在构建修复 prompt 时调用两个外部函数收集修复指引：

- `topology_repair_guidance_lines()` from `orchestrator/dag/workflow_topology.py`：根据拓扑评估结果（如节点数不足、缺少关键路径）生成结构修复建议。
- `report_repair_guidance_lines()` from `orchestrator/export/report_planning.py`：针对报告输出模式（`status=ready` 且 `dag` 涉及报告生成）的语义校验修复建议。

### 修复 prompt 的输出约束

修复 prompt 明确要求 LLM：
1. 不要输出解释文字（"不要解释你将如何修复"）。
2. 输出必须是单个 JSON 对象（"回复首字符必须是 `{`，最后一个非空字符必须是 `}`"）。
3. 按同一 JSON 结构修复后重新输出。

### DAG Planner Skill 修复规则注入

`_dag_planner_repair_reference()` (`planning_repair.py:46-50`) 通过 `render_skill_reference_block("dag-planner", "rules-and-examples.md")` 从 `claude-runtime/skills/dag-planner/` 中读取修复规则和负面范例，注入到修复 prompt 中，使 LLM 的修复行为符合系统规范。
