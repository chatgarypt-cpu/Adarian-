# 02 — 端到端流程：从用户输入到报告产出

> 以"分析 2026 台北市长选举"为例，追踪一条用户消息如何穿越 10 层流水线，最终生成一份包含数据、分析和可视化的完整报告。

## 阶段一：用户输入阶段（Layer 0 前半部分）

### 1.1 前端发送消息

用户在 Chat UI 输入框中键入"分析 2026 台北市长选举"，点击发送。前端的 `useChatStreaming.ts` hook 向 FastAPI 的 `POST /api/chat/send` 端点发送一个 JSON payload：

```json
{
  "session_id": "sess_abc123",
  "message": "分析 2026 台北市长选举",
  "mode": "auto"
}
```

`mode=auto` 表示由 Planning Agent 决定执行路径（chat/ask/ready），而不是强制走 DAG 调度或单 Agent 模式。

### 1.2 `stream_generate_workflow_response()` 启动

后端 `orchestrator/chat/chat_api.py` 中的 `stream_generate_workflow_response()` 函数被调用。这是一个异步生成器函数，负责整个端到端流程的编排。它首先执行资源审计。

### 1.3 资源审计（resource_audit）

在调用 Planning Agent 之前，系统扫描 `public/` 数据目录，生成一份资源审计报告。审计内容包括：

- **数据文件清单**：`public/` 下的所有 CSV、JSON、YAML 文件及其 schema。
- **年份范围**：数据中覆盖的选举年份（如 2018-2028）。
- **选举类型**：可用的选举类型（市长、市议员、总统等）。
- **地理覆盖**：可用的县市列表。

这份审计报告被注入 Planning Agent 的 system prompt，让 Agent 在不实际读取文件内容的情况下就知道"系统有什么数据可用"。这避免了 LLM 规划一个需要不存在数据的任务。

### 1.4 Planning Agent 分析意图

Planning Agent（一个 Claude SDK Session）收到 system prompt（包含资源审计报告 + 规划策略 + 意图分类指南）和 user message（用户原始输入 + 对话历史）。它执行以下推理：

1. **意图识别**：用户想分析选举 → 这是一个需要 DAG 执行的复杂任务。
2. **信息充分性判断**：用户已指定年份（2026）、地点（台北）、选举类型（市长）→ 信息充分，无需澄清。
3. **输出状态**：`ready`。

Planning Agent 返回一个 `PlanningAgentResult`，同时附带结构化的意图字段：`{year: 2026, location: "台北", election_type: "市长"}`。

## 阶段二：规划阶段（Layer 0 后半部分 → Layer 1 → Layer 2）

### 2.1 如果输出是 ask

如果用户只输入了"分析选举"，没有年份和地点，Planning Agent 会返回 `ask` 状态并附带一个澄清问题："请问您想分析哪一年、哪个地方的选举？目前系统中有 2018-2028 年台湾各县市的选举数据。"

前端收到 `ask` 事件后，在 Chat UI 中显示这条澄清消息。用户的回复作为下一轮输入，重新进入 Planning Agent。这个"多轮澄清"循环由 `planning_round_policy.py` 控制，包含最大轮次限制（防止无限循环）和信息增量检测（防止用户重复提供相同信息）。

### 2.2 如果输出是 chat

如果用户输入的是"你好"、"今天天气怎么样"等与选举分析无关的内容，Planning Agent 返回 `chat` 状态并直接回复，不触发 DAG 流程。

### 2.3 如果输出是 ready → DAG 生成

这是最常见的工作流场景。`ready` 状态触发 Layer 1：

1. `OrchestrationEngine.generate_plan()` 被调用。
2. 七层 system prompt 组装：角色定义（"你是一个选举分析工作流规划专家"）→ 35 个 Skill 的功能摘要表 → 策略模板（`planning_strategies.py` 中预定义的任务分解模式）→ 输出 JSON schema 约束 → 可用数据摘要 → 规划启发式规则 → 用户具体任务。
3. LLM（`WORKFLOW_GEN_MODEL`）被调用，返回一个包含 `WorkflowPlan` JSON 的文本响应。
4. 对于"分析 2026 台北市长选举"，LLM 可能生成如下 DAG：

```
agenda_setter (设定模拟参数)
    ↓
candidate_registry_searcher (搜索候选人资料)
    ↓
simulation_runner (运行选举模拟)
    ↓
report_writer (生成分析报告)
```

### 2.4 Compile → Validate → Repair

Layer 2 接管：

1. **PlanCompiler**：从 LLM 文本响应中提取 JSON 对象（`extract_json_object()`），构造 `WorkflowPlan` Pydantic 实例。
2. **PlanValidator**：执行两层校验：
   - **Schema 校验**：JSON 是否匹配 `WorkflowPlan` 的 Pydantic schema（字段类型、必填字段等）。
   - **业务规则校验**：DAG 无环检测（DFS 环检测算法）、无孤立节点（所有节点都在至少一条边中）、边引用完整性（`from_node` 和 `to_node` 都在 `nodes` 列表中）、输出类型合法性（`expected_output_type` 必须是 `csv` / `text` / `json` / `report_md` 之一）。
3. **[如果校验失败]** **PlanRepairLoop**：将原始 Plan + 错误列表反馈给 LLM，要求修正。LLM 返回修正后的 Plan，重新进入 Compile → Validate。循环最多 `workflow_plan_repair_attempts` 次。超过次数则抛出异常并向前端报告。

## 阶段三：DAG 编译阶段（Layer 3 → Layer 4）

### 3.1 Skill Auto-Binder 自动匹配

Layer 3 的 `SkillAutoBinder` 遍历每个 `allowed_mode="open"` 的节点，执行四层匹配：

- **agenda_setter**：节点 ID 包含 `agenda` 关键词 → 关键词降级匹配到 `agenda_csv` Skill。
- **candidate_registry_searcher**：节点 ID 包含双下划线前缀候选 → 匹配到 `candidate_registry_searcher` Skill。
- **simulation_runner**：节点 ID 匹配 → `election_simulation_runner` Skill。
- **report_writer**：节点 ID 匹配 → `report_writer` Skill。

如果任一 Skill 被标记为 `single_use` 且已被前面的节点占用，后续匹配会自动降级为 `generic`。这防止了多个节点不当地共享同一个单次使用 Skill。

### 3.2 Materializer 编译为 GeneratedDAG

Layer 4 的 `build_generated_dag()` 执行以下操作：

1. **拓扑排序**：使用 Kahn 算法对节点排序，确定执行顺序。对于上述 DAG，拓扑序为 `[agenda_setter, candidate_registry_searcher, simulation_runner, report_writer]`。
2. **层级分配**：`assign_layers_orders()` 分析依赖关系，将无相互依赖的节点分配到同一层以支持并行执行。如果一个 DAG 包含与 `simulation_runner` 并行的 `data_visualizer` 节点，它们会被分配在同一层。
3. **搜索子节点注入**：`_inject_search_sub_nodes()` 检查每个节点是否需要外部搜索。如果 `candidate_registry_searcher` 被标记为 `external_search`，系统在它前面自动插入一个搜索子节点，该子节点使用搜索 Agent Skill 从联网资源获取数据，上游输出自动流入 `candidate_registry_searcher` 的工作区。
4. **agent_config 构建**：为每个节点确定使用的模型、工具白名单、Skill bundle 路径。例如 `agenda_setter` 可以使用性价比较高的模型，而 `report_writer` 需要高容量模型来生成长篇报告。

输出是 `GeneratedDAG`：一个包含完整运行时配置的 DAG 数据结构。

## 阶段四：任务准备阶段（Layer 5 → Layer 6）

### 4.1 Launcher Prompt 为每个节点组装 task_prompt

Layer 5 的 `build_node_prompt()` 为每个 DAG 节点生成独立的 `task_prompt.md`。七层组装顺序：

1. **执行权威层级**：声明该节点在整个 DAG 中的位置和上下级关系。
2. **SCOPE_LINES（作用域约束）**：节点级别的行为边界。例如 `agenda_setter` 的 SCOPE_LINES 规定"你只负责设定模拟参数和生成 agenda CSV，不要尝试搜索候选人资料或运行模拟——那些是下游节点的职责"。
3. **具体任务描述**：从 `WorkflowPlanNode.task` 中获取的自然语言任务。
4. **上游节点输出摘要**：下游节点可以看到上游产出了什么文件、文件格式和内容摘要。
5. **期望输出格式与合约**：`execution_contract` 和 `required_outputs` 描述节点必须产出的文件类型、格式和字段约束。
6. **工具调用纪律**：批量操作合并、不要重复读取同一文件等行为规范。
7. **进度 CSV 写入规范**：每个节点需要将进度写入标准 CSV 追踪文件，供调度器监控。

此外还会注入 `resource_hints`：告诉 Agent 数据文件在哪里、格式是什么、有哪些字段。这样 Agent 不需要反复探测文件格式。

### 4.2 Workspace Sync 同步 claude-runtime/ 到容器

Layer 6 的 `sync_workspace_skills()` 使用 `shutil.copytree` 将宿主机的 `claude-runtime/` 完整复制到容器的 `.claude/`：

```
claude-runtime/skills/    → .claude/skills/    (所有 Skill 定义)
claude-runtime/agents/    → .claude/agents/    (8 个 Subagent 角色)
claude-runtime/settings.json → .claude/settings.json (共享配置)
```

同时执行 MCP 模板变量替换：`{{MCP_SERVER_URL}}`、`{{MCP_API_KEY}}` 等占位符被替换为实际的运行时值，确保容器内的 Agent 可以连接外部 MCP 服务（如浏览器自动化、代码执行沙箱等）。

## 阶段五：执行阶段（Layer 7 → Layer 8）

### 5.1 DAGScheduler 调度执行

Layer 7 的 `DAGScheduler` 按照拓扑顺序和层级并行度调度节点执行：

- **Layer 0 节点**（无上游依赖）先执行：`agenda_setter`。
- **Layer 1 节点**（依赖 Layer 0 输出）随后执行：`candidate_registry_searcher`。如果有多个同层节点（如并行运行的数据分析），它们可以同时执行。
- **Layer N 节点**依次执行，直到全部完成。

如果系统配置为单 Agent 模式（`execute_single_agent()`），则跳过 DAG 调度，直接在一个 Agent Session 中完成所有任务。

### 5.2 Docker 容器启动

容器使用长生命周期策略：不是每个节点启动一个新容器，而是启动一个容器后通过 `docker exec` 在其中依次执行多个 Agent Session。这大幅减少了冷启动延迟。容器挂载了以下卷：

- `/workspace`：节点工作目录，包含 `input/`、`meta/`、`output/`。
- `/workspace/upstream`：上游节点的输出目录，只读挂载。
- `/public`：系统数据根目录，只读挂载。
- `.claude/`：从 Layer 6 同步的 Claude Runtime 配置。

`RunContainerMonitor` 监控容器健康状态（CPU、内存、是否僵死），在异常时触发重启或告警。

### 5.3 Agent SDK Session 执行每个节点

Layer 8 是核心执行层。以 `agenda_setter` 节点为例：

1. **入口**：容器内执行 `python -m agent.election_agent --node-id agenda_setter`。
2. **初始化**：`election_agent.py` 初始化 Claude SDK 客户端，配置模型、超时、max_turns=300。
3. **System Prompt 注入**：`system_prompt.py` 构建 system prompt，注入时间基准（当前时间、选举年份上下文）、运行时约束（`runtime_required_outputs`）、Subagent 可见性列表。
4. **User Message 注入**：将 `task_prompt.md` 的内容作为首个 user message 发送给模型。
5. **推理循环**：模型开始推理，可以调用以下工具：
   - **Read / Write / Edit**：文件操作工具，读写工作区内的文件。
   - **Bash**：执行命令（`python`、`jq`、`csvkit` 等数据处理工具）。
   - **Skill**：调用预定义的 Skill（如 `agenda_csv` Skill 包含了如何生成标准 agenda CSV 文件的知识）。
   - **Agent**：委派子任务给 Subagent。例如如果任务需要联网搜索，Agent 调用 `Agent(subagent_type="search-grok")`。
   - **MCP**：通过 MCP 协议连接外部服务（浏览器、数据库等）。
6. **输出写入**：Session 结束时，Agent 将结果写入 `output/result.json`（结构化结果）、`output/report.md`（自然语言摘要）、并完整记录 `sdk_messages.jsonl`。

每个后续节点（`candidate_registry_searcher` → `simulation_runner` → `report_writer`）按相同模式执行，区别在于它们可以读取上游节点的 `output/` 目录来获取之前的分析结果。

## 阶段六：输出阶段（Layer 9）

### 6.1 事件流回传

Agent Session 在执行过程中持续写入 `sdk_messages.jsonl`。`EventRecorder`（在 `agent/event_recorder.py` 中）实时 tail 这个文件，将原始 SDK 事件转换为统一的监控事件格式，推送到 Redis Streams。

事件类型包括：

| SDK 原始事件 | 转换后的监控事件 | 前端效果 |
|-------------|----------------|---------|
| `message_start` | `node_thinking` | 节点状态变为"思考中"（黄色闪烁） |
| `message_delta` | `token_stream` | Chat UI 中流式显示思考过程 |
| `tool_use` | `tool_call_start` | 运行详情面板中显示工具调用记录 |
| `tool_result` | `tool_call_end` | 工具调用结果展示 |
| `assistant` (final) | `node_complete` | ReactFlow 节点变绿 |
| `error` | `node_error` | ReactFlow 节点变红，错误信息悬浮展示 |

### 6.2 SSE 推送到前端

后端的 SSE endpoint（`GET /api/runs/{run_id}/events`）从 Redis Streams 消费事件，通过 HTTP Server-Sent Events 协议持续推送到前端。关键设计：

- **消费者组**：Redis Streams 的消费者组机制允许多个消费者（如 SSE endpoint 的多个实例）协同消费，不重复、不丢失。
- **断线重连**：前端在 SSE 连接断开时自动重连，并在请求中携带 `Last-Event-ID` header，后端从该 ID 之后继续推送，确保不遗漏事件。

### 6.3 前端 ReactFlow 实时更新

前端 `useChatStreaming.ts` hook 接收 SSE 事件流，解析事件类型后更新 `runEventStore`（Zustand store）。ReactFlow 组件订阅 store 的变化，实时更新 DAG 画布：

- 节点颜色：pending（灰）→ running（黄）→ completed（绿）→ failed（红）。
- 边动画：运行中的节点输出边显示流动动画。
- 节点详情：点击节点可在侧边栏查看实时日志、工具调用记录、上游/下游依赖。
- 最终报告：`report_writer` 完成后，前端自动展示最终报告的内容，包括 Markdown 渲染的文本、数据表格和可视化图表。

### 6.4 会话完成

当所有 DAG 节点执行完毕后，`DAGScheduler` 标记运行状态为 `completed`，SSE endpoint 推送 `run_complete` 事件。前端收到后：
- 停止所有节点动画。
- 在 Chat UI 中显示最终报告。
- 运行详情面板中提供完整执行记录的下载入口（`result.json` + `report.md` + `sdk_messages.jsonl`）。

用户从输入"分析 2026 台北市长选举"到看到最终分析报告，端到端延迟通常在 30-120 秒之间（取决于 DAG 节点数量和每个节点的模型推理时间）。

## 关键路径耗时分析（典型值）

| 阶段 | 耗时 | 说明 |
|------|------|------|
| Layer 0（Planning Agent） | 2-5s | 单次 LLM 调用，轻量推理 |
| Layer 1（DAG 生成） | 5-15s | 大规模 prompt + 结构化输出生成 |
| Layer 2（验证修复） | 0-5s | 通常一次通过；Repair 每次增加 5-10s |
| Layer 3-6（编译准备） | <1s | 全部为确定性操作，毫秒级 |
| Layer 7（容器启动） | 2-5s | 长生命周期容器预热后可接近 0 |
| Layer 8（节点执行） | 15-90s | 主要耗时，取决于节点数量和模型推理速度 |
| Layer 9（事件回传） | 实时 | 事件在节点执行期间持续推送 |
| **总计** | **30-120s** | 5 节点 DAG 的典型端到端延迟 |
