# 02 规划代理详解：内部机制、配置与分支处理

## 1. 核心函数 `run_planning_agent()`

`orchestrator/chat/planning_agent.py` 中的 `run_planning_agent()` 是 Planning Agent 的顶层入口。它是一个异步生成器，产生 `PlanningAgentUpdate` 事件流。

### 1.1 函数签名

```python
async def run_planning_agent(
    *,
    router: Any,                          # PlanningAgentAdapter 实例
    user_input: str,                      # 规划专用的用户输入文本
    conversation: list[dict] | None,      # 历史对话（最近 30 条）
    resource_audit: dict | None,          # 资源审计结果
    mcp_capabilities: dict | None,        # MCP 能力描述
    planning_richness: str | None,        # 规划档位
    target_mode: Literal["ask", "ready"], # 初始目标模式
    require_ready: bool,                  # 是否强制 ready
    config: PlanningAgentConfig,          # Agent 配置
    plan_answers: dict | None = None,     # 用户已回答的问题
    requested_deliverables: list[str] | None = None,  # 请求的交付物
    current_round: int = 1,              # 当前轮次
    planning_gear: str | None = None,     # Planning Gear 值
    previous_answers: dict | None = None, # 历史答案
    focus_context: str | None = None,     # 焦点上下文
    information_state: dict | None = None,# 信息充分性状态
) -> AsyncIterator[PlanningAgentUpdate]:
```

### 1.2 执行流程

```
run_planning_agent()
    │
    ├─ _build_planning_agent_prompt()    构建完整 prompt
    │   ├─ 嵌入 system prompt（禁止文件/Shell/Web 工具）
    │   ├─ 嵌入 resource audit 快照
    │   ├─ 嵌入 MCP capabilities 描述
    │   ├─ 嵌入 conversation 压缩摘要
    │   ├─ 嵌入 Skill 引用块（chat-planner-guide / dag-planner）
    │   └─ 嵌入 output schema（PlanningDecisionPayload JSON 模板）
    │
    └─ asyncio.timeout(config.timeout_s) 超时保护
        │
        └─ _run_planning_attempts()      多轮尝试 + 校验修复
            │
            ├─ _run_sdk_session()        打开 Claude Agent SDK 会话
            │   └─ ClaudeSDKClient.query() + receive_response()
            │       产出原始 SDK message（system/assistant/user/tool_result）
            │
            ├─ 逐条 message → coerce_sdk_message() → events
            │   └─ yield PlanningAgentUpdate(kind="event", event=...)
            │
            └─ 所有 message 收集完毕后：
                ├─ _build_planning_agent_result() 解析 JSON → PlanningAgentResult
                │   ├─ planning_decision_payload_from_messages() 提取 JSON 块
                │   ├─ Pydantic Validation → PlanningDecisionPayload
                │   ├─ 按 status 分支：_build_chat_result / _build_ask_result / _build_ready_result
                │   └─ _build_ready_result 内部调用 router._workflow_plan_to_dag()
                │
                ├─ 成功 → yield PlanningAgentUpdate(kind="result", result=...)
                │
                └─ ValidationError → _repair_prompt_from_messages()
                    └─ 构造 repair prompt，追加原始 prompt 尾部
                    └─ continue 循环（最多 max_attempts 次）
```

## 2. SDK Session 管理

### 2.1 `_run_sdk_session()`

```python
async def _run_sdk_session(*, prompt: str, config: PlanningAgentConfig) -> AsyncIterator[Any]:
    with tempfile.TemporaryDirectory(prefix="planning-agent-") as temp_dir:
        work_dir = _prepare_planning_agent_workspace(Path(temp_dir))
        client_cls, options = _sdk_bundle(config=config, work_dir=work_dir)
        async with client_cls(options=options) as client:
            await client.query(prompt)
            async for message in client.receive_response():
                yield message
```

关键步骤：

1. **临时工作目录**：创建 `planning-agent-` 前缀的临时目录。
2. **Skill 同步**：`sync_workspace_skills()` 将 `claude-runtime/skills/` 下的 Skill 扁平投影到临时目录的 `.claude/skills/`，使 Agent 容器态可用。实际源文件在 `claude-runtime/` 而非 `.claude/`。
3. **SDK 客户端**：`_sdk_bundle()` 创建 `ClaudeSDKClient` 及 `ClaudeAgentOptions`，配置好 CLI 路径、model、MCP servers、permission mode、system prompt 等。
4. **查询与响应**：`client.query(prompt)` 发送完整规划 prompt，`client.receive_response()` 逐条产出 SDK message。

### 2.2 `_sdk_options_kwargs()` 配置详解

该函数构造 `ClaudeAgentOptions` 的全部参数：

```python
kwargs = {
    "cwd": str(work_dir),                    # 工作目录（临时）
    "cli_path": resolve_claude_cli(...),      # Claude CLI 可执行文件路径
    "model": config.model,                    # 模型名（来自 CHAT_PLANNING_AGENT_MODEL）
    "disallowed_tools": [...],                # 禁止的工具列表（全部文件/Bash/Web/Agent）
    "permission_mode": "bypassPermissions",   # 绕过权限提示（安全：所有危险工具已被禁止）
    "mcp_servers": build_project_mcp_config(...)["mcpServers"],  # MCP 服务器配置
    "env": _sdk_env(config=config),           # 环境变量（含 LLM 网关路由）
    "max_turns": _planning_agent_max_turns(), # 最大轮数（默认 16）
    "include_partial_messages": True,         # 包含部分消息（用于流式事件）
    "system_prompt": {...},                   # 预设 claude_code + append 自定义指令
    "setting_sources": ["project"],           # 仅读取项目级 .claude/settings.json
    "can_use_tool": _planning_agent_can_use_tool,  # 自定义工具权限回调
    "thinking": _planning_agent_thinking(...), # thinking mode 配置
}
```

## 3. `PlanningAgentConfig` 配置项

定义于 `planning_agent.py`，构造于 `planning/request_pipeline.py::planning_agent_config()`：

```python
@dataclass(frozen=True)
class PlanningAgentConfig:
    model: str                       # 模型名称 → CHAT_PLANNING_AGENT_MODEL 环境变量
    timeout_s: float                 # 超时秒数 → 按 richness 分档 (standard=120, detailed=180, comprehensive=480)
    session_id: str                  # 会话 ID，用于 LLM 网关路由
    enable_external_data: bool       # 是否允许外部数据检索
    knowledge_mcp_enabled: bool      # 知识库 MCP 是否启用
    knowledge_mcp_provider: str      # 知识库 MCP provider 名
    knowledge_mcp_json: str          # 知识库 MCP 配置 JSON
    search_mcp_enabled: bool         # 搜索 MCP 是否启用
    search_mcp_provider: str         # 搜索 MCP provider 名
    search_mcp_json: str             # 搜索 MCP 配置 JSON
    mcp_manifest: dict | None        # MCP 清单（tool schema 等）
    llm_gateway_url: str             # LLM 网关基础 URL
```

### 3.1 超时策略

`orchestrator/chat/planning_modes.py` 按 `planning_richness` 分档定义超时：

| PlanningRichness | 超时 (秒) | 说明 |
|------------------|-----------|------|
| `standard` | 120 | 标准规划，适用于简单查询 |
| `detailed` | 180 | 详细规划，包含更多 DAG 节点 |
| `comprehensive` | 480 | 全面深度规划，多轮搜索 + 复杂 DAG |

环境变量 `PLANNING_AGENT_TIMEOUT_S` 可覆盖。`planning_agent_total_timeout_s()` 从编排引擎的 `_intent_parse_timeout_s()` 获取基础超时，再与 richness 超时取较大值。

### 3.2 LLM 网关路由

环境变量 `ANTHROPIC_BASE_URL` 被设置为 `{llm_gateway_url}/run/chatplan_{session_id}`，使 Planning Agent 的 API 调用通过网关统一路由和追踪。

## 4. `PlanningAgentUpdate` 事件流

```python
@dataclass(frozen=True)
class PlanningAgentUpdate:
    kind: Literal["event", "result"]
    event: dict[str, Any] | None = None       # kind="event" 时填充
    result: PlanningAgentResult | None = None  # kind="result" 时填充
```

两种事件类型：

### 4.1 `kind="event"` -- 流式中间事件

来自 Claude Agent SDK 的逐条 message，经 `coerce_sdk_message()` 标准化后，再通过 `sdk_events_from_message()` 拆分为前端可消费的事件：

- `message.reasoning` -- 模型推理链文本块（thinking / reasoning）
- `message.delta` -- 文本增量（通常不出现在最终 JSON 前）
- `tool.start` / `tool.end` -- MCP 工具调用的开始和结束
- `message.stop` -- 消息结束

在 `planning_api.py` 中，这些事件被直接透传给 SSE：

```python
if update_kind == "event":
    event = getattr(planning_update, "event", None) or {}
    event_type = str(event.get("type") or "").strip()
    if event_type:
        yield f"data: {json.dumps(event)}\n\n"
```

### 4.2 `kind="result"` -- 最终结果

当所有 message 收集完毕且 JSON 解析/校验通过后，产出 `PlanningAgentResult`：

```python
yield PlanningAgentUpdate(kind="result", result=result)
```

## 5. 多轮修复机制 (`_run_planning_attempts`)

Planning Agent 的输出 JSON 必须通过 Pydantic `PlanningDecisionPayload` 校验。如果校验失败（`ValidationError`、`ValueError`、`json.JSONDecodeError`），系统不会立即失败，而是进入修复循环。

### 5.1 修复流程

```
第 1 次尝试
  ├─ _run_sdk_session() 完整执行
  ├─ _build_planning_agent_result() 解析 JSON
  ├─ 校验通过 → 返回 result
  └─ 校验失败 (ValidationError)
      │
      ├─ 记录 attempt_debug（validationError, previousOutputPreview）
      ├─ _repair_prompt_from_messages() 构造修复 prompt
      │   └─ router._build_planning_repair_prompt() → planning_repair.py
      │       追加：校验错误信息 + topology 修复指导 + report 修复指导
      │       要求："回复首字符必须是 `{`，直接输出修复后 JSON"
      │
      └─ 更新 prompt 为 repair prompt → 进入下一次尝试

第 2...N 次尝试
  ├─ 使用 repair prompt 重新调用 _run_sdk_session()
  └─ 同上流程

达到 max_attempts 仍失败
  └─ raise PlanningAgentExecutionError（含 planning_debug 完整调试信息）
```

### 5.2 最大尝试次数

由 `router.engine._workflow_plan_repair_attempts()` 决定。每次尝试都记录在 `attempt_debug` 数组中，最终作为 `planning_debug.payload.attempts` 返回。

### 5.3 Repair Prompt 构造

`orchestrator/chat/planning_repair.py::build_planning_repair_prompt()` 在原 prompt 后追加：

- 拓扑修复指导（`topology_repair_guidance_lines`）
- 报告修复指导（`report_repair_guidance_lines`）
- dag-planner Skill 的 `rules-and-examples.md` 引用块
- 校验错误原文（截断至 1200 字符）
- 上一次输出的前 2500 字符
- 强制指令："直接输出修复后的单个 JSON 对象，不要输出任何额外解释文字"

## 6. `_planning_agent_can_use_tool` 权限控制

```python
async def _planning_agent_can_use_tool(tool_name, input_data, _context):
    if tool_name != "Skill":
        return PermissionResultAllow()      # 允许非 Skill 工具（实际已被 disallowed_tools 拦截）
    skill_name = _skill_name_from_input(input_data)
    if skill_name in _PLANNING_AGENT_ALLOWED_SKILLS:
        return PermissionResultAllow()      # 仅允许这两个 Skill
    return PermissionResultDeny(message="...")  # 拒绝其他 Skill
```

`_PLANNING_AGENT_ALLOWED_SKILLS = frozenset({"chat-planner-guide", "dag-planner"})`

两层安全：
1. **`disallowed_tools`** 黑名单：禁止 Read/Glob/Grep/Write/Edit/Bash/WebFetch/WebSearch/Agent/TodoWrite/AskUserQuestion 等全部本地操作工具。
2. **`can_use_tool`** 白名单：对于 Skill 工具，仅允许调用 `chat-planner-guide` 和 `dag-planner`。

MCP 工具（如 `mcp__<provider>__search`）不经过 Skill 权限检查，通过 `mcp_servers` 配置注入。

## 7. `planning_round_policy.py` 多轮决策逻辑

### 7.1 `build_planning_round_policy()` 决策树

```
build_planning_round_policy(plan_state, max_rounds, force_execute, use_plan_mode, ...)
    │
    ├─ force_execute == True
    │   └─ return PlanningRoundPolicy(require_ready=True, reason="force_execute")
    │
    ├─ use_plan_mode && information_state.is_sufficient
    │   ├─ current_round < min_rounds
    │   │   └─ return (require_ready=False, reason="minimum_rounds_not_reached")
    │   │      → 即使信息充分，也必须至少跑满最低轮数
    │   └─ current_round >= min_rounds
    │       └─ return (require_ready=True, reason="information_sufficient")
    │
    └─ 其他情况（信息不充分 或 非 plan mode）
        ├─ use_plan_mode && current_round >= effective_max_rounds
        │   └─ return (require_ready=True, reason="max_rounds_reached")
        │      → 达到最大轮数，强制进入 ready
        └─ 未达最大轮数
            └─ return (require_ready=False, should_continue_asking=True)
```

### 7.2 核心数据类型

**`PlanningGear`** -- 规划深度档位：
```python
class PlanningGear(str, Enum):
    STANDARD = "standard"   # 最大 2 轮，最低 1 轮
    DETAILED = "detailed"   # 最大 3 轮，最低 2 轮
    DEEP = "deep"           # 最大 4 轮，最低 2 轮
```

**`InformationSufficiency`** -- 信息充分性：
```python
@dataclass(frozen=True)
class InformationSufficiency:
    is_sufficient: bool
    rationale: str
    suggested_next_topics: tuple[str, ...] = ()
```

**`PlanningRoundPolicy`** -- 轮次策略：
```python
@dataclass(frozen=True)
class PlanningRoundPolicy:
    current_round: int
    max_rounds: int
    require_ready: bool
    reason: str | None
    gear: PlanningGear
    information_state: InformationSufficiency | None
    should_continue_asking: bool
```

### 7.3 Planning Gear 与 PlanningRichness 的映射

`resolve_planning_gear()` 将 `planning_richness` 映射到 `PlanningGear`：

| planning_richness | PlanningGear | max_rounds | min_rounds |
|-------------------|-------------|------------|------------|
| `standard` | STANDARD | 2 | 1 |
| `detailed` | DETAILED | 3 | 2 |
| `comprehensive` | DEEP | 4 | 2 |

## 8. `planning_api.py` 三种分支处理

`stream_generate_workflow_response()` 在收到 `PlanningAgentResult` 后，根据 `planning_status` 分三路处理。

### 8.1 `planning_status == "chat"` -- 直接回复

```python
if planning_status == "chat":
    storage.set_planning_state(session_id, {})  # 清空规划状态
    # 流式输出 assistant_reply 文本
    async for stream_chunk in stream_text(assistant_reply):
        yield stream_chunk
    # 构建 chat panel + metadata → 持久化 ChatMessage
    storage.add_message(session_id, ChatMessage(...))
    return  # 不进入 DAG 流程
```

- 清空 `planning_state`
- 输出 `assistantReply` 文本
- 构建 `chat_panel`（含 audit_tool + planning_tool 的历史记录）
- 持久化消息并返回

### 8.2 `planning_status == "ask"` -- 保存问题状态

```python
if planning_status == "ask":
    questions = _enforce_ask_question_contract(...)  # 契约校验
    assistant_reply = _normalize_ask_assistant_reply(...)  # 防止泄露 ready 用语
    # 流式输出 response_content
    async for stream_chunk in stream_text(response_content):
        yield stream_chunk
    # 持久化 ask 消息
    storage.add_message(session_id, ChatMessage(...))
    # 保存规划状态，等待下一轮
    storage.set_planning_state(session_id, {
        "round": question_round,
        "pending_questions": questions,
        "previous_questions": ...,
        "planAnswers": merged_plan_answers,
        "planning_richness": planning_richness,
        "gear": round_policy.gear.value,
        "focus_context": focus_context,
        "information_state": ...,
        "ask_message_id": state.assistant_message_id,
    })
    return
```

关键点：
- `_normalize_ask_assistant_reply()` 检测并替换包含 "工作流已生成" 等 Ready 状态泄露文本，防止前端展示错误提示。
- `_enforce_ask_question_contract()` 对 questions 做契约校验（去重、限流、option 上限）。
- `planning_state` 持久化到 storage，下一轮用户回复时会从中恢复状态。

### 8.3 `planning_status == "ready"` -- 进入 DAG 生成

```python
# 清空规划状态
storage.set_planning_state(session_id, {})

# 可选：输出 ready 提示消息
if ready_msg:
    yield ready_msg

# 进入 DAG 生成阶段
yield phase.change → "generating_workflow"

# finalize DAG（同步化、规范化、校验）
dag_result = await _finalize_generated_workflow(
    runtime=runtime,
    orchestration_engine=orchestration_engine,
    dag=dag,
    storage=storage,
    ...
)

# 输出 workflow.created 事件
yield workflow_preview

# 输出 ready response 文本
async for stream_chunk in stream_text(response_content):
    yield stream_chunk

# 持久化 ready 消息
storage.add_message(session_id, ChatMessage(...))
```

关键点：
- `_finalize_generated_workflow()` 在 `run_in_threadpool` 中同步执行（涉及 DAG 规范化、去重、校验等重型操作）。
- 输出 `workflow.created` 事件，前端据此展示工作流卡片。
- 如果有 `dag_thinking` 文本且未在 planning 阶段发送，则补发 reasoning 事件。

## 10. 安全边界总结

| 层级 | 机制 | 说明 |
|------|------|------|
| 工具黑名单 | `_PLANNING_AGENT_DISALLOWED_TOOLS` | 禁止 Read/Glob/Grep/Write/Edit/Bash/WebFetch/WebSearch/Agent/TodoWrite/AskUserQuestion 等 |
| Skill 白名单 | `_PLANNING_AGENT_ALLOWED_SKILLS` | 仅允许 `chat-planner-guide` 和 `dag-planner` |
| MCP 路径 | `mcp_servers` 配置 | 外部检索通过 MCP server 限定范围 |
| 临时工作目录 | `tempfile.TemporaryDirectory` | 每次 SDK session 使用独立临时目录，session 结束自动清理 |
