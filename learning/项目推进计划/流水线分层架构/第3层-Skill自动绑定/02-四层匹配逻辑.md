# 02 - 四层匹配逻辑

## 概述

`_candidate_skill_id()`（`skill_auto_binder.py` 第 115-134 行）是 Auto-Binder 的核心匹配函数。它按**优先级递减**的顺序依次尝试四层策略，一旦命中即返回并短路后续层级。当四层全部未命中时，返回空字符串 `""`，由下游 Materializer 兜底降级为 `"__generic__"`。

```
_candidate_skill_id(node, skills)
    │
    ├── Layer 1: 显式 skill 赋值  → 命中则返回
    ├── Layer 1b: 注册表精确匹配 → 命中则返回
    ├── Layer 2: 双下划线前缀匹配 → 命中则返回
    ├── Layer 3: 关键词正则降级   → 命中则返回
    └── 全部未命中 → 返回 ""
```

## Layer 1：显式 Skill 赋值

**代码位置**：`skill_auto_binder.py` 第 117-121 行

```python
explicit = str(node.skill_id or node.skill or "").strip()
if explicit == GENERIC_AGENT_SKILL_ID:
    return ""
if explicit:
    return explicit
```

**逻辑**：

1. 从 `node.skill_id`（优先）或 `node.skill`（fallback）提取字符串值。
2. 若该值等于 `"__generic__"`（`GENERIC_AGENT_SKILL_ID`）——说明 Planning Agent 显式声明了通用 agent，**返回空字符串**让 Materializer 使用 `__generic__`（不参与后续绑定）。
3. 若该值为非空的非 generic 字符串——**直接返回**，信任 Planning Agent 的选择。

**典型场景**：Planning Agent 在生成 plan 时已经为 node 指定了正确的 `skill_id`，如 `"agenda_setter"`、`"master_analyst"`。此时 Auto-Binder 不做任何覆盖，直接采用。

**重要约束**：Layer 1 不验证 skill_id 是否在注册表中存在。如果 Planning Agent 给出了一个不存在的 skill_id，Auto-Binder 仍然返回它——注册表有效性校验在后续 `validate_plan_dag()` 中由 Materializer 完成。

## Layer 1b：注册表精确匹配

**代码位置**：`skill_auto_binder.py` 第 122-125 行

```python
node_id = str(node.id or "").strip()
if _has_skill(skills=skills, skill_id=node_id):
    return node_id
```

**逻辑**：

1. 提取 `node.id` 字符串。
2. 直接以 `node.id` 为 key 查询 skill 注册表（`skills` 字典）。
3. 若命中——**node.id 本身就是一个合法的 skill_id**，返回 `node.id`。

**典型场景**：

- `node.id = "agenda_setter"` + `skills` 中存在 key `"agenda_setter"` → 绑定 `"agenda_setter"`
- `node.id = "district_race_analyst"` + 注册表命中 → 绑定 `"district_race_analyst"`

此层的核心假设是：**当 node.id 恰好命中注册表中某个 skill 时，该 node 的意图就是执行该 skill**。这是一种基于命名约定的快速匹配，避免了额外的语义推断。

## Layer 2：双下划线前缀匹配

**代码位置**：`skill_auto_binder.py` 第 126-129 行（入口），第 154-178 行（实现）

```python
prefix_match = _match_by_double_underscore_prefix(node_id, skills=skills)
if prefix_match:
    return prefix_match
```

### 命名约定

Planning Agent 在 `allowed_mode="open"` 下生成的复合 semantic node_id 遵循命名约定：

```
<family>__<detail1>__<detail2>...
```

其中 `__`（双下划线）是分隔符，`<family>` 前缀通常与 skill 注册表中的某个 skill 族名对应。

示例：
- `district_race__taipei_north` → family = `district_race`
- `issue_impact__minimum_wage__2026` → family = `issue_impact`
- `sntv__multi_member__keelung` → family = `sntv`

### 匹配策略

`_match_by_double_underscore_prefix()` 执行**三级尝试**（第 7-12 行）：

**第一级：直接前缀匹配**

```python
prefix = node_id.split("__", 1)[0]
if _has_skill(skills=skills, skill_id=prefix):
    return prefix
```

若 node_id 不含 `"__"`，直接返回空（不进入此 layer）。提取 `"__"` 前的 family 前缀，若该前缀恰好是一个完整 skill_id（如 `district_race` 对应 skill `district_race`），直接返回。

**实际案例**：注册表中不存在名为 `district_race` 的 skill，因此通常不会在此级命中，会进入第二级。

**第二级：追加常见后缀**

```python
for suffix in ("_analyst", "_detector", "_modeler", "_profiler", "_collector"):
    candidate = f"{prefix}{suffix}"
    if _has_skill(skills=skills, skill_id=candidate):
        return candidate
```

将 family 前缀依次追加 5 个常见职业后缀并查询注册表。例如：

| node_id | prefix | 候选匹配 |
|---------|--------|----------|
| `district_race__taipei_north` | `district_race` | `district_race_analyst` (命中) |
| `issue_impact__minimum_wage` | `issue_impact` | `issue_impact_analyst` (命中) |
| `swing__taichung_central` | `swing` | `swing_district_detector` (未命中——后缀不匹配) |

**为什么需要后缀追加**：注册表中的 skill 通常以完整的 `<topic>_<role>` 命名，而 Planning Agent 生成的 family 前缀可能是 topic only（如 `district_race`），缺少 role 后缀。此步骤自动补全。

**第三级：无更多尝试**

若前缀和所有后缀组合均未命中，函数返回 `""`，进入 Layer 3。

### 边界情况

- **无 `"__"` 的 node_id**：`_match_by_double_underscore_prefix()` 直接返回 `""`，不进入 Layer 2。
- **多层 `"__"`**：仅取第一段。`a__b__c` → prefix = `a`。
- **前缀本身就是注册表 skill**：第一级直接命中，不追加后缀。

## Layer 3：关键词正则降级

**代码位置**：`skill_auto_binder.py` 第 130-133 行（入口），第 137-151 行（实现）

```python
kw_match = _fallback_skill_by_node_id(node_id, skills=skills)
if kw_match:
    return kw_match
```

### 降级表结构

`_NODE_ID_SKILL_FALLBACKS`（第 22-56 行）是一个 `list[tuple[re.Pattern, str]]`，包含 **21 条**正则规则。每条规则是 `(compiled_regex, target_skill_id)`，**按优先级排序，第一个匹配获胜**。

### 优先级设计原则

降级表最前面的条目匹配最具体、最有区分度的语义场景，后面的条目匹配更泛化的模式。例如：

1. **最优先**（第 24 行）：swing/marginal/battlefield → `swing_district_detector`（关键选区检测，语义明确）
2. **次优先**（第 26 行）：issue_impact/政策效應 → `issue_impact_analyst`
3. **中等优先级**（第 28-38 行）：SNTV、派系、选区、选民结构等专项 domain
4. **通用兜底**（第 32-33 行）：通配 `_race$` / 選區分析 → `district_race_analyst`

### 中英文双语覆盖

每条规则同时覆盖英文和中文本地化关键词：

| 目标 skill | 英文关键词 | 中文关键词 |
|-----------|-----------|-----------|
| `swing_district_detector` | swing, marginal, pivot, battlefield | 搖擺, 膠著, 激戰 |
| `sntv_vote_allocation_analyst` | sntv, multi_member, vote_management | 複數選區, 配票, 當選名額 |
| `local_faction_network_analyst` | faction, local_network, clan | 派系, 地方派系, 樁腳 |
| `recall_politics_analyst` | recall, by_election_after_recall | 罷免, 罷免門檻, 罷免連署 |
| `electoral_compliance_analyst` | integrity, fraud_claim, dispute, factcheck | 選舉爭議, 驗票, 政治獻金, 合規 |
| `local_governance_resource_analyst` | fiscal, budget_cycle, local_finance | 地方治理, 地方財政, 預算連結 |

### 查询逻辑

`_fallback_skill_by_node_id()`（第 137-151 行）：

```python
for pattern, skill_id in _NODE_ID_SKILL_FALLBACKS:
    if pattern.search(node_id) and _has_skill(skills=skills, skill_id=skill_id):
        return skill_id
return ""
```

**双重校验**：不仅要求正则 `pattern.search(node_id)` 命中，还要求**目标 skill_id 在注册表中确实存在**（`_has_skill()`）。这防止了降级表指向已删除/未加载的 skill。

**first-match 语义**：在降级表中找到第一个同时满足"正则命中 + skill 存在"的条目即返回，后续条目不再尝试。

## 匹配失败兜底

当四层全部未命中时，`_candidate_skill_id()` 返回 `""`。回到 `_auto_bind_node()`：

```python
candidate = _candidate_skill_id(node, skills=skills)
if not candidate:
    return node
```

node 保持未绑定状态（`skill_id` 和 `skill` 为空）。随后在 Materializer 的 `validate_plan_dag()` 中：

- `_validate_node_allowlist()` 检查未绑定 node 是否合法
- 在 `allowed_mode="open"` 下，未绑定 node 被允许，但会被赋予 `"__generic__"` skill
- `DAGNode.agent_config["skill"]` 最终值为 `"__generic__"`

这意味着通用 agent 将加载 `claude-runtime/skills/__generic__/SKILL.md`（如果存在），或使用容器内的默认 Claude Code 行为执行任意自然语言任务。

## 匹配验证：注册表存在性

所有 Layer 1b、2、3 的匹配结果在返回前都会经过 `_has_skill()` 验证（skill_id 是否在注册表 `skills` 字典中存在）。唯一的例外是 Layer 1（显式赋值），它信任 Planning Agent 的选择，但当 `node.skill_id == "__generic__"` 时被特殊处理为返回空字符串。

## 性能特性

- **零 I/O**：所有匹配在已加载的 Python dict 和预编译正则上完成
- **短路求值**：四层依次尝试，命中即返回
- **正则预编译**：`_NODE_ID_SKILL_FALLBACKS` 在模块加载时一次性编译，后续调用零开销
- **O(n)** 复杂度：n 为 node 数量，每个 node 最多执行 21 次 `pattern.search()` + dict `in` 检查
